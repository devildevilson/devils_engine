# devils_engine — каталог маленьких playground-проектов

Этот документ описывает ограниченные проверочные проекты. Playground — основная единица текущего
планирования: законченный срез, который можно запустить и оценить глазами/на слух либо который доказывает
крупную симуляционную систему. Нумерованные задачи движка остаются каталогом зависимостей и не задают
порядок работы сами по себе.

Playground отвечает на конкретный технический вопрос и заканчивается наблюдаемым результатом. Если он
оказался полезен, его можно расширять следующими именованными slices; некоторые стенды естественно
превратятся в ранние срезы игр. До этого момента они не обязаны иметь сюжет, баланс, production UI или
законченный art style.

## Общие правила

### Что считается хорошим playground

- Запускается отдельным executable или отдельным явно выбранным scenario.
- Имеет один главный технический риск и не более двух вторичных.
- Использует обычные engine resources, manifests и lifecycle, а не специальный тестовый путь.
- Имеет маленький authored либо generated fixture, который легко понять глазами.
- Позволяет менять ключевые параметры в runtime и видеть промежуточные состояния.
- Поддерживает headless validation там, где результат не обязан оцениваться глазами.
- Имеет измеримые критерии завершения: frame time, determinism, memory, latency, artifact hash или
  корректный state transition.
- Имеет свой `README.md`: назначение, запуск, точки входа, debug views, граница и Definition of Done.
- Может быть удалён без потери проектного контента: ценность остаётся в закреплённом engine contract,
  tests и reusable resources/tools.

### Чего в playground быть не должно

- попытки сразу собрать полный gameplay loop;
- production-контента и большого числа уникальных assets;
- временной архитектуры, обходящей обычный `simul`/`demiurg`/`painter` path;
- project semantics внутри engine только ради удобства одного стенда;
- нескольких крупных неизвестных одновременно;
- требования «выглядеть как готовая игра».

### Общая оболочка

Полезно дать всем graphical playgrounds одну небольшую оболочку:

- свободная и фиксированная camera;
- pause, single-step и time scale;
- выбор scenario без перекомпиляции;
- runtime parameter inspector;
- небольшой Visage overlay с названием/описанием сцены, controls и FPS/frame time;
- render-target/debug overlay;
- CPU/GPU timings и resource residency;
- capture screenshot + config/resource/build fingerprints;
- reset scenario в исходное состояние;
- deterministic seed;
- опциональный headless запуск с фиксированным числом ticks/frames.

Frame pacing этой оболочки не выводится из present mode: MAILBOX/FIFO/IMMEDIATE выбирают tearing и
поведение presentation queue, а отдельный deadline + sleep limiter задаёт частоту producer loop. На обычном
desktop предпочтителен MAILBOX-first; fallback между FIFO и IMMEDIATE выбирается явно по политике платформы.

Первый рабочий common slice уже используется PF01: `frame_pacer` держит абсолютный deadline и отбрасывает
пропущенное расписание без catch-up burst, а non-interactive Visage-overlay загружает общий Lua entry/MSDF
font и показывает описание сцены, controls, сглаженные FPS/frame time. GPU upload/font descriptor и
`draw_ui` остаются обычными ресурсами render graph конкретной лаборатории.

Это не полноценный editor. Оболочка только делает маленькие experiments наблюдаемыми и повторяемыми.

### Режим работы

- В каждый момент активна одна campaign и один её лабораторный срез.
- Мелкая задача из `ROADMAP.md` берётся только как обнаруженный blocker текущего результата.
- Числовой/focused test закрепляет контракт, но не выбирает направление работы.
- Независимая идея, не мешающая текущему срезу, остаётся в backlog/parking lot.
- Лаборатория закрывается запускаемым сценарием, debug-представлением, минимальным regression contract
  и обновлённой документацией.
- Все площадки физически живут под `subprojects/playgrounds/<CODE>_<human_name>/`; уже доказанная общая
  оболочка постепенно собирается в `subprojects/playgrounds/common/`.

## Текущий фокус — Painter visual stack

Campaign содержит десять независимых painter-лабораторий `PF01`–`PF10`: `PF01`–`PF08` закрыты,
[`PF09_territory_zoning`](subprojects/playgrounds/PF09_territory_zoning/README.md) остаётся отдельной открытой
площадкой, а текущий новый фокус —
[`PF10_functional_planet`](subprojects/playgrounds/PF10_functional_planet/README.md): displaced сферическая
поверхность, устойчивые при вращении провинции и interaction. `anomalous_weather` перенесена в ненумерованный
parking lot и не занимает следующий код заранее.
PF04 закрыт основными срезами: `D24S8`
selection/outline/debug; независимые bits `0x02/0x04` для local tint и spatial window; runtime
`StencilReference/CompareMask/WriteMask`; asymmetric front/back fixture; а после закрытия — отдельная coverage+depth selection mask,
трёхпиксельный depth-aware screen-space outline, optional through-wall selector и `depth_fail_op`-силуэт скрытой цели на bit `0x40` с явным порядком относительно portal. Внутреннее
представление dynamic states свёрнуто из растущего набора bool-полей в один массив Vulkan values;
их человеческие имена и mapping задаёт один X-macro list в `painter/common.h`.

`PF03` закрыт 2026-08-21 полной запускаемой post-цепочкой, numeric/debug контрактами и shader-аудитом.
Финальная незакрытая техника, TAAU, теперь действительно реконструирует: при масштабе 0.5 ошибка против
native TAA составляет `2.98/255`, у простого upscale — `7.40/255`; непрерывный coverage дополнительно убрал
заметное переключение кромок при движении камеры. Аудит, исправленные контракты и
сознательно оставленные production-границы записаны в
[`SHADER_AUDIT.md`](subprojects/playgrounds/PF03_post_processing/SHADER_AUDIT.md). Проект build-вариантов уже
выбранного render graph, declared-value references и частичных material/step patches вынесен в
[`RENDER_PROFILES.md`](subprojects/playgrounds/PF03_post_processing/RENDER_PROFILES.md): основной state —
независимые graph-specific settings, общий preset лишь массово их записывает, а concrete variant выводится
resolver'ом. Реализация остаётся отдельным backlog, а не блокером следующей площадки.

Лаборатории не образуют CMake/source dependency chain. Более поздняя площадка может выборочно взять
зафиксированный baseline ранней либо общий код из `common`/`libs/painter`, после чего развивается
независимо. Поэтому расширение ранней gallery не меняет автоматически `PF06`.

[`GN05_constraint_collapse`](subprojects/playgrounds/GN05_constraint_collapse/README.md) **ОТКРЫТА
2026-09-05** как первый потребитель решателя ограничений. Нужен он ровно за одним, чего не даёт ни
шум, ни вороной, ни заливка: ЖЁСТКИЙ ЛОКАЛЬНЫЙ ЗАПРЕТ — «вода никогда не касается травы». Апертура у
него `sequential`, и это не деталь реализации: какую клетку наблюдать следующей, решает поле,
оставшееся после предыдущего распространения, — поэтому в очередь он не попадёт и на устройство не
поедет никогда. Он же единственный инструмент библиотеки, который может НЕ НАЙТИ ответа: противоречие
здесь нормальный исход, а исчерпание объявленных попыток — громкий отказ, потому что недособранная
сетка это другой мир под тем же зерном. Энтропия заменена целочисленным критерием ради детерминизма
(ничья ломается хешем от номера клетки и зерна, как у `graph_flood`), а память — только волна, без
счётчиков поддержки на 64 МиБ. Неожиданное число: веса объявлены как `трава 2.4`, `лес 1.8`,
`вода 1.0`, а выходит `вода 32%`, `трава 20%`, `лес 11%` — вес это предпочтение ПРИ ВЫБОРЕ, а не
частота в результате.

[`GN04_texture_generation`](subprojects/playgrounds/GN04_texture_generation/README.md) **ОТКРЫТА
2026-09-04** как первый настоящий потребитель вычислительной очереди. Случай выбран не наугад: это
единственное место, где НЕ МЕШАЕТ ни одна слабость очереди — результат остаётся на устройстве
(передача не платится), детерминизм не требуется (представление, а не симуляция), свёртка
целочисленная (порядок прихода групп не важен), цепочка короткая. Главное число — `4096:1`: мегабайт
картинки остался на GPU, наружу уехали 256 байт сводки. Неожиданное число — гистограмма через атомики
дороже самой разметки Вороного (`7.43` против `4.65` мс) из-за конкуренции 262144 пикселей за 64
счётчика; правильная форма (накопление по группе, один атомик на группу) названа и не сделана до
появления настоящего потребителя свёртки. Окна у площадки нет намеренно: она доказывает, что картинка
не уезжает с устройства, а окно это доказательство подменило бы.

**Переведена на составленный pipeline 2026-09-05** (`22/22`): проходы больше не связаны руками —
площадка объявляет вызовы и границу, а программы, наборы дескрипторов, порядок, барьеры, загрузку и
выгрузку составляет `originator::device_queue`. Отношение стало проверяемым по-настоящему: рядом
строится ВТОРОЙ план из тех же вызовов с границей осмотра, он не запускается вовсе (вся передача
выведена при составлении), и сравниваются ПЛАНЫ — `65537:1` на `1024x1024`. Из четырёх полей растра
картинкой стало ровно одно, и никто этого не объявлял: объявлено было «вход прохода сглаживания
читают фильтром». Разметка совпала с путём на CPU на ВСЕХ пикселях.

**В тот же день пайплайн уехал в КОНФИГ**, как у остальных площадок кампании: `buffers.tavl`,
`values.tavl`, точка входа и тело шага в lua, а в `main.cpp` не осталось ни строки GLSL и ни одной
команды Vulkan. Тела шести проходов уехали в библиотеку нативными инструментами (`voronoi_label` с
необязательным вторым выходом, `filtered_blur`, `label_colour`, `count_by`), и это ответ на вопрос
«общие они или уникальные»: общие, а один из них площадка попросту переписывала. Где считать —
объявляет число манифеста, а не флаг площадки. Полный контекст — `ORIGINATOR_GPGPU.md` §5 п.5, §9 и
§10.

[`GN01_generator_contract`](subprojects/playgrounds/GN01_generator_contract/README.md) **ЗАКРЫТА
2026-08-31** закрывающим аудитом. Пайплайн описан в `tavl`, тела шагов — lua в роли `command`,
параллельное исполнение совпадает с последовательным побайтово по всем буферам. Три уровня исполнения
измерены на одном правиле, `4 194 304` элемента: нативное ядро `3.44` нс/элемент, `devils_script`
`90.05`, поэлементный lua `120.13`, и у последнего параллельного пути нет вовсе. Подключены FastNoise2
(граф шума = закодированная строка в конфиге, кросс-машинный детерминизм через `FASTNOISE2_STRICT_FP`)
и jc_voronoi (разметка, соседство из Делоне, контуры как планарная сетка с общими вершинами —
замощение карты проверено точно). Оба инструмента `scatter` дают побитово одинаковый результат при
любом числе потоков. Чанкование замерено по апертурам: pointwise переживает его точно, gather
расходится строго в полосе шириной `radius`, глобальный `scatter` в чанковом проходе не собирается по
объявлению носителя ключа.

Четыре правила, каждое из которых было ошибкой до замера: полные строки у регулярного шума
(отрезок с середины строки расходится), `STRICT_FP` вместо выбора набора SIMD в рантайме, **два**
зерна вместо одного при чанковании (иначе шум разъезжается на швах), и несовместимость самокалибровки
по измеренному диапазону с чанкованием. Закрывающий аудит нашёл восемь пунктов, включая настоящий баг:
быстрый путь доступа к полю сверял только размер, поэтому `span<float>` над полем, объявленным сырым
`uint32`, проходил и молча писал туда биты float.

[`GN02_planet_generator`](subprojects/playgrounds/GN02_planet_generator/README.md) **ЗАКРЫТА
2026-09-02 закрывающим аудитом** (первый вертикальный срез — 2026-08-31): планета считается целиком от тектоники вниз по причинам.
Девять шагов — топология, тектоника, поверхность, области рельефа, климат, сезоны, люди, области,
география, — и каждый читает то,
что записал предыдущий. Адрес поверхности здесь направление, а не пара координат: клетки лежат
равнораспределённой решёткой Фибоначчи, соседство — симметризованный CSR, поэтому швов нет и суммы по
клеткам считаются без весов площади. Уровень моря не задан числом, а найден бисекцией под заданную
долю суши; осадки нормированы на среднее по СУШЕ (нормировка по планете дала 28% пустыни, потому что
над океаном дождь идёт всегда); конвективный дождь нелинеен по температуре, иначе экватор выходит суше
средних широт. Провинции и морские зоны нарезаны заливкой по ПОДГРАФУ (вода непроходима), а не по
дорогой цене: иначе провинция через пролив остаётся двумя кусками. Итог — пакет на диске с отпечатком;
`69/69` проверок на пяти зёрнах (одно столкновение имён материков на зерне `1` нашлось этой проверкой
и вылечено по построению: при совпадении затравка продвигается), `5.5 с` на 262144 клетках (разрешение по умолчанию) и `25.0 с` на
миллионе в Release.
Есть и окно (`--view`): сглаженная сфера с подписями мест и выделением области мышью, двадцать полей на цифрах, просмотр ПО ШАГАМ генерации (`[`/`]`
пересчитывают мир до шага N), кнопка другого зерна и простые настройки генератора, границы и шаг
которых объявлены рядом с самим значением в `values.tavl`. Оно же в первые минуты
нашло два дефекта, которых числа не показывали: расселение культур считалось в шагах графа (то есть
зависело от разрешения) и на карте меток земля без метки красилась как вода, из-за чего занятые `87%`
пригодной суши выглядели пятнышком.

Отдельно взят срез играбельности: материки расставлены разнесёнными центрами (а не выбором плит,
который давал то сверхматерик, то сушу в одном полушарии) и ГРУППАМИ (ровно разнесённые центры дали
восемь одинаковых одиночных материков: `13%` в крупнейшем куске против `52%`), островов много, они
среднего и РАЗНОГО размера, прибрежная эрозия смывает крошки в одну-две клетки, а размер провинции
ограничен и сверху вместимостью заливки, и снизу слиянием — в долях от средней, поэтому границы не
зависят ни от разрешения, ни от числа провинций.

**Острова, области и вода 2026-09-02.** Океанические острова больше не задаются числом: плюм стоит в
мантии, плита едет над ним, и цепь, её направление, возраст и длина выпадают из геометрии полюса
Эйлера, а не задаются параметрами; второй механизм — островная дуга, и работает она только как ДВЕ
части, широкая платформа задугового бассейна плюс узкие вулканы на ней. Появился отдельный шаг
`landforms`: он опознаёт физические ОБЛАСТИ (нагорье, низина, шельф, архипелаг, горная страна,
вулканический остров) по измеренным величинам и затем УСИЛИВАЕТ каждую — равнина становится ровнее,
горы резче, проливы архипелага глубже. Разброс между прибрежной равниной и горами вышел
двадцатисемикратным по уклону. Доля суши поднята до 40% при СОХРАНЁННОМ объёме воды (океан глубже,
объём 1.03 земного, и он печатается в отчёте): жизнь идёт по суше, и океан на карте воспринимается
меньше, чем он есть. Побочное свойство физических островов — разрешающая способность: постройка
поперёк в две сотни километров на решётке из 16 тысяч клеток занимает полторы клетки, поэтому
разрешение по умолчанию стало 262144, а контрактная проверка идёт на 49152.

**Очередь задач 2026-09-02** записана списком в README площадки; из семи пунктов сделаны пять.

*Дуги стали архипелагами (пункт 5).* Выбрана правка тектоники, а не резка готовой картинки, и обе
части починки физические: фронт дуги ГУЛЯЕТ относительно жёлоба (у настоящей дуги угол погружения плиты
меняется вдоль стыка — это и был ответ на «полоса РОВНОЙ формы»: расстояние до стыка считается
заливкой по графу и оттого гладкое), а сама дуга разбита поперечными проливами по образцу Алеутской и
Курильской. Ключевой находкой было то, что мельчащая вулканы маска не решала ничего, пока платформа
задугового бассейна оставалась непрерывной и поднимала дугу целиком выше воды. Измерено: кусков
`18 → 87`, медиана `254 → 28` клеток, вытянутость `4.9 → 2.3`, полос длиннее четвёртных `61% → 15%`.
Для этого в отчёт добавлено измерение ФОРМЫ куска — вытянутость через собственные значения матрицы
разброса клеток: без числа спорить о «полосах» бессмысленно.

*Иерархия названных мест и титулы (пункты 3 и 4).* Девятый шаг `geography` плюс два инструмента, каких
в движке не было: `connected_components` (связный кусок — это не значение поля, а свойство графа) и
`label_adjacency` (CSR по МЕТКАМ). Второй и есть ответ на главное правило задачи: уровень растится по
графу соседства ПРОВИНЦИЙ, поэтому граница уровня физически не может пройти внутри провинции — совпадение
границ не проверяется, а выполняется по построению. Титулы де-юре оказались не вторым разбиением, а тем
же множеством провинций в других масштабах, причём де-юре королевство ЕСТЬ историческая область;
державы де-факто, наоборот, растятся голосованием по населению, а не делением площади, и 83% их
графств выходят собственной культуры. Названия лежат ЗАТРАВКОЙ, а не текстом (буферы числовые, а имя
полностью определено затравкой), традиция слогов выбирается культурой, а историческая область
называется стороной света своего материка — «Северная Европа». На 262144 клетках: 109 массивов → 19
материков → 288 областей → 3235 провинций, 56 империй → 967 герцогств → 8533 баронства, 341 держава.

*Три ошибки, которые нашлись только счётом.* (1) Уровень нельзя растить по всему множеству сразу:
заливка не переходит через воду, и число областей начинает определяться не размером области, а тем,
сколько кусков суши есть на планете — три затравки океанов накрыли 57 зон из 94, остаток дал 35
«океанов» по одному озеру. (2) Мелкий массив не должен получать свой материк: Япония — остров, но
материк у неё Азия, иначе сотня островов даёт сотню «материков». (3) Записи областей индексировались
ДВУМЯ способами сразу — скрипт писал центр по «метка минус один», а `group_by`/`accumulate` кладут по
сырому ключу, — и запись склеивала две разных области; живой эффект: слияние мелких провинций читало
`frontier` соседа. Ловится это только сложением, и такая проверка теперь стоит в `--verify`.

*Просмотрщик (пункты 1 и 2).* vsync вернулся в движок целиком: `choose_swapchain_present_mode` теперь
принимает желаемый и запасной режимы, по умолчанию `Fifo`. Ограничителей оказалось ДВА, и это выяснилось
замером — со снятым производящим циклом частота осталась 63 кадра в секунду, её держал режим
представления. Звёзды: отдельный полноэкранный проход, и главный урок тот же, что в PF07, — считать
надо не число, а нужную величину: счёт звёзд сошёлся (315 на половине экрана при расчётных 950 на
весь), а небо не читалось, потому что медианная звезда светила на 20 из 255. Плюс найдена настоящая
геометрическая ошибка: кубическая решётка в ОБЪЁМЕ не биективна направлениям, звезда уезжает в соседнюю
клетку и не рисуется никем — нужна кубическая развёртка.

*Скопления островов, тактильность и сглаживание — очередь закрыта целиком.* Появился ТРЕТИЙ механизм
островов, потому что ни цепь горячей точки, ни островная дуга скопления вроде греческого архипелага дать
не могут: у обоих острова стоят ЛИНИЕЙ. Эгейское море — затопленное нагорье на континентальной коре:
кора за дугой растянута, область просела, над водой торчат вершины прежнего складчатого пояса. Механизм
поэтому не «поднять острова», а ОПУСТИТЬ ГОРНУЮ СТРАНУ, и он потребовал четырёх исправлений, каждое
пойманное числом: условия задаются порогами по отдельности (произведение четырёх величин около половины
после общего насыщения давало «полное растяжение» всюду, и материки превращались в решето); полоса
шириной в размер настоящего архипелага, а не широкая область (спад 0.18 рад накрывал почти всю сушу,
потому что расстояние до стыка мало почти везде); ороген гасится маской бассейна, иначе поднятие
поднимает опущенную кору обратно (459 замкнутых водоёмов при 13 островах); и отметка внутри бассейна
ЗАМЕНЯЕТСЯ шельфовой, а не уменьшается на фиксированную величину — фиксированная просадка не знает, где
стояла кора. Мерить надо было не число островов, а ДОЛЮ СУШИ внутри бассейна: при 45% она смыкается в
один массив (порог протекания), при 15% островов мало; взято 23% — 49 островов, 25 из них в скоплениях.

Сглаживание (пункт 7) заняло два захода, и второй переставил водораздел: **вершина решает форму,
фрагмент решает всё остальное**. Первый заход увёл цвет на четыре ближайшие клетки (это убрало террасы
рельефа) и берег — во фрагмент, на уровень 0.5 гладкой доли суши. Второй нашёл, что выбор области на
вершине НЕВОЗМОЖЕН в принципе: метка дискретна, поэтому любое интерполируемое число смешивает две
разные метки, а обход «пара цветов плюс знаковое поле» разбивается о вершины в глубине области — у них
пары нет, знак не согласован с соседями, и на карте появляются обведённые лоскуты внутри провинций.
Согласовать знак глобально нельзя: это требовало бы двудольности графа соседства областей.

Поэтому пиксель сам находит свою клетку — спуском по графу от клетки, которую назвала вершина (ячейки
Вороного выпуклы, а треугольник мельче клетки, значит шага нужно одного) — и считает ПОКРЫТИЕ областей
компактным ядром. Ширина ядра ВЫВЕДЕНА, а не подобрана: одноклеточная область обязана выигрывать в
своём центре у худшего кольца из восьми соседей, отсюда `8·(1 − 1/R²)² < 1`, то есть `R < 1.244`, и
взято `1.2`. Первая попытка ставила `1.5` «на глаз» и была неверна арифметически — при ней с карты
исчезают 154 клетки массивов суши и 91 клетка провинций, то есть как раз одноклеточные острова,
полученные физикой; проверка на это теперь стоит в `--verify` и повторяет правило шейдера.

Отсюда же общее правило: **метке нужна граница, числу нужна интерполяция**. Класс — тоже метка, поэтому
климат и области рельефа заливаются плоско, как провинции: пока их смешивали «мягко» со степенью от
веса, обе карты выходили БУСАМИ по клеткам. Число (высота, температура) интерполируется линейно, и
параметр резкости ушёл целиком — между этими двумя случаями ничего не понадобилось. Линия границы легла
на НУЛЬ ТОГО ЖЕ ЗАПАСА, по которому выбрана заливка, поэтому разойтись с ней она больше не может; до
этого было четыре неверных попытки, и самая поучительная — размытый рубеж: у беззнаковой величины нет
стороны, поэтому её уровень 0.5 даёт ДВЕ линии, каждую в клетке от настоящей границы. Наличие линии —
отдельный флаг от наличия областей: у смысловой палитры (климат) чёрная черта между пустыней и степью
сообщала бы о рубеже, которого в природе нет. Цена: `254 → 207` кадров без ограничения, с vsync
по-прежнему ровно 60.

*Дырявые границы (третий заход).* На удалении линия рвалась на штрихи, и обе причины оказались про
ДИСКРЕТИЗАЦИЮ, а не про поле. Наклон поля нельзя брать экранной производной: набор клеток окрестности
меняется на рёбрах Вороного, покрытие получает крошечный скачок — граница от него не шевелится, а
производная улетает, и по ней считалась толщина линии. У компактного ядра производная есть
аналитически (`-4u(1-u²)/R`), она непрерывна, и градиент покрытия собирается из неё суммой по клеткам
области. Вторая причина — край заливки не сглаживался: лестница в один пиксель под тонкой линией и
делала её дырявой. Доказательство было прямым — тот же кадр в двойном разрешении с уменьшением вдвое
давал чистую линию. Сглаживание края считается ДОЛЕЙ ПЛОЩАДИ ПИКСЕЛЯ по тому же расстоянию, что и
линия, и это не запрещённое смешивание метк: смешиваются не значения областей, а их доли в площади
пикселя, ровно как у буквы в шрифте. Общее правило: заливка, её край и её граница обязаны считаться
ОДНИМ полем. Масштаб сглаживания вынесен кнопкой (`B`) и ключом `--smoothing=`: вкус — настройка,
границы диапазона — выведены. Цена: `207 → 150` кадров, разброс между прогонами `136..171`.

Две бесшумные ошибки за проход, и обе одного рода — молчащая подмена значения. (1) Число соседей лежит
в записи ЦЕЛЫМ, и читать его надо разрядами, а не приведением типа: целое 6 в разрядах float это
денормал, то есть нуль; окрестность оказывалась пустой, спуск не шагал ни разу, и картинка МОЛЧА
возвращалась к решётке Вороного. (2) Номер защёлки нажатия назначается руками у каждого вызова, и с
добавлением кнопки сглаживания он вышел за массив — запись мимо массива поменяла НОМЕР ПОЛЯ, и окно
показывало рельеф вместо запрошенного ключом. Признак у обеих один: правка, которая обязана всё
изменить, не меняет ничего, или меняет НЕ ТО. Проверка границы теперь стоит внутри самой защёлки.

Тактильность (пункт 6): подписи мест — ДЕКАЛИ НА ПОВЕРХНОСТИ. Каждый угол каждого глифа лежит на сфере
(направление угла считается от якоря сдвигом по касательному базису и нормируется), поэтому надпись
гнётся вместе с планетой, укорачивается к горизонту и заслоняется горой. Первый заход рисовал ЩИТОК с
высотой в долях экрана — читался всегда, но висел НАД планетой, а не лежал на ней. Размер поэтому в
РАДИАНАХ: у декали есть место на поверхности, значит есть и размер на поверхности, а читаемость держит
не постоянный размер, а три порога (экранный размер = он же LOD, горизонт, занятый ПРЯМОУГОЛЬНИК —
точки мало, у длинного названия другая ширина). Плюс выделение лучом из камеры в клетку с подсветкой её
области. Главное свойство выполнено: что выделяется и подписывается, определяет ВЫБРАННОЕ
ПРЕДСТАВЛЕНИЕ, а уровень объявлен рядом с самим представлением, а не выведен второй формулой.

Попутно: `find_present_modes` вернулся к ранжированию ВОЗМОЖНОСТЕЙ (mailbox, потом fifo) — политика
вертикальной синхронизации живёт в том, что просит свопчейн, а не в опросе железа; оверлей выключается
кнопкой `U`; и найдены два бага, каждый громкий: блок камеры, повторённый в шейдере БЕЗ одного поля,
уводит все следующие поля на чужое смещение (так пропал весь интерфейс, и ни ошибки, ни предупреждения
при этом нет), а ёмкость морских зон зависела только от запрошенного их числа — на миллионе клеток
метка дошла до 1302 при 1232 корзинах, потому что замкнутых водоёмов тем больше, чем мелче решётка.

Итог по площадке: **очередь задач закрыта целиком**, `67/67` проверок на пяти зёрнах, `321/321` тестов
проекта, `5.5 с` на 262144 клетках и `25.0 с` на миллионе в Release, пакет `117 MB`.

**Переработка рельефа 2026-09-01** («правдоподобнее и выраженнее») нашла шесть настоящих ошибок модели,
и все одного рода: величина считалась не там, где имеет смысл, а результат при этом оставался
правдоподобным на вид. Скорость сближения плит ненулевая только на ленте в ОДНУ клетку, поэтому все
ширины пояса в конфиге не значили ничего; частоты шума были примерно в сто раз ниже задуманного, потому
что в закодированное дерево зашита своя частота; глубину дна и построенный склон делали ДВА механизма
сразу, и побеждал случайный; островной конус складывался с материковым вместо наложения; нормировка
фрактала по сумме амплитуд делала его слабее одной октавы; кривая возраста дна была линейной по ШАГАМ
заливки и потому зависела от разрешения. Общий вывод: мерить надо ФОРМУ поля — гипсографию и уклон по
классам поверхности, — а не только его размах: правдоподобные min/max скрывали каждую из шести.

Три свойства `devils_script`, изменившие форму правил: вызов функции не является операндом выражения;
у контекста восемь слотов аргументов (то есть не больше семи `ctx:arg`); и **перенос строки заканчивает
выражение** — элементы в `ds` разделяются `,` или `\n`, поэтому формула, разбитая на две строки, это
законно две формулы. Последнее не дефект, а правило языка, но наступить на него легко: та же формула
роста населения в одну строку дала `0..0.49`, а в две `0.00013..1`, и без ошибки, потому что ошибки
нет. Отсюда правило конфига: выражение занимает одну строку, перенос — только после запятой.

*Закрывающий аудит GN02 (2026-09-02).* Десять пунктов, четыре из них настоящие дефекты. Клик выбирал
БЛИЖАЙШУЮ клетку, а карта заливает победителя по покрытию — у границы это разные ответы, поэтому щелчок
у края выделял соседнюю область; правило карты сведено в одну функцию, которую зовут заливка, проверка
и выбор мышью. Ключ `--smoothing=W` молча притягивался к ступени кнопки, потому что просмотрщик держал
номер ступени, а не число. Комментарий «обратного отображения метка → клетка в данных нет» оказался
НЕПРАВДОЙ — оно строится тем же `group_by`, только по полю затравки, — и из-за этой неправды самый
дорогой шаг делал пять плотных обходов в lua: `regions` `1334 → 1204 мс` при побитово том же
результате, а цена одного обхода измерена дублированием обхода (`35..105 мс`). Обрезание кольца соседей
до восьми не было проверено, хотя степень в графе доходит до двадцати четырёх: отброшенный вес
отрезается НЕ симметрично относительно границы, и проверка теперь мерит, что за ядром он и остаётся.
Плюс: классы правил связаны с именами и палитрой (палитра зажимает, поэтому новый класс молча взял бы
цвет предыдущего), пять рукописных копий блока камеры сведены в один включаемый файл (механизм в движке
был, площадка им не пользовалась), убрана мёртвая varying и описана скрытая связь `--frames` с
фиксацией вращения. Оставлено сознательно: один плотный обход остался в
`S02_tectonics.lua`, потому что помощника между телами шагов не разделить, и это решение автора движка, а не
пробел — `require` притащил бы за собой `demiurg`, поэтому внутри площадки дублирование кода норма
(оттуда же и отсутствие `os`: у скриптов генератора нет ни выхода в ОС, ни источников недетерминизма).
НАЗВАН один пробел движка: заливка карты по покрытию решётки как часть painter — после второго
потребителя.

*Правки по разбору аудита (2026-09-02).* Базовые функции lua теперь приходят из движка: в окружение
тела шага ставится `bindings::basic_functions` (таблица `base`), и скрипты переведены с рукописного
splitmix на `base.prng64_2` — ОДИН ХЕШ НА ВЕСЬ ДВИЖОК вместо копии в каждом файле. Для этого базовые
функции вынесены в отдельную цель `devils_engine::bindings_base`: раньше они лежали вместе с
биндингами nuklear и тянули visage в headless-генератор (заодно развязался круг visage↔bindings).
Последствие названо прямо: другой хеш — другой мир при том же зерне, все числа отчёта сдвинулись, и НИ
ОДНО свойство не сломалось (71/71 на тех же зёрнах) — довод за проверки-свойства вместо эталонных
снимков. Скрипты пайплайна названы по шагам (`S01_topology.lua`, `S02_convergent.ds`; у правила `ds` —
номер шага, где оно встречается первым), поле буфера пишется оператором (`position = v3` вместо
кортежа: строка с оператором это та же ПАРА, поэтому оба написания валидны). Двоеточия хотелось, но `:`
не входило в `operator_chars` tavl — правка в tavl сделана с тремя тестами и ждёт релиза. Новый мир
вскрыл пятую находку того же семейства: имена исторических областей могли совпасть внутри материка
(сторон света пять, областей до двадцати), вылечено по построению.

[`GN03_streaming_volume`](subprojects/playgrounds/GN03_streaming_volume/README.md) **ЗАКРЫТА
2026-09-04 закрывающим аудитом** (открыта 2026-09-03). Первая площадка кампании, у которой результат генерации — ГЕОМЕТРИЯ, а не поле
на клетках, и первая, где мир считается только вокруг наблюдателя. Свободная камера летит, вокруг из
чанкового поля плотности строится поверхность marching cubes: холмы, нависания, арки и ходы.

Главным вопросом был выход ПЕРЕМЕННОЙ длины: до сих пор все буферы originator имели известную длину —
сколько клеток, столько высот, — а сколько треугольников даст поле, не знает никто до исполнения.
Ответ оказался коротким: нового механизма в библиотеке не понадобилось. Ёмкость объявлена размером
буфера, занятая длина приезжает обычным буфером на один элемент (как любое состояние между шагами), а
переполнение — громкий отказ с именем буфера и двумя числами, потому что обрезанная поверхность
выглядит как дырка в мире. Инструмент `marching_cubes` живёт в движке (`add_volume_tools`), у него
апертура `scatter` и первый честный `chunk_local` в проекте: группа — это список вершин одного
прохода, и чанк заканчивает его сам. Его таблица случаев ВЫВОДИТСЯ из правила соединения на грани
куба, а не переписана из статьи: правило — функция только четырёх знаков самой грани, поэтому два
соседних куба видят общую грань одинаково, и непрерывность получается по построению.

Измерено (Release, Iris Xe): чанк 32 клетки, `42875` отсчётов — `4.15` мс и `8524` вершины в один
поток; `216` чанков в секунду в один поток против `870`–`970` на одиннадцати (`4.0`–`4.5x` — упирается в память,
каждый поток тащит свой буфер в 1.4 МиБ); окно по умолчанию `9x9` чанков на четыре слоя = 324 чанка и
`4.67` млн вершин, кадр `4.44` мс одним вызовом отрисовки. Проверок `23/23` плюс `6/6` тестов
инструмента в движке; всего по проекту `361/361`.

Четыре находки, каждая — ошибка до замера. «Замкнута» — это про НАПРАВЛЕННЫЕ рёбра: критерий «ровно
два треугольника на ребро» дал 74 ложных отказа из 20752 рёбер, потому что на неоднозначной грани
поверхность законно КАСАЕТСЯ САМОЙ СЕБЯ вдоль отрезка. Метры оказались не метрами: у общего дерева
шума движка свой масштаб (период `91` единицы при частоте 1, размах `±1.35`), поэтому «форма 190
метров» вышла формой в 17 километров, чанк видел поле постоянным, и мир получился пустым — нашлось
только по диапазонам полей в отчёте, потому что по нулю вершин «пусто» не отличить от «здесь нет
поверхности». Отложенный чанк должен ЖДАТЬ места в арене, а не возвращаться в очередь: возврат дал
молотилку на 717 пересчётов вместо 324 чанков. И камера начинала внутри горы, потому что рельеф
доходит до 1.35 амплитуды.

**Мир во все стороны и координаты относительно камеры (2026-09-03).** Окно чанков стало КУБОМ вокруг
наблюдателя (радиусы по трём осям вместо абсолютных границ по вертикали: прежняя форма означала «мир
плоский, и у него есть верх»), а выше уровня земли появились воздушные острова — редкий выброс шума с
воротами по высоте и спадом, собранный НАЛОЖЕНИЕМ, а не суммой (с суммой остров тем толще, чем ниже
висит, и на уровне земли превращается во второй слой рельефа).

Второе крупнее и важнее: мировое место теперь это ЦЕЛЫЙ КЛЮЧ ЧАНКА ПЛЮС СМЕЩЕНИЕ ВНУТРИ НЕГО, и
больших мировых координат нет ни в вершине, ни в шейдере, ни в камере. Вершина — двенадцать байт: три
`uint16` фиксированной точки внутри своего чанка (шаг полмиллиметра), слот чанка и три байта нормали;
где этот чанк относительно камеры, говорит таблица смещений на 4096 слотов, то есть 64 КиБ, и она
пишется целиком каждый кадр. Отсюда главное: уход камеры из чанка стоит 64 килобайт записи вместо 72
мегабайт арены, точность кадра не зависит от удаления, а вершина заодно уменьшилась на четверть.

И три находки того же дня. СЛОТ ЧАНКА НЕЛЬЗЯ ВОЗВРАЩАТЬ В ОБОРОТ РАНЬШЕ ЕГО БАЙТОВ: пока арена
держала байты выгруженного чанка «чтобы не писать в то, что читает устройство», а слот отдавала сразу,
старые треугольники уезжали в ЧУЖОЕ место мира на кадр-два — правильный порядок обратный, обнулять
сразу (вырожденный треугольник не рисуется), а откладывать только переиспользование места. ПЛАВАЮЩЕЕ
НАЧАЛО КООРДИНАТ ЛЕЧИТ РАЗРЕШЕНИЕ, А НЕ НАКОПЛЕНИЕ: измерено на 370 км полёта — наивный `float32`
уезжает на `2783.78` м, оконный на `0.36` м, но именно в нуль он не уходит, потому что складывается
всё равно во `float`; обещание схемы — постоянное разрешение (`3.8` мкм против `3` см), и проверка
теперь утверждает это, а не отсутствие сноса. У ПОЛЯ ПРЕДЕЛ СВОЙ, И ОН БЛИЖЕ: позиции узлов уходят в
шум как `float32`, поэтому до `10^7` метров решётка различима, а на `10^8` слипаются 88% соседних
узлов — с `--start=1000000:2:-500000` отрисовка идеальна, а острова стали кубами. Рабочий радиус мира
объявлен числом, и лечится он только другой арифметикой внутри шума.

**Единый метр и два бага стриминга (2026-09-03).** Размер формы шума теперь задаётся В МИРОВЫХ
ЕДИНИЦАХ (`feature`), а масштаб дерева `originator` ИЗМЕРЯЕТ сам (наклонная линия, зерно ноль — период
обязан быть свойством дерева, а не мира; кэш по тексту дерева). Правило из ошибки с метрами оказалось
не «умножать на 91», а «не предполагать масштаб чужих данных», поэтому переводной множитель ушёл из
конфига в движок, и в конфиге площадки не осталось ни одного. Заодно в README библиотеки записано, что
именно несёт длину у остальных инструментов: `radius` у размытий — это ШАГИ РЕШЁТКИ, а не метры.

Два бага стриминга с ОДНИМ симптомом («чанк не появляется, пока не улетишь и не вернёшься»), оба в
очереди, а не в генераторе. ПОТЕРЯННАЯ ОЧЕРЕДЬ: `set_window` пересобирал очередь и добавлял только те
чанки, которых ещё нет в таблице состояний, — а чанк, ждавший своей очереди в прошлом окне, в таблице
уже был, и оставался «в очереди» ровно нигде. НЕПРОСНУВШИЙСЯ ПОТОК: возврат чанка в очередь не будил
спящие потоки, и он лежал незамеченным до следующей смены окна. Первый закреплён проверкой, которая с
восстановленным багом падает: окно сдвигается трижды, пока очередь полна, и все чанки финального окна
обязаны прийти.

**Накопление ошибки — вторая болезнь, и она вылечена (2026-09-03).** Плавающее начало координат лечит
РАЗРЕШЕНИЕ (что число способно выразить), а НАКОПЛЕНИЕ (сумма миллиона округлений) от начала координат
не зависит вовсе — оно зависит от ШИРИНЫ НАКОПИТЕЛЯ. Измерено на 370 км пути: мировая позиция во
`float32` уезжает на `2783.78` м, ключ + смещение во `float32` — на `0.364759` м, ключ + смещение в
`double` — на `2.9e-10` м, а ключ + смещение в ФИКСИРОВАННОЙ ТОЧКЕ (1/65536 м) — РОВНО НА НОЛЬ.

Последнее и есть ответ до конца: ноль там по построению, потому что целое сложение не округляет, а
единственная цена — однократное квантование шага (`4.9e-6` м), одинаковое на всех машинах и не
растущее со временем. Отсюда разделение по назначению: камера это представление, ей всё равно нужен
`float` для матрицы вида, поэтому `double` в накопителе стоит двенадцать байт и закрывает вопрос; а
позиции СУЩНОСТЕЙ, когда они появятся в симуляции, обязаны быть «ключ + фиксированная точка», потому
что там нужен не малый снос, а его отсутствие и побитовое равенство на разных машинах — тот же вывод,
по которому проект уже выбрал фиксированную точку языком симуляции, и та же запись, в которой уже
живут вершины этой площадки. `free_camera` в общей оболочке получила раздельные `look`/`displacement`:
накопитель принадлежит потребителю.

**Детерминизм: граница объявлена (2026-09-03).** СОДЕРЖИМОЕ чанка детерминировано полностью (четыре
проверки: порядок, потоки, обнуление буферов, второй пайплайн), и отпечаток двенадцати эталонных
чанков печатается строкой — измерено, что Debug и Release дают его ПОБИТОВО одинаковым, то есть ни
FMA-свёртка, ни переассоциация ничего не сдвинули. МОМЕНТ ПОЯВЛЕНИЯ чанка не детерминирован, и это
объявленное свойство: сетка — представление поля, а не состояние мира, поэтому проверять надо «пришли
ли все чанки окна», а не «в каком кадре». Граница сдвинется, когда поверхность станет коллизией или
навигацией: тогда её придётся считать в фиксированной точке от начала до конца, и целочисленная
геометрия вершины (позиции фиксированной точкой, нормали байтами) — половина этого пути.

А вопрос «стоит ли вообще париться про разную float-арифметику на разных платформах» получил ЧИСЛОВОЙ
ответ. Расхождение превращается в другую геометрию только через решения, и у marching cubes их два:
знак узла (выбирает топологию) и доля вдоль ребра (двигает вершину, но вершина всё равно уезжает в
фиксированную точку с шагом 0.5 мм, поэтому разница меньше кванта исчезает). Измерено на 257250
узлах: в полосе `1e-7` от порога (масштаб расхождения наборов SIMD) — НИ ОДНОГО узла, в полосе `1e-5`
— ни одного, в полосе `1e-3` (заведомо больше любой арифметики) — три, то есть один перевёрнутый узел
на два чанка, и он меняет геометрию не более восьми клеток вокруг себя. Отсюда правило шире площадки:
расхождение float опасно ровно там, где решение его УСИЛИВАЕТ — у GN02 таким решением был уровень моря
бисекцией под долю суши (последний бит → другой порог → другой набор клеток суши → другая планета), а у
GN03 решения локальные, и усиления нет.

**Сущности: ключ чанка плюс смещение (2026-09-03).** Первые сущности площадки — вехи с местом,
наклоном и родом, и механизм у них тот же, что у геометрии: позиция это целый ключ чанка плюс смещение
(абсолютной нет нигде), чанк ВЛАДЕЕТ своими сущностями (выгрузили чанк — выгрузили и их, отдельного
учёта мировых объектов не понадобилось), а что в чанке стоит — третий шаг генератора, то есть
`f(ключ, зерно)`, как и поле. Длина выхода снова переменная, и механизм снова тот же: объявленная
ёмкость плюс счётчик.

Здесь наконец пригодилось ВТОРОЕ зерно контракта GN01: поле обязано быть непрерывным через шов
(`step.seed`), а разброс сущностей — независимым в каждом чанке (`step.chunk_seed`), и до объёма ни
один потребитель не использовал оба. Ставятся вехи сорока попытками на чанк, столбец выбирается ХЕШЕМ
(сетка дала бы регулярность на швах), в столбце ищутся ПОЛЫ — переходов может быть несколько, потому
что пол пещеры это тоже пол, и именно этим объём отличается от карты высот. Всё остальное решает поле:
высота — линейная доля перехода (та же, что у marching cubes, поэтому веха стоит НА поверхности),
наклон — минус градиент, стена полом не считается, а род выбирается наличием СВОДА над головой (столб
на площадке, валун на склоне, светящийся кристалл под сводом). Сущность не расставлена по миру, а
выведена из него.

Рисуются они экземплярами, и буфер переписывается ЦЕЛИКОМ каждый кадр — в отличие от вершин, которые
живут в арене. Разница не в принципе, а в количестве: вершин миллионы, сущностей десяток на чанк
(измерено: 1072 в окне над землёй, 2631 под землёй), полмегабайта на кадр — столько же пишет оверлей,
а вторая арена со слотами и отложенным освобождением обошлась бы дороже во всём. Проверок семь, и они
про мир: воспроизводимость теми же тремя способами, «стоит ровно там, где поле проходит порог», «лежит
внутри своего чанка», «не стоит на склоне круче предела», ёмкость против самого населённого чанка.

**Память мира: выводимое плюс отличие (2026-09-03).** Пока сущность выводима, она бесплатна: выгрузили
чанк — освободили, вернулись — посчитали заново. Память начинается там, где мир перестал быть функцией,
и хранится не мир, а ОТЛИЧИЕ: `мир = выводимое + delta`. Идентичность сущности — (ключ чанка, НОМЕР
ПОПЫТКИ генератора), а не место в выходном массиве: место зависит от того, сколько попыток до неё
отказалось, поэтому подкрутка порога сделала бы память об одной сущности памятью о другой. Склад
разрежен (растёт с числом тронутых, а не существующих: 760 записей = 30416 байт, запись 40 байт), он же
и есть файл сохранения (порядок фиксирован сортировкой, поэтому два сохранения сравнимы побайтово), а
соединение выводимого со складом — ФУНКЦИЯ, и это проверено тем самым сценарием: чанк, посчитанный
заново после других чанков, даёт тот же мир.

Главная находка здесь — КРИТЕРИЙ того, что попадает в сохранение: «МИР ОТЛИЧАЕТСЯ», а не «что-то
происходило». Первая версия учитывала счётчик касаний, поэтому снятая пометка оставляла запись
навсегда: игрок, потрогавший и вернувший как было тысячу вех, платил тысячей записей. Величина, от
которой мир не зависит, — статистика, а не отличие; как только от неё что-то начнёт зависеть, она
станет отличием и войдёт в условие сама. Отличие, которому в мире ничего не соответствует (мир
изменился под сохранением), не выбрасывается, а СЧИТАЕТСЯ: сущность может вернуться, но «половина
памяти больше ни на что не ссылается» обязано быть видно числом.

Сознательно НЕ сделано: сущности, которых в выводимом мире не было вовсе (поставленные игроком) — им
нужна собственная идентичность, не привязанная к генератору, то есть РЕЕСТР, а не отличие. Это же
граница для следующих уровней: лагерь, приобретающий разум при приближении, фоновая симуляция фракций,
обретающая физические очертания рядом с игроком, и поезд на частично представленной железной дороге —
все три сводятся к паре «авторитетное представление + выведенное из него», и разбор их лежит в README
площадки.

**Два масштаба сошлись: каркас и мета чанка (2026-09-03).** Библиотека объявляет их с GN01 («грубый
мировой проход, один раз, и мелкий чанковый, по требованию»), но до этого среза они не встречались.
Каркас — ОТДЕЛЬНЫЙ генератор (`generator/skeleton`): геймплейные узлы решёткой с дрожанием, обход
ближайшего соседа, Катмулл-Ром и распрямление в ЛОМАНУЮ; считается один раз (`1.2` мс), покрывает
`4096` м против трёхсот метров видимого окна и лежит пакетом на диске.

Главный вопрос стыка — как чанк получает свою часть каркаса, и ответ: НЕ КАРКАС, А ЗАПРОС ПО ОБЛАСТИ,
результат которого приезжает обычным буфером с объявленной ёмкостью. Три правила из этого: запрос
обязан быть ПОЛНЫМ (иначе тот же ключ даёт разный мир в зависимости от истории загрузки — неполная
мета это не «чуть хуже», это другой мир, поэтому индекс проверяется против полного перебора); поле
запроса ВЫВОДИТСЯ из радиуса влияния, который объявляет сам каркас (отрезок, проходящий рядом с чанком,
гнёт поле внутри него); переполнение ёмкости — ОТКАЗ, а не обрезка (обрезанный маршрут даёт коридор,
кончающийся в середине горы). Измерено: маршрут попадает в 7 из 147 опрошенных чанков, самому густому
нужно 3 точки из объявленных 96.

В ДВИЖКЕ от этого появилось два предмета. `polyline_distance` (gather, точки плюс CSR цепочек,
отсечение по прямоугольнику, проекция с зажимом в концы) — та величина, которой не хватало, чтобы
превратить маршрут в поле; кривых движок не знает намеренно, они распрямляются в ломаную на грубом
масштабе, и густота распрямления и есть гладкость. И `pipeline_description::inputs` — ВХОДЫ ПАЙПЛАЙНА:
буфер меты заполняет ХОСТ, значит шага, который его пишет, нет и быть не должно, а правило «читать
раньше первой записи нельзя» без объявления входа отклонило бы весь пайплайн. Объявляет вход автор, а
не библиотека выводит: отличить «привезли извне» от «опечатался в имени» можно только по объявлению.

Коридор режется НАЛОЖЕНИЕМ МИНИМУМА, а не вычитанием (внутри трубы поле обязано стать отрицательным
независимо от того, сколько там породы, а снаружи не тронуть её вовсе), и режется ПОСЛЕДНИМ: пока он
стоял до островов, остров, попавший на маршрут, честно наполнял тоннель обратно. Проверяется главное
свойство стыка: у двух соседних чанков МЕТА РАЗНАЯ, а поле на общей грани совпадает точно.

**Биомы: смешиваются ПРАВИЛА (2026-09-03).** Биом — набор чисел (амплитуды, градиент, пещеры, оттенок)
плюс место в климатической плоскости; правило одно на все биомы, а плотность считается по правилу
каждого ПРИСУТСТВУЮЩЕГО в чанке биома и складывается со своим весом. Пять биомов: плато, горы, карст
(мир становится сетью ходов), степь, бэдленды.

Два решения делают это работоспособным. ВЕС С КОМПАКТНЫМ НОСИТЕЛЕМ — `(1-r²/reach²)²` обращается в
РОВНО НОЛЬ за радиусом, а не «почти ноль», как экспонента, и только поэтому «считать лишь
присутствующие биомы» это ТОЧНОЕ равенство: проверено побитово против расчёта всех пяти. С экспонентой
пришлось бы выбирать порог «пренебрежимо мало», и мир зависел бы от того, где он проведён. ЦЕНА — ЧИСЛО
БИОМОВ В ЧАНКЕ, А НЕ В МИРЕ: присутствие определяется диапазоном климата в чанке (две свёртки),
измерено 2.5 биома на чанк из пяти, чанк стоит 15.9 мс с отбрасыванием против 21.9 мс без него.

Слои шума считаются ОДИН раз на все биомы, и это про цену: размер формы входит в частоту, поэтому биом
с другим РАЗМЕРОМ потребовал бы пересчитать шум на биом, а другая амплитуда стоит одно умножение.
Нормировка потребовала от движка инструмента `ratio` с ОБЯЗАТЕЛЬНЫМ минимальным знаменателем: нулевая
сумма весов это «ни одно правило не действует», а молчаливый ноль плотности стал бы ПОВЕРХНОСТЬЮ, то
есть стеной в дырке покрытия. Цвет приходит от генератора (оттенок накапливается тем же весом, едет в
четвёртом байте вершины, шейдер разворачивает его в ленту) — считать биом в шейдере значило бы завести
вторую копию правила, которая однажды разъедется с первой.

**Тоннели: стиль — это ГЕОМЕТРИЯ, а не коэффициент (2026-09-03).** Маршрут размечен стилями, и стиль —
свойство ЦЕПОЧКИ, а не точки (меняется на узлах, иначе сечение перескакивало бы посреди хода);
выбирается он на звено, а подряд идущие звенья одного стиля становятся одной цепочкой, поэтому в мире
получаются участки, а не чередование через шаг. Естественная пещера — круглое сечение (евклидова
метрика) со стенами, разбитыми слоем деталей, и ход по Катмулл-Рому; тоннель бункера — угловатое
сечение (метрика Чебышёва, поверхность уровня куб), ровные стены и прямые отрезки с поворотом в узле.
Отсюда два ВЫЗОВА с разными метриками вместо одного с коэффициентом, и две пары буферов меты вместо
одной с полем «стиль»: инструмент расстояния считает по одному набору цепочек с одной метрикой, а
подмножество цепочек ему не задать — разделяет их хост при заполнении входа.

**Оптимизация сцены: цена кадра — это ДИАПАЗОН ОТРИСОВКИ, а не то, что видно (2026-09-04).** Вопрос
пришёл с проверки глазами («на ускорении кадры просаживаются»), поэтому в площадке появился ЗАПИСАННЫЙ
полёт и отчёт по фазам кадра плюс пассы устройства через `gpu_timestamp_profiler`.

Первое правило замера: МЕРИТЬ НАДО БЕЗ ТЕМПА. Один и тот же кадр с одной и той же геометрией стоит
5.1 мс на полном ходу и 10.6 мс под темпом в шестьдесят кадров — у встроенного видеоядра 633 МГц из
1250, и в размеренном цикле оно не разгоняется. Замер под темпом мерит управление питанием.

Пасс сцены пропорционален вершинам В ДИАПАЗОНЕ ОТРИСОВКИ (1.33/2.80/4.83 млн → 1.81/2.99/4.21 мс,
предельно около 0.65 нс на вершину), а разложение по разрешению (3.69/2.55/2.16 мс на 1280x720 /
640x360 / 320x180) делит это на ~2.1 мс потока вершин и ~1.5 мс фрагментов. ОТСЕЧЕНИЕ ПО ПИРАМИДЕ
ВИДИМОСТИ НЕ ДАЁТ НИЧЕГО: из окна видно 29-30% чанков, а пасс не меняется (4.65 против 4.74 мс), потому
что треугольник за экраном и так не даёт фрагментов, а поток вершин читается целиком — вершина узнаёт
свой слот только из своих байтов. Оставлено ключом `--cull` ради повторяемости замера, выключено по
умолчанию. НАЗВАН пробел движка: невидимый чанк станет бесплатным только при МНОГОКРАТНОМ косвенном
вызове (рисовать по чанку на строку), а у painter `draw_indirect` зашит `drawCount = 1`.

Рывок при движении был другим и он вылечен: шаг окна в сторону выбрасывает 45 чанков сразу (вверх 81),
и выгрузка обнуляла отрезок арены целиком — измерено 36.6 из 78.8 млн залитых вершин (ПОЛОВИНА заливки
была нулями), худший кадр 9.66 МиБ, фазы выгрузки и заливки 5.25 и 5.13 мс поверх кадра в 6.6 мс.
Теперь СМЕРТЬ ЧАНКА — ЭТО СТРОКА ТАБЛИЦЫ СМЕЩЕНИЙ (шейдер схлопывает вершину мёртвой строки в точку),
выгрузка стоит ноль байтов арены, а обнуление осталось только затем, чтобы вернуть слот и место, и
платится по бюджету на кадр (65536 вершин = 768 КиБ): худший кадр везёт 2.3-2.9 МиБ вместо 9.66. И
главное число для владельца: у земли с окном по умолчанию кадр под темпом стоит 15.4 мс СТОЯ НА МЕСТЕ
(из них 10.0 мс пасс сцены, 1.0 мс оверлей и 0.16 мс ВСЯ работа стриминга) — то есть просадка при
движении это цена окна, к которой движение добавляет проценты.

*Закрывающий аудит GN03 (2026-09-04).* Восемь пунктов, шесть настоящих дефектов, и лучший — про то
самое, чем площадка занимается: ПОВОРОТ ВЕХИ считался в шейдере хешем от её позиции, а позиция в кадре
задана ОТНОСИТЕЛЬНО ЧАНКА КАМЕРЫ — вехи проворачивались на месте при каждом переходе наблюдателя в
соседний чанк. Правило: всё выводимое у сущности выводится из её ИМЕНИ (ключ чанка плюс номер попытки,
то самое, по которому мир её помнит), а не из чисел кадра. Дальше: столбцы вех выбирались из узлов
`2..cells-1`, поэтому от дальней границы чанка они отступали на две клетки, а от ближней на одну — вдоль
каждого шва шла полоса без вех (проверка мерит доли вех у обеих границ: было 103 против 0, стало 94
против 83). Время поверхности набиралось через `+=` в переиспользуемом теле, а выброшенный окном чанк
тело не сбрасывал — «стоимость чанка» врала тем сильнее, чем быстрее двигается окно. Пакет каркаса
читался БЕЗ проверок инвариантов CSR (они стояли только на сборке), и испорченное смещение вело индекс
за конец массива точек. В движке два места, где объявленное расходилось с сделанным: у
`polyline_distance` параметр `max_distance` читался дважды с РАЗНЫМИ значениями по умолчанию (0 в
подготовке, 1e9 в теле — вызов без параметра давал поле с разрывом), а у `ratio` минимальный
знаменатель был объявлен обязательным, но имел значение по умолчанию, то есть движок сам решал, какая
сумма весов нулевая; оба параметра теперь обязательны. И две тихие обрезки там, где вся площадка
отказывается вслух: переполнение буфера вех обрывало цикл молча (ёмкость 128 не покрывала объявленный
диапазон 200), а «сумма весов биомов не бывает нулевой» было свойством таблицы, которую правит автор
конфига. Плюс закреплена проверками дисциплина слотов арены — то, что однажды уже ломалось.

Ближайшие кандидаты после неё — потоковая пещерная генерация для `submarine_coop` (граф маршрутов
грубым проходом, кишка чанковым: половина механизма теперь есть) и чтение пакета GN02 площадкой
`PF10`; обе требуют решений уровня проекта, поэтому берутся вместе с проектом, а не раньше него.

[`GN01_generator_contract`](subprojects/playgrounds/GN01_generator_contract/README.md) закрыл первый вертикальный срез
2026-08-31: пайплайн описан в `tavl`, тела шагов — lua, параллельное исполнение совпадает с
последовательным побайтово при 1/3/7 потоках, а граница уровней измерена на `4 194 304` элементах —
нативное ядро `3.35` нс/элемент, `devils_script` `51.79`, поэлементный lua `106.18`, причём у
последнего параллельного пути нет вовсе. Отсюда правило: lua обходит только те множества, которые
сама перечислила. Подключены FastNoise2 (дерево узлов = закодированная строка в конфиге) и jc_voronoi
(соседство областей из Делоне и контуры как планарную сетку с общими вершинами), а оба инструмента
`scatter` (`group_by`, `accumulate`) дают побитово одинаковый результат при любом числе потоков.
Отдельно замерено чанкование: pointwise переживает его точно, gather расходится строго в полосе
шириной radius, а самокалибровка по измеренному диапазону с чанкованием несовместима. Фоновый поток
принадлежит потребителю, а не движку.

`PF01`–`PF08` закрыты. PF07 зафиксировал P-type систему, календарь, атмосферу, экспозицию/colour script,
тени двух светил, proxy-долину и инстансные заросли; PF08 независимо наложила на эту сцену единый weather-state,
высотный туман, конечные 3D-облака, near/mid/far дождь и снег, видимое укрытие, дешёвую world-space память,
радугу и снежные блики, универсальную молнию и planet-anchored aurora shell. Её headless контракт — `117/117`.
Восемь постоянных closing-audit кадров покрывают clear в трёх временах суток, overcast, rain, snow, lightning
и aurora; повторный PF08-only прогон совпадает с ними побитно. Пять активных Vulkan-validation путей чисты,
а худший зафиксированный Iris Xe кадр при 1280x720 занимает `10.038 ms`. PF07 при этом не переснимается:
старый baseline использует его сохранённые PNG, а новая PF08-галерея имеет собственные frozen frames.
Обе project-look сцены фиксируют только нужное им подмножество
gallery-возможностей в собственных resources/presets. Исходники и CMake targets лабораторий
не зависят друг от друга.

Параллельно открыта [`PF09_territory_zoning`](subprojects/playgrounds/PF09_territory_zoning/README.md) —
каркас территорий для `medieval_hero_manager`. Площадка начиналась с единого иерархического разбиения
плоскости и растра по нему; эта постановка ЗАКРЫТА и перестроена, потому что игре нужно оказалось другое.
Несущая конструкция теперь такая: **зона — это МЕСТО из выпуклых частей, а проход — ЗАПИСЬ В ФАЙЛЕ**;
всё это лежит в секторных файлах и подгружается с диска по мере движения игрока. Общее ребро — лишь один
из способов эту запись получить, и работает он ровно один раз, в сборщике: совпадение рёбер ненадёжно как
источник связности, а вычисляемая на лету связность начинает мигать на округлении. Что связность обязана
быть данными, доказывают два случая, и оба есть в фикстуре: связь БЕЗ ребра (лестница на второй этаж,
дорога между поселениями) и ребро БЕЗ связи (верхний зал лежит в плане ровно над нижним, «общее ребро»
идеальное, а между ними перекрытие). Отрезок в портале хранится затем, чтобы по нему можно было
прицелиться, как в navmesh.

Дверь при этом — не особый вид связи, а МЕСТО с переключаемой проходимостью: у двери четыре ребра, и
запертость на ребре пришлось бы держать согласованной на всех четырёх, а у места она одна. Состояние
переживает выгрузку сектора, и маршрут меняется со следующего же поиска. Здание — не фигура, а абстрактный
узел-группа, и вопрос «здание и комната накладываются» исчез вместе с его формой.

Отдельный вывод про координаты: зонируется НЕ планета, а окрестность партии — дальние города симулируются
фоном и зон не имеют вовсе. Область сборки переехала к началу координат, где шаг `float` равен четырём
миллиметрам вместо трёх сантиметров, и целый класс ошибок точности, стоивший площадке трёх разборов
подряд, исчез вместе с источником: щели округления задевают ноль точек выборки из `4096` против одной.

Три правила модели: зоны НЕ замощают пространство (пропуск между ними — законный ответ, а не дефект);
уровни НЕ образуют дерева (у каждого своя карта взаимодействий, ссылка вверх справочная); связность — это
и есть содержание.

Внутри мест появились ПРЕДМЕТЫ — стулья, столы, бочки, камни, — и они ломают то, на чём держалась вся
модель движения: «часть выпукла, значит внутри неё можно идти по прямой к проёму». Ответ — НЕ делать
предмет зоной: зонами предметы превратили бы комнату в лоскутное одеяло, а связность — в граф, который
надо пересобирать всякий раз, когда подвинули стул. Часть остаётся единицей связности, маршрут о мебели
не знает вовсе, а обход предмета — местная задача шага. Что это работает, проверяется не отсутствием
ошибок, а тем, что те же `64` маршрута всё ещё проходятся целиком при `17 760` предметах на пути.

На предметах стоят ТАКТИЧЕСКИЕ ЗАПРОСЫ, ради которых зонирование и затевалось: где спрятаться, откуда
виден вход, куда развести группу. Все три — на одном примитиве, видимости, и границей видимости служит
само место: вышел за его пределы — значит между точками стена, потому что покрытие полное и снаружи стоит
соседнее место. Отдельный список стен не понадобился, и вот это прямой выигрыш от полного замощения.
Укрытие ПРОВЕРЯЕТСЯ, а не выводится, и его авторство честное: если подход к предмету со стороны угрозы
тоже не просматривается, прячет форма места, а не предмет, — иначе игра сожгла бы ящик и удивилась, что
укрытие осталось. Приказ игрока «держим этот дом» разворачивается в разные задачи каждому: `fan_out`.

Над всем этим появился КОНТРОЛЬ, и его главное решение: **ответ несёт ровно один уровень, и не тот, на
котором спрашивают.** У комнаты нет своего уровня преступности — он есть у района, и комната его наследует;
у района нет своей торговли — она есть у поселения. Запрос это подъём по вложенности до носителя, а не поле
в каждой записи: держать преступность у каждой комнаты значило бы завести десять тысяч чисел, обязанных
меняться вместе. Отсюда прямо следует то, ради чего иерархия и заводилась: **уровни ВПРАВЕ расходиться** —
район держит одна сила, город другая, и в этом расхождении живёт игра (`13` районов из `44` в фикстуре).
Навигация это учитывает ценой, а не запретом: запрет означал бы «пути нет», когда единственная дорога идёт
через чужой квартал, — а идти туда бывает надо, просто дорого.

Над контролем встало ПРАВО, устроенное как система титулов CK. Титулы — отдельная от зон структура, и
разделение несущее: у зоны есть пространственная вложенность («где это»), у земли — юридическая
принадлежность («чьё это»), и совпадать они не обязаны — дом стоит на улице, но принадлежит не улице.
Обойтись одной иерархией значило бы сделать «переехал» и «сменил хозяина» одним событием. **Титулы не
стримятся**: земля подгружается, а «кто правит этим городом» обязано отвечаться всегда, иначе право
собственности зависело бы от того, где стоит партия.

У титула есть де-юре родитель (карта права) и де-факто держатель (карта силы). Держатель признаёт власть
уровня выше, если законен сам; узурпатор — нет, и на нём цепочка признаний обрывается: в законопослушном
квартале действует закон державы, в занятом — его собственный, а **занятый дом посреди законопослушного
квартала оказывается местом без закона вовсе** (собственность законов не издаёт). Частную территорию
открывает ДЕ-ФАКТО держатель, а не законный владелец: дом, занятый революционером, закрыт и для хозяина,
причём право хозяина никуда не девается. Навигация уважает это ценой, а не запретом.

Улица заодно нарезана на полосы: мостовая посередине, обочины по краям, разница выражена СКОРОСТЬЮ, а не
флагом «дорога». Полосы кладутся параллельно улице — иначе дверь дома выходила бы на проезжую часть.

Отрисовка доведена до партийной РПГ: наклонная камера, этажи с переключением (`Z`/`X`), срез переднего
плана расширяющимся к камере клином (`C`), маршруты по серединам проёмов из ТОГО ЖЕ пути, по которому
персонаж шагает (`V`), и мировой интерфейс над персонажами — якорь в мире, раскладка в пикселях (`N`).

Померено: `6x6` секторов по `8192 м` дают `12 009` зон, `155 248` проходов и `8.0` МБ на диске, то есть
весь мир при той же плотности — `3.4` ГБ и `5` млн зон, и это оценка сверху. `696` дверей (`93` заперты в
файле), `117` лестниц, `234` зоны выше первого этажа, `466` рёбер графа без геометрии. Переключение двери
изменило маршрут в `48` случаях из `48`, и ни один маршрут не прошёл сквозь закрытое место. `17 760`
предметов; из `2 609` найденных укрытий `2 381` даёт предмет и `228` — форма места. При весе преступности
`6` средняя преступность маршрута падает с `482` до `394`: тише у `38` пар из `96`, хуже ни у одной.
`1 591` титул на область; `2 055` мест под законом державы и `859` под законом своего квартала. Мостовая
берёт `55%` шагов при трети площади улицы. Законопослушный проходит `19` чужих шагов против `27` у
безразличного. Движение: `64` маршрута между комнатами, `46 000` шагов, персонаж всё время внутри своей
зоны и ни разу внутри предмета. `140` численных проверок на девяти сидах.

Дефекты, которые нашлись только проверками: остов для замков строился по всем рёбрам, включая стены (стена
давала мнимую связность, и настоящая дверь запиралась как лишняя, отрезая кусок города); рёбра выводились
между зонами РАЗНЫХ уровней (персонаж мог «войти в поселение» как в комнату); рёбра графа у зоны без формы
молча терялись, и весь политический уровень уезжал на диск набором изолированных точек; здание разъезжалось
по секторам, потому что сектор выводился из центра габарита, а у зала, лестницы и стен центры разные. И
отдельный урок про сами проверки, полученный трижды: **проверка, которая не может провалиться, хуже
отсутствующей** — угроза в проверке укрытий стояла СНАРУЖИ места и фильтр «не просматривается» пропускал
всё; расхождение уровней контроля насчиталось у всех `44` районов, потому что у одного из уровней потерялся
носитель и он отвечал нулём; а когда образец не находился, шесть утверждений молча не выполнялись, и
единственным следом было «123 проверки вместо 129». Отдельно записан и класс ошибок времени жизни:
`zone_record*` смотрит внутрь резидентного сектора и после `focus` становится висячим — через границу
подгрузки носят КЛЮЧИ, а не указатели. От
прежней постановки в ядро переехала разрежённая локальность; клипмап идентичности из несущей конструкции
выпал.

**Ревью на закрытии** записано в README площадки и закончилось уборкой. Несущими оказались четыре
решения, но переезжать в движок должно только то, что шаблонизируется без выдумывания: **правило и
библиотека — разные вещи.** Переехало одно — «ответ несёт ровно один уровень» стало
`utils::nearest_carrier`; плюс то, чего в списке не было: **таблица рантайм-подмен была написана в
площадке ЧЕТЫРЕ раза** (двери, контроль, занятые места, титулы) и стала `utils::override_table`.
«Связность — данные» и «избегание — цена» остались правилами: обобщать там нечего, кроме графа и функтора
стоимости. Дерево титулов с де-юре/де-факто — игровая механика, кандидат в отдельную библиотеку, а не в
`utils`.

Выкинуто: клипмап (`1 196` строк, `19` проверок и `3.49 с` из `7.24 с` времени `--verify`) вместе с
`resolve_single`, существовавшим ровно для GPU-запекания; мёртвые значения формата; две тавтологичные
проверки. Итог уборки: **`9 043` строки вместо `10 239`, `--verify` за `3.5 с` вместо `7.2 с`.** Поиск
пути отдан общему `devils_engine::astar` с нулевой эвристикой — стоимость шага здесь не расстояние, и
завышенная оценка снизу сделала бы A* просто неправильным. Появился первый замер времени: `0.26` мс и
`376` развёрнутых узлов на маршрут; он же показывает границу, за которой линейный перебор открытого и
закрытого списков внутри движкового A* станет квадратичным. Остаётся долгом линейный `zone_store::sector()`
и отсутствие проверок производительности стриминга — сознательно оставлено на другой раз.

### Текущая PF10: functional planet

[`PF10_functional_planet`](subprojects/playgrounds/PF10_functional_planet/README.md) строит функциональную
планету, а не затенённый гладкий шар. Канонический адрес поверхности — единичное направление `d` в локальной
системе глобуса; вершина лежит в `p=d*(R+h(d))`, поэтому высота меняет геометрию, depth и силуэт и вращается
вместе с планетой. Bump/normal map без displacement этот контракт не закрывает.

То же направление независимо отображается в стабильный `province_id`. Политический слой получает границы,
соседство, hover и закреплённый selection, но не становится источником формы рельефа. Первый fixture — один
вращающийся глобус с нарочито читаемой высотой и несколькими десятками spherical Voronoi provinces без
longitude seam и особой логики полюсов. PF09 остаётся источником доказанных идей идентичности и interaction,
но его плоские sector polygons не становятся зависимостью или геометрией PF10.

Первое отображение уже запускается: cube-sphere `6x256x256` даёт `786 432` displaced-треугольника, а
плотный политический bake — `4072` land-провинции, четыре крупные water region и две polar region.
Материализованный CSR-граф имеет `12 895` undirected edges, mean degree `6.33`, одну land-компоненту и
никаких isolated nodes. Границы меняют цвет, camera ray выбирает displaced surface, 24 anchors показывают
city/wonder/construction. MSDF-текст теперь является depth-reconstructed planet-space decal: дальше видны
имена крупных областей, ближе — placeholder каждой провинции, с owner-ID clipping по её поверхности.
One-time surface/political bake и triangle strips снизили uncapped Iris Xe GPU frame с `15.906` до примерно
`2.2–2.5 ms` при 1280x720; полный ближний label pass стоит около `.31 ms`. `--verify` — `18/18`.
Следующий контракт — отдельный water port-to-port graph; полюса остаются non-playable.

### Parking lot: anomalous weather

Будущая `anomalous_weather` должна исследовать не ещё десять названий для дождевого preset, а общий язык
**аномальных явлений**. Она независимо берёт зафиксированную сцену и доказанные механизмы PF08, не создавая
source/CMake dependency на закрытую площадку. Главный вопрос: как одним renderer-контрактом описывать
локальное событие, погодную область, верхнеатмосферную оболочку и явление космического масштаба, сохраняя
понятный контроль изнутри и снаружи эффекта. Номер площадки будет назначен, когда эта работа вернётся в
активный фокус.

Редкая реальная сторона площадки собирает эффекты, которые PF08 сознательно оставила за своей границей:

| Семейство | Явления | Новый вопрос |
|---|---|---|
| Ледяная атмосферная оптика | `22° halo`, sundogs/parhelia, circumzenithal arc, световые столбы | ориентированное спектральное рассеяние и преломление на кристаллах; две звезды создают две пересекающиеся системы дуг |
| Обратное рассеяние и дифракция | glory, Brocken spectre, белая fogbow, corona солнца/луны, иризация облаков | observer-anchored anti-solar geometry, узкие phase peaks и спектральный размер капель |
| Незавершившиеся осадки и сильный ветер | virga, rain shafts, microburst, diamond dust, позёмка и снежные языки | высотное испарение, локальные нисходящие потоки и повторный подъём surface precipitation |
| Высокие слои атмосферы | noctilucent и nacreous clouds | разрежённая верхняя оболочка, которая рассеивает свет из-за горизонта, а не испускает его как aurora |
| Верхнеатмосферное электричество | sprites, elves и blue jets | перенос универсального lightning event из облаков на высоты десятков километров |
| Редкие формы облаков | lenticular, mammatus, shelf/roll clouds | управляемое world-space density authoring и деформация общим ветровым полем |
| Рефракционные явления | нижний/верхний мираж, Fata Morgana, heat shimmer и green flash | искривление луча градиентом показателя преломления вместо обычного Beer–Lambert march |
| Фаза осадков | град, freezing rain и прозрачная наледь | температура, столкновения и material-specific response вместо универсальной «мокрости» |

Нереальная сторона не обязана притворяться физикой. Она использует те же пространственные контракты, но
явно помечает художественное нарушение и должна позволить собирать, например:

- дождь, снег, пепел или светящиеся частицы, падающие вверх, к выбранному телу либо вдоль произвольного
  векторного поля; боковые стены дождя, спиральные осадки и фронты, остановленные в воздухе;
- локальные штормовые сферы и движущиеся погодные «существа», внутри которых другие свет, гравитация,
  направление ветра и течение времени, но граница остаётся наблюдаемой с обеих сторон;
- невозможные облака — кольца, винтовые башни, идеально плоские стены, левитирующие океаны и структуры,
  которые отбрасывают тень прежде, чем закрывают светило;
- руническое северное сияние, занавеси до самой земли, несколько магнитных полюсов, aurora вокруг лун и
  управляемые цветом/музыкой небесные поля;
- чёрное солнце, отрицательные радуги, цветные затмения, световые трещины в небе, порталы, ложные созвездия
  и геометрические «шрамы» на небесной сфере;
- магические грозы: молнии между облаками, землёй, персонажами и лунами; медленные устойчивые каналы,
  шаровые разряды, цепные дуги и гром, который приходит раньше вспышки как намеренный world rule;
- метеорные ливни, кометные хвосты, падение звёзд, планетарные кольца и их тени, stellar flares, видимые
  ударные волны и туманности, которые проходят через небо как реальная объёмная область;
- смешанные явления: дождь из метеоров внутри aurora, радуга вокруг чёрного светила, снежная буря в невесомости
  или космический фронт, превращающий обычную погоду в магическую по мере движения через мир.

Предварительные срезы после возвращения площадки:

1. **Frozen inheritance.** Выбрать минимальный PF08 baseline, собственные reference frames и нулевую стоимость
   при выключенных аномалиях; никаких изменений закрытой PF08.
2. **Ice-crystal optics.** Гало, паргелии, столбы и дуги от обоих светил с раздельными physical/art controls.
3. **Observer and refractive optics.** Glory/fogbow/corona, мираж и heat shimmer; определить, где достаточно
   angular sky evaluation, а где необходим bent-ray либо screen/depth distortion.
4. **Rare volumes.** Virga, microburst, blowing snow, high clouds и upper-atmosphere lightning как расширения
   существующих world fields и spherical shells.
5. **Anomaly grammar.** Единое описание области, системы координат, времени, vector field, emission,
   extinction и связи с celestial bodies; магический эффект собирается данными, а не новым shader на имя.
6. **Cosmic weather.** Метеоры, кометы, stellar events, рифты и другие планетарные/небесные phenomena с
   корректным масштабом, окклюзией, экспозицией и наблюдением из разных точек мира.
7. **Composition and audit.** Сочетания нескольких аномалий, переходы через их границы, GPU budgets,
   deterministic gallery и явное различие между physically based, physically inspired и impossible режимами.

Ключевая защита от превращения площадки в мешок спецэффектов: каждый срез обязан добавить либо проверить
новый пространственный/оптический механизм. Новый цвет дождя или ещё одна форма облака без нового вопроса
остаётся preset/content, а не отдельным техническим результатом.

Текущие ограниченные результаты PF05 — запускаемые Crimson MSDF и screen-space decal slices: один atlas обслуживает UI,
индивидуальные world glyph matrices на прямой/quadratic Bézier и три billboard space — spherical world-size,
cylindrical/Y-locked и constant-pixel world-anchored screen-size. Fixed font height обрезает хвост по длине,
при одной длине размер выводится из метрик, а optional detail texture стилизует fill без изменения MSDF coverage.
World/billboard glyph coverage теперь пишет depth. Настоящий decal pass растеризует ориентированные box-volume,
восстанавливает world position из opaque depth, ограничивает её через `world_to_decal`, фильтрует receiver по
scene normal и проецирует MSDF на дальнюю и боковую стены. `F`/`--no-decals` дают наблюдаемый A/B.
Третий срез добавляет persistent GPU spark partition на 2048 stable slots: compute читает `history=1`, выполняет
spawn/lifetime, semi-implicit Euler, gravity/drag и bounce от аналитических границ комнаты; procedural spherical
billboards проходят world depth и используют order-independent additive blending. `P` переводит emitter из
emitting в draining/stopped и обратно, `R` очищает pool. Fixed-step rail после stop совпадает с пустым pool
(`AE=0`) по завершении максимального lifetime.
Weather-срез расширяет общий buffer ещё на 1024 camera-local slots и переносит compute после opaque scene:
отрезок движения сравнивается с current `scene_depth`, world hit/normal восстанавливаются, sparks отражаются,
а rain/snow respawn'ятся. `T` циклически меняет быстрые rain streaks, медленные drifting snow flakes и clear.
Rain использует velocity-aligned cylindrical ribbons: мировая ось падения не зависит от camera-up, к камере
поворачивается только тонкая ширина. Явный shelter AABB закрывает semantic gap screen depth для offscreen roof;
комната стала roofed dry fixture, `H` даёт shelter A/B, а `C` — depth-collision A/B. Weather использует alpha,
sparks остаются additive, UI гарантирован отдельным последним pass.
Cel-срез добавляет runtime UBO вместо pipeline variants: `G` включает Lambert quantization, `B` меняет число
bands, а `O` выбирает screen-space outline `off/silhouette/feature`. Отдельная гладкая сфера делает уровни
наблюдаемыми; outline читает visible opaque depth/normal до decals/particles/text и поэтому не превращается в
through-wall selector. Fixed A/B различает smooth/2/5 bands и обе outline policies, повторный crop даёт `AE=0`.
World-UI срез использует отдельный native Nuklear context без Lua: bounded C++ config задаёт anchor/name/health,
до трёх status rows и image slots. Три окна проходят один `nk_convert`; command userdata становится `window_id`
в расширенной вершине, а 48-byte/window SSBO переводит локальные пиксели в world-anchor clip space. Размер следует
`reference_distance/depth` с min/max clamp и дальним fade, поэтому панель приближается вместе с объектом, не теряя
читаемость. `I` освобождает cursor, CPU hit rectangles выбирают ближайший stable id, selection слегка подсвечивает
панель и связанный scene instance. Material сохраняет reverse-Z anchor depth; hidden-behind-wall fixture совпадает
с UI-off (`AE=0`).
Лаборатории по-прежнему не зависят друг от друга; общие production fixes принадлежат `libs/painter`.

## 4. `hierarchy_sim_lab` — симуляция иерархического AI

### Вопрос

Можно ли ограниченно, детерминированно и объяснимо выполнять решения на уровнях персонажа, группы,
организации и региона, не превращая `acumen` в политическую симуляцию?

### Представление

Стенд преимущественно headless. Его UI — не игровая карта, а несколько простых views:

- граф регионов и дорог;
- список actors и groups;
- дерево goals/operations/tasks;
- timeline обязательств и interruptions;
- ownership ресурсов;
- explanation выбранного решения;
- budgets, expanded nodes, cache hits и rejected candidates.

### Минимальная модель

- 4 региона и 5–7 дорог;
- 2 фракции;
- 3 группы по несколько logical actors;
- ограниченные ресурсы: еда, деньги и influence;
- несколько операций: travel, recruit, guard, trade, investigate;
- локальные события: нехватка еды, опасная дорога, выгодная возможность;
- разные cadences для actor/group/faction decisions.

### Последовательные slices

1. Goal candidate selection с объяснимым utility score.
2. Persistent operation instance с duration/commitment/interruption.
3. Разбиение group goal на actor tasks.
4. Reservation ограниченного ресурса или дороги.
5. Multi-cadence scheduler.
6. Aggregate actors, из которых несколько materialize в detailed state.
7. Save/resume посередине операции.
8. Serial-vs-MT и 1/2/4-worker identity.
9. Batch прогон сотен seeds со статистическим отчётом.

### Ownership

- engine: workflow cursor, scheduling, budgets, reservations primitives, traces and inspectors;
- project: politics, utility factors, operation schemas, faction relations and consequences.

### Не входит

- полноценная экономика;
- дипломатический UI;
- detailed combat;
- 3D presentation;
- тысячи типов событий.

### Definition of Done первого среза

Одинаковый seed даёт одинаковый outcome после save/resume и при разном числе workers. Для каждой
операции можно ответить: кто её начал, почему, какие ресурсы заняты, какой шаг выполняется и почему она
была продолжена, отменена или прервана.

## 5. `tower_floor_lab` — квадратный этаж и небольшой tactical loop

### Вопрос

Достаточно ли project-owned grid semantics поверх общих query/resolve/workflow primitives для
детерминированного маленького этажа?

### Минимальная карта

- квадратная grid-карта 12×12 либо 16×16;
- стены, двери, опасные клетки и один exit;
- player party из двух units;
- два типа противников;
- один интерактивный объект;
- простая отдельная map presentation.

### Игровые features

- grid movement и occupancy;
- path preview;
- line of sight и простое укрытие;
- initiative/reservation;
- melee attack и один area shape;
- один status либо environmental hazard;
- enemy scorer из двух-трёх решений;
- group exit condition.

### Generator slice

Генератор создаёт не игру, а один проверяемый floor artifact:

1. room/connection graph;
2. rasterization в grid;
3. placement start/exit/objective;
4. reachability validation;
5. простой semantic quest graph из 3–5 nodes;
6. bounded repair при недостижимом exit;
7. provenance view: какой pass создал клетку/дверь/objective.

### Не входит

- campaign;
- большой набор abilities;
- inventory/equipment;
- полноценный quest narrative;
- production procedural variety.

### Definition of Done первого среза

Один seed создаёт canonical floor bytes/hash. Этаж гарантированно проходим, actor movement и combat
возобновляются после save, а visual map и tactical state читают одну grid model без дублирования координат.

## 6. `generator_contract_lab` — typed passes и Lua glue

**Стала кампанией генератора, см. выше.** Первый срез живёт как `GN01_generator_contract`; описанные
ниже pipeline'ы остаются планом следующих срезов.

### Вопрос

Можно ли собирать разные генераторы из одного host/toolkit, сохраняя typed artifacts, determinism,
provenance, validation и bounded repair?

### Первый pipeline

Намеренно абстрактная 2D region map:

1. coarse continent mask;
2. height/noise field;
3. water and moisture propagation;
4. biome classification;
5. Voronoi-like regions;
6. adjacency graph;
7. validation и один repair pass.

### Второй pipeline

Небольшой adventure graph без production terrain:

1. hierarchy задач;
2. decomposition до конечных objectives;
3. region graph;
4. content-node graph;
5. примитивные volumes/boxes вместо финальных meshes;
6. connectivity validation.

### Что проверяется

- C++ tools регистрируются как reusable building blocks;
- отдельный headless Lua environment связывает passes;
- pass видит только объявленные typed inputs;
- artifacts получают seed/version/hash;
- provenance связывает output с pass/tool/input fingerprints;
- serial и MT execution дают одинаковый canonical result;
- cache hit не меняет результат;
- invalid artifact не публикуется;
- viewer показывает fields, graphs, filters, groups и validation issues.

### Definition of Done первого среза

Lua переставляет и параметризует проходы без изменения C++. Неверная связь типов отклоняется до
execution, одинаковый seed даёт одинаковый artifact hash, а выбранная клетка/область объясняет своё
происхождение через provenance chain.

## Дополнительные playgrounds

### 7. `network_session_lab`

Маленькая статическая комната с двумя peers и dedicated server. Проверяет ENet transport, HTTPS-like
rendezvous mock, key bootstrap, encrypted UDP envelope, NAT/relay adapter seam, intents, snapshots,

### 8. `planet_streaming_lab`

Небольшая условная планета или кольцо cells без финальной графики. Camera/observer движется между cells;

cache, residency и stable package hashes. Это ранний consumer `mmo_planet_shooter`, но не MMO server.

### 9. `city_actor_lab`

Один квартал-прокси из простых blocks, несколько actors, vertical links и одна group operation. Проверяет
сложную navigation, hierarchical actor/group intent, короткий replay и scene streaming для
`bandit_in_the_shell`. Позже можно добавить skinned character, ragdoll handoff и crowd pressure, но не
в одном первом slice.

### 10. `resource_churn_lab`

Автоматически загружает, публикует, заменяет и выгружает textures, meshes, sounds, shaders и generated
artifacts. Проверяет fence/task lifetime, stable handles, artifact epochs, bindless slot reuse,
dependency invalidation и memory budgets. Визуальная часть показывает текущие slots и intentionally
missing/corrupt resources.

### 11. `localized_text_lab`

Небольшая UI-галерея с несколькими scripts/locales. Проверяет fallback, plural/select/case forms, typed
parameters, safe tags, inline icons, pseudo-localization, RTL/bidi, shaping, font fallback, wrapping,
hit spans и locale-switch invalidation. Gameplay поставляет только loc-key и typed values.

### 12. `headless_run_lab`

Универсальная оболочка автономного scenario: seed/config, fixed tick budget, statistics, failure
artifacts и comparison между builds. Первым consumer может стать простой `cardgame` player policy без
новых карт. Позже сюда подключаются generation batch runs и dedicated-server soak tests.

### 13. `audio_environment_lab`

Три соединённые комнаты с разными материалами, дверями и acoustic zones. Проверяет
`(material, action/impact, context) -> sound event`, шаги, удары, reverb/filters, obstruction, portals,
priorities и virtual voices. Может использовать ту же proxy geometry, что `PF06_submarine_light_room`, но
остаётся отдельным аудио-сценарием.

### 14. `swarm_field_lab`

Плоская карта 128×128 с 1 000 proxy creatures, двумя food areas, одной составной operation
`approach corridor → terminal area` и одной pressure front. Проверяет versioned layered fields, brush
journal, dirty recompute, group demand/allocation, flow field, congestion, hysteresis и explanation
выбранного actor. Headless и visual runs обязаны давать один canonical hash; затем количество actors
увеличивается ступенями 1k → 10k → целевой budget. В первый slice не входят production animation,
физиология улья и полноценный бой.

### 15. `commander_mission_lab`

Граф 8–12 tactical areas, четыре абстрактных бойца, укреплённый прямой путь, обход, подготовленная
оборонительная позиция, одна неизвестная угроза, дополнительная цель и deadline эвакуации. Planner
получает только immutable squad-knowledge snapshot. Scenario проверяет mission/route plan records,
evidence-backed explanation, один interrupt, partial replan, reservation cleanup, недостижимый intent и
batch no-progress/cycle detector. Сначала это headless simulation + 2D graph/timeline inspector; 3D не нужен.

### 16. `apates_campaign_bridge_lab`

Фиксированный замкнутый граф 12–20 провинций, один persistent ruler/hero, несколько knowledge holders,
одна институциональная rule chain и одно encounter. Проверяет calendar workflow, rumor/contact/mapped-route
views, truthful rule preview и lifecycle `reserve → materialize → outcome journal → atomic reconcile`.
Первая encounter execution может быть headless/discrete: важно вернуть смерть/рану/время/предмет/
witness ровно один раз. Save/resume и different-worker runs не должны менять политический outcome.

### 17. `globe_topology_lab`

Отдельный от campaign bridge стенд замкнутой поверхности. Создаёт маленький immutable world package с
surface cells/provinces, adjacency и несколькими routes. Проверяет seam/pole-safe distance, полный обход,
projection switching, ray→surface→province picking, map-mode buffers, label anchors и terra-incognita,
которая не раскрывает hidden boundaries через hover/picking. После topology proof сюда добавляются
generator provenance и culture/history layers; distributed MMO coordinates не входят в первый scope.

## Как playground растёт в срез игры

Расширение должно идти не «добавим ещё контента», а последовательными доказанными рисками:

```text
isolated engine contract
        ↓
project-specific consumer
        ↓
second consumer / generalization review
        ↓
persistence + diagnostics + failure paths
        ↓
small repeatable gameplay loop
        ↓
early game slice
```

Перед каждым расширением стоит ответить:

1. Какой новый технический вопрос появляется?
2. Нельзя ли проверить его меньшим fixture?
3. Какая часть остаётся project-owned?
4. Что после proof действительно переносится в engine?
5. Как воспроизвести failure и сравнить результат между запусками?

Если следующий шаг отвечает только «нужно больше контента», playground уже выполнил движковую задачу.
Дальнейшее развитие должно происходить в проекте либо ждать возвращения интереса к его gameplay.

## Физическая организация

Площадки каталогизируются по коду и человеческому имени. У каждой есть собственная директория и README;
наличие отдельного executable определяется её topology и независимостью эксперимента:

```text
subprojects/
  playgrounds/
    common/
    AU01_spatial_audio/
    AU02_directional_coloration/
    PF01_forward_plus/
    PF02_shadows/
    PF03_post_processing/
    PF04_stencil_effects/
    PF05_scene_effects/
    PF06_submarine_light_room/
    PF07_party_environment/
    PF08_weather_effects/
    PF09_territory_zoning/
    PF10_functional_planet/  # README-only до первого executable
    ...
```

`common` — не mega-demo и не источник feature inheritance. Он содержит только маленькую shared shell.
Отдельный executable оправдан независимым экспериментом, отличающейся thread/process topology,
renderer presence, dedicated-server режимом или набором platform dependencies.
