# originator

Каркас процедурных генераторов: типизированные буферы, шаги, объявленные в конфиге, и lua в роли
программируемой команды шага.

Библиотека не описывает мир. Она описывает, **как устроен генератор**: что течёт между шагами, кто
имеет право это писать, и почему результат воспроизводится. Конкретный мир — планета, подземелье,
объёмный чанк — принадлежит проекту.

| Сущность | Что это | Аналог в painter |
|---|---|---|
| `buffer` | плотный массив элементов с именованными полями и явной раскладкой | `resource` |
| `step` | объявленная единица работы с привязками `reads`/`writes` | `step` |
| тело шага | lua-функция, дирижирующая одним куплетом генерации | `material` |

**Цели сборки** (разделены по зависимостям, а не по темам):

| Цель | Что внутри | Зависимости |
|---|---|---|
| `originator` | буферы, инструменты, пайплайн, очередь | ничего лишнего |
| `originator_script` | программы `devils_script` над плотным буфером | `devils_script` |
| `originator_primitives` | FastNoise2 и jc_voronoi | внешние |
| `originator_lua` | скриптовый хост: свой `sol::state`, окружение, бюджет | lua, `bindings_base` |
| `originator_config` | генератор как ресурс: id точки входа -> тексты | `demiurg` |
| `originator_device` | исполнение очереди на GPU | `painter::compute_context` |

## Как этим пользоваться

Задача -> чем решается -> что получается.

**Получить поле из шума.** Объявить буфер с полем в `buffers.tavl`, в теле шага позвать
`originator.noise_grid{ outputs = {...}, params = { tree = ..., feature = ... } }`. Получается поле,
посчитанное в нативном ядре многопоточно, воспроизводимое по зерну шага.

**Написать правило, которое моддится без C++.** Положить программу `devils_script` в `.ds`, назвать
её в `programs` шага, позвать `originator.run_script{ program = "biome", inputs = {...}, outputs =
{...} }`. Правило читает поля СВОЕГО элемента по их именам из конфига и пишет одно поле; пороги
приходят из параметров шага как `ctx:arg:имя`.

**Сцепить несколько проходов в одну единицу.** Объявить их через `originator.queue.*` и отдать
`originator.queue{ ..., output = {...} }`. Получается: проверка всей цепочки до первого вызова,
слияние подряд идущих `pointwise` проходов в один обход данных и отчёт о том, что реально сделано.

**Посчитать ту же цепочку на GPU.** Добавить в очередь `device = true`. Передача, барьеры и род
ресурса выводятся из самой очереди; на хост уезжает ровно `output`.

**Считать мир по чанкам.** `pipeline::set_chunk(key)` перед прогоном шагов. Поле по мировой позиции
берёт `step.seed` (непрерывно через шов), локальный разброс — `step.chunk_seed`.

**Сделать что-то, чего инструментами не выражается.** Обойти из lua — но только множество, которое
lua сама перечислила (список областей, кандидаты, вершины графа), а не плотный буфер: 4 млн
элементов из lua это `501` мс, 4 тысячи провинций — `0.48` мс.

### Три цепочки целиком

Классификация по порогам, один шаг:

```lua
return function(step)
  local cells = step.writes.cells
  originator.noise_grid{ outputs = { cells:field("height") },
    params = { tree = step.params.tree, feature = step.params.feature } }
  originator.queue{
    originator.queue.box_blur{ inputs = { cells:field("height") },
      outputs = { cells:field("smoothed") }, params = { radius = 2 } },
    originator.queue.run_script{ program = "biome",
      inputs = { cells:field("smoothed"), cells:field("moisture") },
      outputs = { cells:field("biome") },
      params = { sea_level = step.params.sea_level } },
    output = { cells:field("smoothed"), cells:field("biome") },
  }
end
```

Выход переменной длины (поверхность из поля плотности):

```lua
originator.queue{
  originator.queue.marching_cubes{ inputs = { density, positions },
    outputs = { vertices, normals, state:field("used") } },
  originator.queue.remap{ inputs = { vertices }, outputs = { scaled },
    range = { count = state:field("used") } },   -- сколько посчитал предыдущий
  output = { scaled },
}
```

Иерархия областей по графу соседства:

```lua
originator.sphere_points{ outputs = { cells:field("position") } }
originator.sphere_adjacency{ inputs = { cells:field("position") },
  outputs = { arcs:field("offset"), arcs:field("neighbour") } }
originator.graph_flood{ inputs = { arcs..., seeds... }, outputs = { cells:field("province") } }
originator.label_adjacency{ inputs = { cells:field("province"), arcs... },
  outputs = { prov_arcs... } }                   -- граф соседства ПРОВИНЦИЙ
originator.graph_flood{ inputs = { prov_arcs... }, outputs = { prov:field("region") } }
originator.lookup{ inputs = { cells:field("province"), prov:field("region") },
  outputs = { cells:field("region") } }          -- границы совпадают по построению
```

## Конфиг

### Точка входа

Генератор называется ОДНИМ именем; как он разложен по файлам — его собственное дело.

```tavl
name = planet

values  = ./values.tavl
buffers = ./buffers.tavl
inputs  = [ route_points, route_offsets ]

steps = [
  { name = topology, body = ./scripts/S01_topology.lua, writes = [ cells, cell_arcs ] }
  { name = climate,  body = ./scripts/S02_climate.lua,  reads = [ cell_arcs ], writes = [ cells ],
    params = { radius = 2 }, programs = { biome = ./scripts/biome_rule.ds } }
]
```

Всё написанное здесь — **demiurg-id**: путь от корня модуля без расширения. Путь с точки считается от
папки точки входа, любой другой — от корня модуля (то же правило, что у `require`). Собирает всё
`load_generator(resources, "generator/planet")`; `script_host` получает текст, а не файл.

Отделителей `//---` в точке входа быть не должно: `demiurg` разложил бы такой файл на суб-ресурсы
`путь:имя`, и id без хвоста перестал бы существовать. Шаги лежат ВНУТРИ документа списком — строка
`values = ...` рядом с блоком верхнего уровня превращает документ в структуру, у которой блоки
становятся лишними значениями (форма документа классифицируется до разбора, обе путаницы называются).

### Буферы

```tavl
{ name = cells, format = [ height = v1, moisture = v1, biome = ub1 ], layout = soa, extent = [ width, width ] }
{ name = state, format = [ used = ui1 ], layout = aos, size = one }
```

| Род | Хранение | Род | Хранение |
|---|---|---|---|
| `v` | float32 | `i` | int32 |
| `sf` | float16 | `is` | int16 |
| `ui` | uint32 | `ib` | int8 |
| `us` | uint16 | `c` | uint8, значение 0..1 |
| `ub` | uint8 | | |

- **Размер задаётся именем константы**, а не числом: генератор обязан назвать свою стоимость по
  памяти до запуска, а одно имя связывает буферы одного масштаба.
- **`extent` вместо `size`**, когда буфер адресуют как растр: число элементов выводится как
  произведение осей, и `size` рядом с `extent` — громкая ошибка. Инструмент берёт форму У ПРИВЯЗКИ.
  Прежнее написание (`width` параметром) ещё принимается, но не одновременно с `extent` на одном
  вызове.
- **`layout` — свойство хранения, а не контракта:** имя поля разрешается в пару (смещение, шаг) один
  раз, поэтому ни lua, ни `ds` разницы `aos`/`soa` не видят, и раскладку можно померить, не тронув
  скриптов.
- Поле пишется оператором (`height = v1`), а не кортежем; двоеточие появится после релиза `tavl`.
- Переиспользование буферов — решение скрипта (`view:clear()`), автоматических времён жизни нет.
- **Состояние между шагами — обычный буфер с `size = 1`**, а не отдельный механизм.

### Общие значения и диапазоны настройки

```tavl
{ numbers = { sea_level = 0.5, dry = 0.35, wet = 0.65 }
  strings = { tree = "DQkGDA==" }
  ranges  = { land_target = [0.10, 0.60, 0.01], continent_count = [3, 16, 1] } }
```

Шаг видит их среди своих параметров и может переопределить своим `params`. Порог, который читают и
нативное ядро, и правило `ds`, и подсчёт итогов, обязан жить в одном месте. `ranges` позволяет хосту
построить настройку, **ничего не зная о смысле числа**; `value_range::advance` считает позицию в шагах
от минимума, поэтому повторные «плюс-минус» не оставляют дробного хвоста. Значение без диапазона не
настраивается.

### Шаги

Буфер в `writes` доступен своему шагу и на чтение, поэтому повторять его в `reads` нельзя. Зерно шага
— `hash(зерно пайплайна, имя шага)`, а не позиция в потоке случайности: перестановка или перезапуск
одного шага не сдвигает случайность остальных. Из привязок выводятся порядок, доступность буферов
после шага N (`published_after`) и громкий отказ до исполнения, если шаг читает то, чего никто не
писал.

### Входы пайплайна

`inputs = [ ... ]` — буферы, которые заполняет ХОСТ, а не шаг. Понятие из двухмасштабной генерации:
грубый мировой проход отдаёт каркас, чанковый пайплайн читает из него свою область, и кто в неё
попадает, знает только хост. Объявляется автором, а не выводится из «никто не пишет» — иначе не
отличить «привезли извне» от опечатки в имени. **Контракт хоста жёсткий: заполненный вход обязан быть
функцией ОБЛАСТИ чанка, а не того, что успело подгрузиться.** Неполный вход — другой мир под тем же
ключом, поэтому либо полнота, либо отложенный чанк.

## Апертуры: параллельность выводится, а не сообщается

Скрипт не говорит движку, что вызов можно распараллелить: он этого не знает. Апертуру объявляет
инструмент, из неё и фактических привязок выводится способ исполнения.

| Апертура | Что делает | Условие параллельности | Диапазон относится к |
|---|---|---|---|
| `pointwise` | читает и пишет свой элемент | всегда; источник и приёмник могут совпадать | входам и выходам |
| `gather` | читает произвольные элементы, пишет свой | **источник ≠ приёмник**, иначе отказ | только выходам |
| `scatter` | пишет по чужим индексам | только готовым инструментам с собственным детерминизмом | только входам |
| `reduce` | много -> одно | всегда, фиксированное разбиение на чанки | входам |
| `sequential` | порядок значим | никогда | первому выходу, входы читаются целиком |

Нарушение по возможности **не выражается**, а не ловится: вью на чтение и вью на запись — разные
типы, у первого нет операции записи. Оставшийся случай (gather с совпадающими источником и приёмником)
отклоняется `check_dispatch` до исполнения, с именами шага, инструмента и поля.

Свёртки разбиваются на чанки ФИКСИРОВАННОГО размера и объединяются строго в порядке чанков, поэтому
сумма плавающих чисел не зависит от числа потоков.

## Инструменты

Устройственное тело есть у 25 инструментов из 46: `fill`, `remap`, `blend`, `modulate`, `ratio`,
`maximum`, `minimum`, `classify`, `decay`, `index`, `position_grid`, `box_blur`, `filtered_blur`,
`count_by`, `label_colour`, `voronoi_label`, `lookup`, `graph_blur`, `graph_frontier`, `graph_slope`,
`graph_vote`, `polyline_distance`, `noise_value`, `noise_perlin`, `noise_cellular`. У остальных вызов
остаётся на CPU, и очередь с ним — тоже.

`sphere_points` тела не получит, и это ИЗМЕРЕННЫЙ отказ: угол спирали Фибоначчи берётся от дробной
части `i * φ`, от которой во `float32` остаётся четыре бита — на миллионе точек угол расходится с
точным на `0.9955` оборота. Фиксированная точка это чинит, но сменила бы решётку НА ОБОИХ путях, то
есть сменила бы мир, а выигрывать нечего: следом идёт `sphere_adjacency` с апертурой `scatter`, и
приклеиться в прогон всё равно не к чему.

### Ядро (`add_standard_tools`, без внешних зависимостей)

| Инструмент | Апертура | Что делает |
|---|---|---|
| `fill` | `pointwise` | константа во все компоненты поля |
| `position_grid` | `pointwise` | мировые позиции регулярной сетки в поле `v2`/`v3` |
| `value_noise` | `pointwise` | value noise на хеше, 2D-сетка (для сборки без примитивов) |
| `index` | `pointwise` | номер элемента как значение: `i * scale + offset` |
| `remap` | `pointwise` | `значение * scale + offset` с ограничением; `absolute` — модуль до умножения; `component` — какую компоненту читать |
| `classify` | `pointwise` | пороговая классификация по двум полям |
| `blend` / `modulate` / `ratio` / `decay` | `pointwise` | `a*x+b*y`, `scale*x*y`, `scale*x/y` (минимальный знаменатель ОБЯЗАТЕЛЕН), `offset + amp*exp(-x/width)` |
| `maximum` / `minimum` | `pointwise` | наложение слоёв вместо сложения |
| `box_blur` | `gather` | усреднение по окну; приёмник обязан отличаться от источника |
| `reduce_min` / `reduce_max` / `reduce_sum` / `reduce_count_above` | `reduce` | свёртки с фиксированным разбиением |
| `group_by` / `accumulate` | `scatter` | ключ -> CSR групп; ключ и значение -> суммы по корзинам |
| `noise_value` / `noise_perlin` / `noise_cellular` | `pointwise` | СОБСТВЕННЫЙ шум движка по полю позиций, с октавами |

Почему арифметика разбита на инструменты, а не пишется в `ds`: программа возвращает ОДНО значение в
ОДНО поле, и вызов функции в этой версии `ds` не является операндом выражения. Движок считает
арифметику, конфиг остаётся местом, где слагаемые складываются.

Отдельные решения, которые иначе выглядят странно:
- `maximum`/`minimum` — там, где слои НАКЛАДЫВАЮТСЯ: остров поднимается над дном, а не прибавляется к
  спадающему конусу материка;
- `absolute` у `remap` — складчатый (ridged) шум: излом хребта там, где значение проходит ноль;
- `component` у `remap` — правило на `ds` компоненту вектора достать не может, а объёму она нужна на
  каждом шаге;
- `ratio` — нормировка (взвешенное среднее без деления не выражается). Нулевая сумма весов означает
  «ни одно правило здесь не действует», и что отвечать в этом месте — дело автора конфига, поэтому
  минимальный знаменатель обязателен буквально: у поля плотности ноль это ПОВЕРХНОСТЬ;
- `index` — номер элемента как данные: заливка, несущая НОМЕР клетки границы, даёт доступ ко всему,
  что у той границы лежит, а признак «здесь граница» — только расстояние.

Параметры принимают и булевы значения; проверка на bool идёт ПОСЛЕ числа и строки, иначе единица
приезжала бы булевым.

### Собственный шум ядра

`noise_value` (значение решётки), `noise_perlin` (градиентный), `noise_cellular` (Ворли F1) — каждый
берёт поле позиций (`v2` или `v3`) и отдаёт значение в `[-1, 1]` с октавами (`octaves`, `lacunarity`,
`gain`, `ridged`). Решётку строит `position_grid`, у которого тело тоже есть.

**ЭТО НЕ FastNoise2 И НЕ ОБЯЗАН С НИМ СОВПАДАТЬ.** У FastNoise2 дерево узлов приезжает закодированной
строкой и вычисляется его библиотекой — перенести его на устройство значило бы перенести туда
интерпретатор графа. Здесь взяты известные алгоритмы, написанные ДВАЖДЫ (C++ и GLSL), и поле,
посчитанное ими, не равно полю FastNoise2 ни при каком зерне.

- **один хеш на оба пути** (`utils::shared::prng2`), **оба пути считают во `float32`**. Побитового
  совпадения при этом НЕТ и обещать его нельзя: измерено — типичное расхождение один последний бит,
  худшее `3e-06` на накоплении четырёх октав, точно совпадают `8`–`15%` элементов. Драйвер вправе
  применять FMA и переставлять ассоциативность, и это ровно то расхождение путей, которое библиотека
  объявляет (§4.2);
- **решётка трёхмерна всегда**, поле из двух компонент означает срез `z = 0`: одна реализация вместо
  двух, которые разъехались бы. Названная цена — вдвое больше хешей, чем нужно плоской решётке;
- **зерно приходит общей шапкой**, а не параметром: float32 не удержит 32-битное зерно;
- **`feature` и `frequency` — одно и то же число двумя способами**, объявлять оба сразу нельзя. Период
  решётки равен единице, поэтому `frequency = 1 / feature` тождественно, а не измерено (в отличие от
  дерева FastNoise2, чей период движок измеряет).

**ЦЕНА ИЗМЕРЕНА И НЕ ЛЬСТИТ**: на CPU свой шум в девять раз медленнее FastNoise2 при равном числе
потоков (`28.1` против `3.2` мс на 1024² и четырёх октавах) — у того SIMD, а здесь скалярный проход
через общий аксессор плюс трёхмерная решётка. **На устройстве он окупается**: решётка и три поля шума
на 262144 элементах — `30.6` мс включая передачу против `223.3` мс одного потока CPU.

Отсюда правило: свой шум берут там, где очередь объявлена устройственной; где всё считается на CPU,
FastNoise2 остаётся быстрее.

### Замкнутая поверхность и граф соседства (`add_graph_tools`)

Другой способ адресовать пространство: у сферы нет плоскости, любая развёртка даёт шов, а шов — место,
где соседство считается неверно и притом молча. Адрес поверхности — направление, соседство — данные
(CSR), края карты не существует.

| Инструмент | Апертура | Что делает |
|---|---|---|
| `sphere_points` | `pointwise` | решётка Фибоначчи на сфере; ось — параметр |
| `sphere_adjacency` | `scatter` | K ближайших, СИММЕТРИЗОВАННЫЕ в канонический CSR |
| `graph_blur` | `gather` | усреднение по соседям вместо окна растра |
| `graph_frontier` | `gather` | «есть ли сосед с другой меткой» |
| `graph_flood` | `sequential` | заливка от нескольких источников по стоимости и ПРОХОДИМОСТИ |
| `graph_slope` | `gather` | средний модуль разности со всеми соседями |
| `graph_vote` | `gather` | пустая клетка перенимает метку сильнейшего соседа |
| `poisson_seeds` | `sequential` | затравки под маской не ближе `min_distance` |
| `lookup` | `gather` | значение из другого буфера по индексу в поле |
| `connected_components` | `sequential` | связные куски подграфа под маской, нумерация плотная |
| `label_adjacency` | `scatter` | CSR по МЕТКАМ, собранный из CSR по элементам |

- **Соседство симметризуется.** Асимметричный граф даёт ошибки через несколько шагов (заливка идёт в
  одну сторону, размытие усредняет не то) и почти не находится по результату.
- **У заливки отдельный вход проходимости, а не только стоимость.** Область, залитая через
  непроходимое место «по дорогой цене», получается РАЗОРВАННОЙ; непроходимая клетка не входит в
  очередь вовсе, поэтому связность держится по построению.
- **Строка метки лежит по индексу, равному МЕТКЕ**, строка 0 всегда пуста — тот же индекс, что у
  `group_by`/`accumulate`. Иначе запись области, её суммы и её строка соседства расходятся, и все три
  буфера при этом остаются валидными.
- **Решётка Фибоначчи** выбрана за почти равные площади клеток: любая сумма по клеткам считается без
  весов.
- `graph_flood` отвечает «кто ближе» (один проход, геометрия), `graph_vote` — «кто напористее» (много
  проходов, вес меняется между ними). Подменять их друг другом не стоит.
- `poisson_seeds` гасит кандидатов ПО ПРЯМОЙ, а заливка идёт ПО ГРАФУ: замкнутое море рядом с океаном
  может остаться без затравки из-за затравки по другую сторону перешейка.
- `label_adjacency` — единственный способ вырастить область из областей так, чтобы границы совпали:
  расти по клеткам — граница ляжет посреди провинции.

### Объём (`add_volume_tools`)

| Инструмент | Апертура | Что делает |
|---|---|---|
| `marching_cubes` | `scatter` | поверхность нулевого уровня поля плотности треугольниками |
| `polyline_distance` | `gather` | расстояние до набора ломаных (CSR цепочек) с отсечением по прямоугольнику |

- **Длина выхода неизвестна до исполнения, и нового механизма под это не понадобилось:** ёмкость —
  объявленный размер буфера, занятая длина — обычный буфер на один элемент, переполнение — громкий
  отказ (обрезанная поверхность выглядит как дырка в мире).
- **Позиции приходят ПОЛЕМ**, а не выводятся из шага решётки: инструмент не знает ни про чанки, ни про
  шаг, и второго мнения о том, где лежит клетка (i, j, k), не заводится.
- **Таблица случаев ВЫВОДИТСЯ** из правила соединения на грани, а не списывается: правило — функция
  только четырёх знаков самой грани, поэтому соседние кубы видят общую грань одинаково, и
  непрерывность получается по построению. Ориентация оттуда же.
- **Проверять такую поверхность надо по НАПРАВЛЕННЫМ рёбрам** (проходов вперёд = проходов назад):
  критерий «ребро принадлежит двум треугольникам» неверен — на неоднозначной грани поверхность
  законно касается сама себя. Измерено: незакрытых рёбер `0`, касаний `74` из `20752`.
- **Нормаль — центральная разность, поэтому чанку нужна полоса в один узел** (`border = 1`): вершины
  на шве совпадают точно, а нормали нет, и шов виден полосой другого оттенка.
- У `polyline_distance` `max_distance` ОБЯЗАТЕЛЕН: он значит и «насколько широко смотреть», и «что
  отвечать там, где ломаной нет», а два default'а этих смыслов однажды разъехались. `metric` задаёт
  ФОРМУ сечения: евклид — круглая труба, чебышёв — угловатая. Кривую движок не знает: сплайны
  распрямляются в ломаную один раз на грубом масштабе, где точек сотни.

### Решатель ограничений (`add_constraint_tools`)

| Инструмент | Апертура | Что делает |
|---|---|---|
| `collapse` | `sequential` | раскладка по растру из весов и матрицы допустимых соседств |
| `graph_collapse` | `sequential` | то же по графу (CSR); матрица обязана быть СИММЕТРИЧНОЙ |
| `learn_rules` | `sequential` | правила из ОБРАЗЦА: окно NxN -> алфавит узоров и таблица соседств |

Покупает то, чего не даёт ни шум, ни вороной, ни заливка: **жёсткий локальный запрет** («вода никогда
не граничит с травой»). Ядро одно на три инструмента — соседство приходит функцией.

- **Противоречие — нормальный исход** arc consistency, а не сбой: отсюда объявленное число попыток и
  ГРОМКИЙ отказ при их исчерпании. Тихо оставленная недособранная сетка — другой мир под тем же зерном.
- **Энтропии нет намеренно:** классика сравнивает шенноновскую энтропию во float. Критерий здесь
  целочисленный (меньше всего вариантов), ничья ломается хешем клетки и зерна.
- **Память названа вслух:** волна это `клетки x ceil(тайлы/32)` слов. Счётчиков поддержки на
  (клетка, тайл, направление) нет — при `512x512` и 64 тайлах это 64 МиБ; поддержка считается
  объединением битовых наборов. Размен времени на память, обратить его можно только после замера.
- **Вес — предпочтение ПРИ ВЫБОРЕ, а не частота в результате:** объявленные `2.4/1.8/1.0` дали
  `20%/11%/32%`, потому что раскладку решают ограничения и заранее занятые клетки.
- **Откаты — две величины:** `rollbacks` это ТЕРПЕНИЕ (сколько отмен на попытку), `history` — ПАМЯТЬ
  (на сколько наблюдений назад). Хранится журнал изменений, а не снимок волны; отменённый выбор
  ЗАПРЕЩАЕТСЯ, иначе поиск не сужается. Окупаются на тесных правилах (до 3x), не окупаются на дешёвой
  работе и бессильны против глобального следствия — там они не лучше перезапуска. Журнал стоит ~18%,
  когда откатов не случилось; раскладка побитово та же.
- **Обучение воспроизводит и ОГОВОРКИ образца:** «ни одного окна, которого не было в образце» — это
  обещание, которое проверяется против САМОГО образца, а не против выведенной из него таблицы. Окно
  это рычаг цены: 7 узоров / 26 мс, 85 / 556 мс, 435 / 80 с.
- **Стоимость линейна по клеткам** (3.3 мкс/клетка) — против 3 нс у поэлементного прохода. Это цена
  решения задачи, а не обхода поля.
- Чанковой генерации у решателя нет: ограничения пересекают границу чанка, поэтому `key_support`
  здесь `global`.

### Scatter (`add_scatter_tools`) — и почему он только у готовых инструментов

Произвольного параллельного разброса не бывает детерминированным: детерминизм даёт не апертура, а
конкретная схема. Общий приём — ФИКСИРОВАННОЕ разбиение на чанки: порядок внутри группы и порядок
сложения определяются номером чанка и индексом элемента, а не тем, какой поток что успел. Поэтому
`scatter` существует только как готовые инструменты (`group_by`, `accumulate`, `sphere_adjacency`,
`voronoi_*`, `marching_cubes`, `label_adjacency`), а не как право, выдаваемое любому телу.

### Примитивы (`add_all_primitives`)

| Инструмент | Апертура | Что делает |
|---|---|---|
| `noise_grid` | `pointwise` | FastNoise2 на регулярной 2D-сетке |
| `noise_at` | `pointwise` | FastNoise2 в произвольных точках (поле позиций `v2`/`v3`) |
| `voronoi_label` | `gather` | какому сайту принадлежит клетка (kd-дерево строится подготовкой) |
| `voronoi_polygons` | `scatter` | контуры областей как ПЛАНАРНАЯ сетка с общими вершинами |
| `voronoi_adjacency` | `scatter` | точная топология соседства из триангуляции Делоне |

- **Дерево шума — закодированная строка** из редактора FastNoise2: граф шума становится данными
  конфига, а не кодом.
- **Кросс-машинный детерминизм куплен опцией `FASTNOISE2_STRICT_FP`:** без неё наборы SIMD расходятся
  на `1.8e-07`, то есть одно зерно даёт разные артефакты на разных машинах. Проверено измерением;
  `feature_set` после этого диагностический.
- **Размер формы задаётся в МИРОВЫХ единицах (`feature`).** Частота обратной размерности, и её
  перевод в метры зависит от масштаба ДЕРЕВА, то есть от чужих данных: частота 1/190 в расчёте на 190
  метров дала форму в 17 километров, потому что период дерева оказался 91 единица — чанк в 32 метра
  видел поле постоянным. Поэтому масштаб дерева измеряет движок (среднее расстояние между сменами
  знака, зерно ноль, кэш по тексту дерева). `frequency` остаётся там, где мировая длина не имеет
  смысла; оба сразу — громкая ошибка.
- **Растр отвечает на вопрос о соседстве плохо** (тонкая область может не получить ни одной клетки,
  две области могут коснуться по диагонали), поэтому соседство берётся из геометрии. Соседи в CSR
  отсортированы, результат не зависит от порядка обхода диаграммы.
- У `voronoi_adjacency`/`voronoi_polygons` `width`/`height` — границы МИРА в его единицах, а не растр
  приёмника; сложить их с `extent` буфера значило бы объявить равными две разные величины.

### Быстрый путь доступа к полю

Нативное ядро берёт поле как `span` и обрабатывает векторно — но только при ТОЧНОМ совпадении
C++-типа с родом хранения и однокомпонентном поле. Сверять один размер нельзя: `ui1` и `v1` оба
четырёхбайтовые, и `span<float>` над сырым `uint32` молча писал бы туда биты float (`1061158912`
вместо `0.75`). Роды `sf` и `c` быстрого пути не имеют вовсе.

**Копия буфера копирует данные ОТ НАЧАЛА ДО НАЧАЛА**, а не вектор целиком: внутри лежат и память, и
сырой указатель на выровненное начало ВНУТРИ неё, а у новой аллокации это начало приходится на другое
смещение. Копия по умолчанию делила бы память с оригиналом — дефект молчащий, и хуже всего то, что
сверка «двух путей» через копию буфера сравнивала бы память с самой собой и сходилась ВСЕГДА.

## devils_script над буфером

Программа компилируется против ИМЁН входных полей, взятых у самих привязок: в скрипте поле зовётся
ровно так же, как в `buffers.tavl`, и второго списка имён не существует.

```
{ value_or = { smoothed < ctx:arg:sea_level, 0,
  value_or = { moisture < ctx:arg:dry, 1,
  value_or = { moisture < ctx:arg:wet, 2, 3 } } } }
```

- **Апертура следует из РЕГИСТРАЦИИ, а не объявляется:** доступны ровно два обращения — прочитать поле
  своего элемента и вернуть значение. Функции, которая пишет или добирается до соседа, не
  зарегистрировано, поэтому программа СТРУКТУРНО `pointwise`. Доступ к соседям, когда появится,
  приедет отдельной регистрацией — и апертура станет `gather` со всеми её проверками.
- **Правило в скрипте, числа в конфиге:** `ctx:arg:имя` берётся из параметров шага, выставляется один
  раз на проход. Забытый параметр — громкая ошибка с именем, а не молчаливый нуль в правиле.
- **Случайность — функция от элемента:** перед каждым элементом состояние PRNG выставляется в
  `hash(зерно шага, индекс)`, поэтому `chance`/`random` не зависят от раскладки по потокам.
- **Saved-слоты сбрасываются на каждый элемент.** `ds::context::clear()` не трогает содержимое
  saved-стека, а контекст живёт на ЧАНК: без сброса слот, сохранённый на элементе i, читался бы на
  i+1, и «параллельно == последовательно побитово» ломалось бы на границе чанка, которая зависит от
  числа потоков. Цену платят только программы, которые `ctx_save` используют.
- **Типы проверяются на разборе:** система собрана с небезопасными опкодами, что удваивает скорость
  исполнения, а не сошедшаяся по типам программа до исполнения не доходит.

## Очередь вычислений

Названная цепочка заранее объявленных вызовов, которая исполняется целиком. Разделение НЕЙМСПЕЙСОМ, а
не флагом: `originator.box_blur{...}` считает сейчас, `originator.queue.box_blur{...}` работу
ОБЪЯВЛЯЕТ. Строка аргументов у обоих одна и та же.

```lua
local report = originator.queue{
  originator.queue.box_blur{ inputs = { height }, outputs = { smoothed }, params = { radius = 2 } },
  originator.queue.run_script{ program = "biome", inputs = { smoothed, moisture }, outputs = { biome } },
  output = { smoothed, biome },   -- уезжает на хост
  resident = { colour },          -- живое, но остаётся на устройстве
  device = true,
}
```

- **Входы ВЫВОДЯТСЯ, выход ОБЪЯВЛЯЕТСЯ.** Своих читателей внутри очередь видит сама; кто прочитает
  результат ПОСЛЕ, знать не может. Это граница передачи: на устройстве неназванное не обязано покидать
  его вовсе.
- **Из границы следует проверка на мёртвую работу:** элемент, чей выход никто не читает и который не
  назван на границе, — потраченный проход. Сюда же перезапись без чтения; затирание проверяется по
  ПОКРЫТИЮ диапазона, потому что два вызова, пишущие разные отрезки одного поля, оба живые.
- **Две границы, а не одна:** `output` едет на хост, `resident` остаётся на устройстве (видимая
  текстура, которую читает пост-процесс). Проверке мёртвой работы они равны, различаются только планом
  передачи; одно поле в обоих списках — отказ. На CPU разницы нет.
- **Один отказ на всю очередь**, до первого вызова, с НОМЕРОМ элемента. Привязки нативного инструмента
  проверяются тем же `check_dispatch`, что и у одиночного вызова. Из lua проверка идёт на ОБЪЯВЛЕНИИ —
  тогда сообщение приходит из той строки, где вызов написан.
- **Объявленный вызов обязан попасть в очередь ровно один раз:** забытый ничего не посчитал, отданный
  дважды посчитал то же самое повторно, и по результату не видно ни того, ни другого. Расхождение
  проваливает шаг.
- Отчёт: `calls` (объявлено), `passes` (реальных обходов данных), `fused` (сколько вызовов слилось),
  `clamped` (сколько упёрлось в ёмкость), `on_device`.

**Кто в очередь не пускается и почему** — у трёх отказов три разные причины:

| Апертура | Причина |
|---|---|
| `scatter` | пишет по чужим индексам в структуру другой формы, и ПОРЯДОК записей задаёт алгоритм |
| `sequential` | порядок значим по построению: очередь на нём разрывается, и это видно в конфиге |
| `reduce` | отдаёт ОДНО число, а промежуточных значений в lua у очереди нет — деть его некуда |

У `scatter` есть объявляемое исключение (`order_free_writes`): отклоняли ПОРЯДОК, а не чужие индексы,
а у целочисленного накопления порядка нет вовсе. Плавающее накопление объявить так нельзя.

Про накопитель очередь выводит сразу три вещи одним вопросом «читает ли он то, во что пишет»: `fill`
нулями перед ним — честная работа; его выход это ВХОД очереди, и на устройстве начальное значение
загружается (иначе атомик прибавлял бы к мусору); между ним и предыдущим писателем нужен барьер.

### Диапазон вызова из поля

`range = { count = state:field("used") }` — число элементов читается из поля ПЕРЕД вызовом. Механизм
уже был (ёмкость = размер буфера, занятая длина = буфер на один элемент); новое только то, что
диапазон умеет на такое поле сослаться. На устройстве тот же буфер и есть аргумент `dispatchIndirect`.

- счётчик читается в момент ИСПОЛНЕНИЯ: его пишет предыдущий элемент этой же очереди;
- поле обязано быть однокомпонентным целым (дробное число элементов — тихое усечение);
- никакой элемент не смеет писать счётчик ПОЗЖЕ читателя — отказ называет оба номера;
- счётчик считается ЧТЕНИЕМ: проход, посчитавший длину, живой, а барьер выводится тем же вопросом;
- диапазон со счётчиком начинается с нуля, явные границы рядом — отказ;
- проверяется ЁМКОСТЬ приёмника, а не диапазон;
- **превышение ЗАЖИМАЕТСЯ, а не отклоняется**: в шейдере бросить нечем, и два поведения у одного
  объявления недопустимы. Поэтому факт зажима едет наружу в `report.clamped`, и **тело шага обязано
  его читать**;
- сливаются вызовы со счётчиком только при ссылке на ОДНО И ТО ЖЕ поле: равенство диапазонов тогда
  держится по построению, а не по совпадению чисел.

### Слияние проходов

Два подряд идущих `pointwise` вызова над одним диапазоном исполняются в ОДНОМ обходе данных:
перестановка обхода на «плитка, потом все вызовы группы» оставляет промежуточное поле в кэше. Законно
ровно для `pointwise` и ровно при равных диапазонах; побитовое равенство сохраняется и проверено при
1, 3 и 7 потоках. Размер плитки — из рабочего набора группы (общее поле считается один раз), целевой
объём L1d взят НАЧАЛЬНЫМ значением для замера.

**Замер важнее самого слияния.** Цепочка `remap` -> `blend` -> `modulate`, три прохода против одного:

| Элементов | Рабочий набор | 1 поток | 11 потоков |
|---|---|---|---|
| `1 048 576` | `12` МБ | `+0.7%` | **`+25.4%`** |
| `4 194 304` | `48` МБ | `-1.0%` | **`+14.0%`** |
| `16 777 216` | `192` МБ | `-0.4%` | **`+14.1%`** |

Ноль в один поток при любом размере и 14–25% на одиннадцати. Объяснение из тех же чисел: проход стоит
`18.8` нс на элемент, то есть один поток гонит `0.6` ГБ/с — экономить нечего; одиннадцать потоков
доводят проход до `4.0` нс при ускорении всего `4.7x`, то есть параллельный проход УЖЕ упёрся в
полосу. Отсюда следует, куда смотреть дальше, и это не слияние: `18.8` нс за одно умножение со
сложением — цена ОБЩЕГО АКСЕССОРА, а быстрым путём пользуются только шумовые и объёмные инструменты.

Программа `ds` в группу пока не входит: её исполнение живёт в другом слое, а вход туда на каждой
плитке создавал бы контекст виртуальной машины заново (нужен свой `prepared_call`).

Про сам замер: разница здесь единицы процентов, а один прогон меряет тепловое состояние. Поэтому
режим отдельный (`--bench-queue`), варианты чередуются, читать надо МЕДИАНУ — минимум первой пары не
значит ничего (на сетке `1024` он дал `-72%` просто потому, что буфер достался горячим).

## Та же очередь на устройстве

Полный контекст — [`ORIGINATOR_GPGPU.md`](../../ORIGINATOR_GPGPU.md). Единица переноса — ОЧЕРЕДЬ, а не
шаг. Побитовое совпадение CPU и GPU генератору не нужно и не обещано; больное место одно — свёртки,
чей результат возвращается в мир.

**В плане всё ВЫВОДИТСЯ из той же очереди, которую проверяет `check_queue`:**

- **передача** — из границ: загружается то, что вызов читает и до него никто не писал; выгружается
  ровно `output`;
- **барьеры** — тем же вопросом, что проверка мёртвой работы;
- **род ресурса** — из того, КАК поле читают: читаемое ФИЛЬТРОМ (между элементами) становится
  картинкой, остальное остаётся буфером. Объявляется не «сделай картинкой», а единственное, чего из
  привязок не видно, — что этот вход читают выборкой.

**УЗКИЙ РОД НЕ ОТКАЗ: копия на устройстве это КЭШ, а кэш вправе быть ШИРЕ истины.** Поле `ub1`/`us1`/
`sf1`/`c1` живёт на устройстве в 32-битном роде того же смысла, а преобразование на границе делают те
же `load_component`/`store_component`, которыми пользуется аксессор хоста — поэтому семантика двух
путей совпадает по построению, вместе с зажимом и округлением. Зажимает при этом ШЕЙДЕР, по границам
ИСХОДНОГО рода: у поля из `resident` скачивания не будет вовсе. Цена — передача и память устройства
вчетверо больше хостовых у байтового поля, и платится она только на устройственном пути.

Отсюда же следует, кому нужно `device_integer_ready`: телу над ШИРОКИМ целым. Узкое целое точно
представляется во `float32` (предел 2^24), поэтому тело, написанное против `float`, над ним считает то
же самое, и решает это род привязки, а не объявление инструмента.

**Параметр-СЛОВО переводит сам инструмент.** Push-константа несёт `float`, а `metric = "chebyshev"`
во `float` не влезает. Числового синонима заводить нельзя — это два способа сказать одно, и они
разъедутся; поэтому у `device_param` есть поле `resolve`: функция, которая читает `parameters` и
отдаёт число. Перевод имени в число живёт там же, где тело на CPU, и происходит один раз при выкладке
push-константы.

**Индекса, подготовленного на хосте, на устройстве нет** — туда уезжают только объявленные привязки.
Тело `polyline_distance` поэтому СОБИРАЕТ отрезок на месте из тех же двух буферов, из которых его
собирает подготовка на CPU, а отсечение по прямоугольнику остаётся не оптимизацией, а условием
применимости.

Отсюда: **привязки нельзя писать в тексте инструмента руками.** Инструмент объявляет ТЕЛО против
аксессоров (`in_<i>_at`, `in_<i>_length`, `in_<i>_sample`, `out_<j>_set`, `out_<j>_add`), а преамбулу
собирает `build_device_shader`, уже зная выведенные роды. Тем же сборщиком собирается переведённая
программа `ds`, поэтому шапка push-константы в проекте ОДНА:
`count, begin, extent_x, extent_y, seed`, за ней объявленные параметры по одному `float`.

**Откуда берётся устройственный код** — водораздел не «GLSL можно или нельзя», а КТО РЕШАЕТ, ЧТО
СЧИТАЕТСЯ:

| | Кто решил | Как приезжает |
|---|---|---|
| нативный инструмент | разработчики | тело написано заранее и лежит в библиотеке рядом с телом на CPU |
| `run_script` | автор данных | приносит программу `devils_script`, в GLSL её переводит движок |

Готовый GLSL внутри библиотеки — нормально: это исходник проекта, он компилируется вместе с движком и
читается на ревью. `run_script` принимает только `ds`: программа проходит разбор, проверки апертуры и
привязок и перевод по AST, который отдаёт сам `ds`; принесённый шейдер не прошёл бы ничего и получил
бы прямой доступ к памяти устройства. Правило подпёрто типом: `translated_form` из строки не собрать,
конструктор закрыт ключом, который ядро выдаёт ровно переводчику.

**Где считается очередь — тоже объявление.** `device = true` означает «эта очередь РЕШЕНА на
устройстве»: решение живёт в конфиге, одинаково на всех машинах, а машина, которая исполнить его не
может, отказывает ГРОМКО. Молча посчитав на CPU очередь, решённую на GPU, генератор выдал бы другой
мир под тем же зерном. План строится один раз и переиспользуется по ПОДПИСИ очереди (структура, не
числа): смена порога не строит второй план. Всё уходит ОДНОЙ отправкой — пошаговая мерилась и
оказалась в 2.4 раза дороже.

### Что переводится из `devils_script`

Математика с именами GLSL, `value_or`, `inv`, ветвления `select` / `sequence` / `switch` / `random`,
случайность `chance` / `rndmix` / `rndmix1`, локали `ctx_save` / `ctx_set`. Не переводятся списки
(нужна динамическая память на элемент), `assert`/`trace` (диагностика в очередь не пускается) и
`execute` (нужны своя трансляция и свой фрейм). Непереводимая конструкция — не ошибка, а объявленный
ОТКАЗ с причиной: очередь остаётся на CPU.

Проверку типов делает `glslc` — свой вывод типов был бы третьей системой типов в проекте. Арифметика
идёт во `float32`; целочисленная программа на числах до 2^24 совпадает с CPU ПОБИТОВО, и именно на ней
транслятор и проверяется. На плавающем правиле GN01 расхождение измерено: `0.50%` клеток попадают в
другой класс, потому что классификация усиливает разницу арифметик до смены класса.

**Почему арифметика плавающая, даже когда числа целые.** В программе `originator` у `ds` ЛЮБОЕ чтение
поля — это `double`: аксессор так и зарегистрирован, независимо от рода поля. Значит целочисленная
арифметика в шейдере РАЗОШЛАСЬ бы с `ds`, а не сошлась: `a / b` стало бы целочисленным делением, сумма
переполнялась бы на 2^32 там, где `double` точен до 2^53. Но у `float32` есть потолок 2^24, и выше
него соседние целые склеиваются — поле-идентификатор шире шестнадцати миллионов на устройстве
слипается, и вот это уже расхождение с `ds`, который читает точно. Граница проведена по семантике:
целым остаётся ЛИСТ.

| Что | Как переводится |
|---|---|
| целочисленный литерал, чтение поля целого рода | ЛИСТ, остаётся целым |
| сравнение двух листов | целыми, без допуска |
| запись листа в целое поле | целым, без круга через `float32` |
| любая арифметика | плавающей, как у `ds` |

Сравнение двух листов целыми ответа не меняет: у `ds` это сравнение двух ТОЧНЫХ `double`, а допуск на
целых равносилен равенству, — зато выше 2^24 оно перестаёт врать. Проверено ровно там, где это видно:
на 4096 парах соседних целых, начиная с 2^24, обе стороны отвечают «не равны»; до правки устройство
отвечало бы «равны» у всех пар.

**Три объявленных расхождения с CPU:**

- **случайность — свой поток.** У `ds` соль места вызова генерирует эмиттер при компиляции, и в AST её
  нет; на устройстве соль выводится из порядка обхода перевода, зерно приходит в общей шапке, а хеш
  32-битный (`utils::shared::prng2`, тот же, что у всего движка). Значение остаётся функцией от (зерно,
  элемент, место вызова) — повторяемо прогон в прогон и не зависит от разбиения работы, — но НЕ равно
  значению CPU. Проверено: устройственный `chance` побитово совпадает с формулой на хосте;
- **`switch` без совпавшей ветки отдаёт ноль.** У `ds` ветки по умолчанию нет вовсе и такой `switch`
  не кладёт значения на стек — ноль здесь определённое поведение вместо неопределённого;
- **`ctx_save`/`ctx_set` — локали шейдера, объявленные ДО записи результата.** Поэтому запись изнутри
  ветки ОТКЛОНЯЕТСЯ: локаль вычисляется до того, как ветка выбрана. Доказательства доминирования у
  перевода нет, и граница проведена по синтаксису.

Равенство переводится сравнением С ДОПУСКОМ — ровно так его считает `ds`, а побитовое `==` разошлось
бы с ним на границе правила. Ветвления собираются вложенными тернарниками, но переводятся ВПЕРЁД:
перевод попутно нумерует аргументы push-константы и соли случайности, а порядок вычисления аргументов
одного вызова в C++ не определён.

## Чанки

Чанкованная генерация и фоновое исполнение — **две разные вещи**. Фоновый поток живёт у потребителя;
в библиотеке остаётся правило независимости: **результат чанка зависит только от (зерно мира, ключ) и
не зависит от того, какие чанки посчитаны раньше.** `set_chunk` не перевыделяет буферы, а
`clear_buffers()` существует ради доказательства обратного: если результат меняется от обнуления,
какой-то шаг читает то, чего не писал.

| Значение | Что это | Для чего |
|---|---|---|
| `step.seed` | `hash(зерно мира, имя шага)` | поле по мировой позиции: **непрерывно** через шов |
| `step.chunk_seed` | `hash(зерно мира, имя шага, ключ)` | то, что обязано быть **независимым** в чанке |

По умолчанию берётся непрерывное: шум, разъехавшийся на швах, хуже случайно совпавшего джиттера.

**Что чанкуется** (измерено на GN01, `512x512` как 2x2, 4x4 и 8x8):

| Апертура | Поведение |
|---|---|
| `pointwise` | точно: расхождение с картой целиком ровно `0` на всех 262144 клетках |
| `gather` | расходится только в полосе шириной `radius` у границы ⇒ нужна полоса перекрытия |
| `scatter` | зависит от НОСИТЕЛЯ КЛЮЧА; глобальный отклоняется |
| `reduce` | свёртка по чанку не равна свёртке по карте |

**Носитель ключа — единственное, что здесь объявляется, а не выводится.** У `pointwise`/`gather`
критерий чистый: значение определяется ограниченной окрестностью. У `scatter` выход индексируется
ГРУППОЙ, и ограничена не окрестность, а носитель ключа: `chunk_local` (чанк заканчивает группу сам)
или `global` (ни один чанк не заканчивает ни одной). Что означает ключ — знание автора пайплайна, из
одного чанка не проверяется никак, поэтому по умолчанию стоит безопасное: молчание означает отказ.

```lua
originator.group_by{ inputs = {...}, outputs = {...}, key_support = "global" }
```

Отказ здесь по СМЫСЛУ: глобальную сводку из чанков не собирают, её считают в грубом мировом проходе,
где чанков нет. Стриминговый генератор естественно имеет два масштаба — грубый мировой (один раз:
материки, области, диаграмма, сводки) и мелкий чанковый (по требованию: рельеф, детали). Числа это
подтверждают: вся диаграмма соседства на 1024 сайта стоит `0.48` мс.

Кросс-чанкового слияния нет намеренно, но замер уже показал, каким оно должно быть: при float-
аккумуляторе порядок прихода чанков меняет **816 из 1024** групповых сумм (`4.8e-07`), при
целочисленном или фиксированно-точечном — ровно `0` в любом порядке.

**Практическое следствие: самокалибровка по измеренному диапазону несовместима с чанкованием.** Шаг,
который меряет min/max и нормализует по ним, в каждом чанке даёт своё отображение. Выбор режима
принадлежит конфигу, а не догадке скрипта.

## Учёт исполнения

`execution_profile` + `script_host::set_profile` отвечают на вопрос «куда уходят часы и что из этого
вообще может уехать на устройство». Включается флагом (`--profile` у GN01/GN02/GN03), потому что
стоит двух отметок времени на вызов; выключенный не стоит ничего.

Шаг меряется целиком, вызов — вокруг диспатча, **разница между ними это КОМПОЗИЦИЯ** (lua вне
вызовов). Мерится ВЕЛИЧИНА, а не признак: считать «сколько вызовов подходят по апертуре» бессмысленно
— сто дешёвых `fill` и один `graph_flood` дают одинаковый счёт и противоположный ответ.

Причина, по которой вызов не уедет, называется поимённо, потому что это четыре РАЗНЫЕ работы:

| Класс | Что означает | Чем закрывается |
|---|---|---|
| `ready` | апертура пускается, тело есть | ничем, готово |
| `no_body` | апертура пускается, тела нет | написать тело (сегодня их 25 из 46) |
| `narrow` | род не подходит вызову: широкое целое под телом против `float` | объявить тело кинд-агностичным или сменить род |
| `refused` | апертура не переносится по построению | другим алгоритмом |

**ПАМЯТЬ: ОБЪЯВЛЕННОЕ ПРОТИВ ЗАНЯТОГО.** Библиотека обещает, что генератор умеет назвать свою
стоимость по памяти до запуска, — и обещание проверяется, а не подразумевается. Инструмент объявляет
свою ВРЕМЕННУЮ стоимость (`tool_description::footprint`, функция от вызова: размер таблиц зависит от
числа элементов и параметров), а учёт складывает её с объявленными буферами и сравнивает с ПИКОМ
процесса (`utils::peak_resident_bytes`).

Ключевое правило: **«ничего» и «неизвестно» — разные ответы.** Инструмент, которому нечего объявлять,
объявляет это явно (`no_temporary_memory`); молчание означает НЕИЗВЕСТНО, и такие вызовы отчёт
называет поимённо. Отношение печатается в обе стороны: «не разложено», когда объявленного меньше пика,
и «объявлено с запасом», когда больше (оценки временных таблиц верхние — занижать стоимость памяти
нельзя, а завышать можно, если сказать вслух).

**ГОДНОСТЬ НЕ РАВНА ПЕРЕНОСИМОСТИ.** Окупается не вызов, а ЦЕПОЧКА: измеренный порог переноса — два-три
прохода, поэтому учёт считает ПРОГОНЫ (подряд идущие годные вызовы одного шага; объявленная очередь
считается своими проходами, она уже цепочка). Отсюда же правильная валюта для охвата: недостающее тело
стоит не своей доли, а того, что оно РВЁТ прогон — учёт печатает обе величины.

Заодно считается то, что даст резидентность между вызовами: передача «по вызову» (как сегодня, каждая
очередь заливает и скачивает своё) против объединения по прогону.

Числа по трём настоящим генераторам — в `ORIGINATOR_GPGPU.md` §5 п.0 и §11. Коротко: после расширения
родов и семи новых тел годная работа В ПРОГОНАХ выросла у GN01 с `0%` до `20.3%`, у GN02 с `1.8%` до
`22.4%`, у GN03 держится на `51%`. Осталась упираться в ШУМ: у всех трёх главный оставшийся `no_body` —
FastNoise2. У планеты сверх того `46%` апертуры (заливки по графу) и `19%` композиции в lua, которые не
переносит никакой перенос.

## Границы уровней исполнения

| Уровень | Кто | Для чего | нс/элемент, 1 поток | нс/элемент, 11 потоков |
|---|---|---|---|---|
| 0 | нативный инструмент | шум, размытие, свёртки, сегментация | 5.88 | 2.04 |
| 1 | `devils_script` | семантика, которую нужно моддить без C++ | 87.96 | 17.29 |
| 2 | lua | композиция внутри шага, небольшие множества | 119.36 | нет пути |

GN01, `4 194 304` элемента, Release; уровни 1 и 2 — одно и то же правило. Пороги из конфига стоят 51%
против литералов в скрипте (`87.96` против `64.12`).

**Выигрыш `ds` перед lua не в скорости интерпретации** — в один поток разница двукратная. Значение
имеет другое: `ds` РАСПАРАЛЛЕЛИВАЕТСЯ (сравнивать надо `8.69` против `108.12`), проверяется по типам
на разборе и остаётся единственным языком симуляции проекта. Цена против нативного ядра — примерно
12-кратная: это плата за моддинг без перекомпиляции, и арифметику внутреннего цикла туда выносить не
нужно.

**Правило для lua не «не трогает данные», а: lua обходит только те множества, которые сама
перечислила.** 4 млн элементов из lua — `501` мс, 4 тысячи провинций — `0.48` мс. Расставить `1024`
позиции сайтов поэлементно совершенно нормально.

## Окружение lua и бюджет тела шага

Стейт lua у генератора СВОЙ, а не общий с `visage`: тело шага адресуется к буферам на миллионы
элементов, UI-скрипт — к кадру, а детерминизм здесь часть контракта.

Видно телу шага: `step` (имя, индекс, оба зерна, ключ чанка, параметры, `reads`/`writes`, `programs`),
таблица `originator`, таблица `base` и `coroutine`/`string`/`table`/`math`/`utf8`. Не видно: файловой
системы, `os`, `package`, `require`, `load`/`dofile`, `debug`, `math.random`. Из отсутствия `require`
следует, что помощник, нужный двум телам шагов, ДУБЛИРУЕТСЯ — это норма, а не пробел.

`base` — базовые функции движка (`base.prng64_2`, `base.prng64_normalize`, `base.value`/`base.dice`,
упаковка): **один хеш на весь движок.** Пока каждое тело держало свой splitmix, «то же зерно»
означало «то же зерно в этом файле», и генератор с симуляцией считали по-разному. Ради этого базовые
функции вынесены в `bindings_base` — генератор считает планету headless и тянуть visage не должен. Две
функции таблицы телу шага противопоказаны: `base.perf` и `base.script_stack` — диагностика.

Whitelist проверяется при создании хоста: пропажа ядра списка (`assert`, `error`, `pcall`, `type`,
`tostring`, `tonumber`, `pairs`, `ipairs`) или пустая стандартная библиотека — громкая ошибка. Так
нашлось, что весь список раньше НЕ работал: ключ `std::string_view` в проксировании sol2 молча
промахивался, и функции оседали в окружении как `nil`, чего по результату генерации не видно.

| Бюджет | По умолчанию | Что измеряет |
|---|---|---|
| `instruction_limit` | `200 000 000` | инструкции **lua**; время внутри нативного инструмента не считается |
| `wall_time_us` | `0` (выключен) | стенные часы тела шага целиком |

По умолчанию ограничение идёт по инструкциям, потому что эти величины измеряют разное: счётчик растёт
только пока исполняется lua, поэтому ловит цикл в скрипте и не срабатывает на честном шаге, который
час считает шум в нативном ядре. Шаг счётчика хуков выводится из лимита (`min(лимит, 10000)`) — иначе
маленький бюджет был бы тихо бесконечным. Исчерпание бюджета ОТМЕЧАЕТСЯ ФЛАГОМ и проверяется после
возврата из тела: `pcall` из окружения не убрать, а шаг, доевший бюджет, провален, даже если сам себя
простил.

## Решения списком

Факты, которые иначе приходится выяснять чтением кода:

- **Параллельность выводится из апертуры**, а не сообщается скриптом: скрипт её не знает.
- **Размер буфера — имя константы**, а не число: стоимость по памяти обязана быть названа до запуска.
- **Форма буфера объявляется вместо размера** и читается инструментом у привязки; два источника одной
  истины однажды разъезжаются.
- **Позиции приходят ПОЛЕМ**, а не выводятся из шага решётки: инструмент не знает ни про чанки, ни про
  шаг, и второго мнения о том, где лежит клетка, не заводится.
- **Состояние между шагами — обычный буфер с `size = 1`**, а не отдельный механизм; из него же растёт
  выход переменной длины и `dispatchIndirect`.
- **Превышение ёмкости зажимается, а не отклоняется** (в шейдере бросить нечем), но факт зажима едет
  наружу отчётом.
- **Зерно шага — хеш имени**, а не позиция в потоке случайности: перестановка шага не сдвигает
  случайность остальных.
- **Два зерна с разными контрактами:** `seed` непрерывен через шов чанка, `chunk_seed` независим.
- **Носитель ключа объявляется** — единственное место, где контракт не выводится; молчание означает
  отказ.
- **Где считается очередь — объявление конфига**, а не свойство машины: иначе мир менялся бы от
  железа.
- **`run_script` принимает только `ds`**, никогда готовый шейдер: решает, что считается, автор данных,
  а проверки и перевод — движка.
- **Шапка push-константы одна** на нативные тела и на переводы; зерно лежит в ней же.
- **Быстрый путь требует совпадения РОДА, а не размера:** `span<float>` над `ui1` писал бы биты float.
- **Копия буфера копирует данные от начала до начала:** у копии своё выравнивание, и копия вектора
  оставила бы её читать со сдвигом (а с копией сырого указателя — вовсе из чужой памяти).
- **Равенство у `ds` — сравнение с допуском**, и перевод повторяет ту же константу.
- **Свёртки разбиваются фиксированно** и объединяются в порядке чанков: сумма float не зависит от
  числа потоков.
- **Соседство симметризуется**, у заливки отдельный вход проходимости, строка метки лежит по индексу,
  равному метке.
- **Таблица marching cubes выводится**, а не списывается; проверяется поверхность по направленным
  рёбрам.
- **Минимальный знаменатель `ratio` обязателен буквально:** молчаливый ноль у поля плотности означал
  бы стену в дырке покрытия.
- **Вес решателя — предпочтение при выборе**, а не частота в результате.
- **Случайность на устройстве — свой поток**, не равный CPU (соль ds живёт в скомпилированном
  контейнере, хеш на GPU 32-битный).
- **Библиотека не тянет lua, `ds`, `demiurg` и Vulkan в ядро:** каждый из них живёт своей целью
  сборки.

## Чего пока нет

- эрозия, watershed, сплайновые коридоры;
- порядко-независимый `accumulate` на фиксированной точке и проверка определённости по полосе
  перекрытия — обе формы известны, но без потребителя проектировать их нечестно;
- слияние программ `ds` в группу с нативными вызовами (нужен свой `prepared_call`);
- чанковая генерация у решателя ограничений: ограничения пересекают границу чанка;
- запечатывание СГЕНЕРИРОВАННОГО пакета на диск и чтение его штатным `demiurg`-ресурсом — что считать
  картой и как устроена связность внутри уровня, решает проект; движок может дать шаблон, а не формат.
