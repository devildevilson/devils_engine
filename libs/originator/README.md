# originator

`libs/originator` — каркас процедурных генераторов: типизированные буферы, шаги, объявленные в
конфиге, и lua в роли программируемой команды шага.

Библиотека не описывает мир. Она описывает, **как устроен генератор**: что течёт между шагами, кто
имеет право это писать, и почему результат воспроизводится. Конкретный мир — планета, подземелье,
подводные чанки — принадлежит проекту.

Это реализация контракта генераторов из `ROADMAP_ULT.md` §6 и задач `GEN-01`…`GEN-13`.

## Три сущности

| Сущность | Что это | Аналог в painter |
|---|---|---|
| `buffer` | плотный массив элементов с именованными полями и явной раскладкой | `resource` |
| `step` | объявленная единица работы с привязками `reads`/`writes` | `step` |
| тело шага | lua-функция, дирижирующая одним куплетом генерации | `material` |

Пайплайн лежит в конфиге (`tavl`), а не в скрипте. Из привязок шага выводится всё остальное — ровно
как painter выводит барьеры из биндингов, а не из ручного списка:

- порядок и зависимости шагов;
- что доступно потребителю после шага N (это ровно `writes`);
- изменяемость вью, которое получит тело шага;
- громкий отказ до исполнения, если шаг читает то, чего никто не писал.

## Буферы

```tavl
{
  name = cells
  format = [ height = v1, moisture = v1, smoothed = v1, biome = ub1 ]
  layout = soa
  size = cell_count
}
```

Поле пишется ОПЕРАТОРОМ (`height = v1`), а не кортежем (`(height, v1)`): в документе-схеме лишние
скобки ничего не сообщают, а строка с оператором читается как строка таблицы. Разбору всё равно — и
это ключевое свойство, а не совпадение: строка с оператором это та же ПАРА, что и строка в скобках,
потому что чтение пары пропускает операторные лексемы между слотами. Поэтому **оба написания
валидны**, и формат можно переводить файл за файлом.

Просилось здесь двоеточие (`height : v1`), и именно так формат и будет выглядеть: `:` не входило в
`operator_chars` самого `tavl`, поэтому зарегистрировать его было нельзя. Правка в `tavl` готова
(двоеточие добавлено в набор, датавремя от этого не страдает — оно распознаётся до операторов, и на
это есть тест), и после её релиза формат переводится одной строкой: достаточно зарегистрировать
оператор в `parse_buffers`, а документы примут любое из трёх написаний.

Написание типа повторяет painter: `<род><число компонент>`. Отличие одно — поля **именованы**,
потому что по этим именам к ним обращаются и lua, и `devils_script`.

| Род | Хранение | Род | Хранение |
|---|---|---|---|
| `v` | float32 | `i` | int32 |
| `sf` | float16 | `is` | int16 |
| `ui` | uint32 | `ib` | int8 |
| `us` | uint16 | `c` | uint8, значение 0..1 |
| `ub` | uint8 | | |

Размер задаётся **именем константы**, а не числом: генератор обязан уметь назвать свою стоимость по
памяти до запуска, и одно имя связывает буферы одного масштаба.

`layout` выбирает `aos` (элемент лежит целиком) или `soa` (один непрерывный план на поле). Это
свойство **хранения**, а не контракта: имя поля разрешается в пару (смещение, шаг) один раз, поэтому
ни lua, ни `devils_script` разницы не видят. Раскладку можно переключить в конфиге и померить, не
тронув ни одной строки скрипта. При `soa` поле лежит подряд и уходит в ядро как `span`, при `aos` —
с шагом элемента.

Переиспользование буферов — решение скрипта: `view:clear()` есть, автоматического наложения времени
жизни нет. Потребление памяти равно сумме объявленного и видно в конфиге глазами.

## Точка входа

Генератор называется ОДНИМ именем. До точки входа хост обязан был знать имена трёх файлов — то есть
знать устройство чужого генератора, — а мод, который приносит свой, назвать эти файлы иначе уже не
мог. Теперь устройство знает сам генератор:

```tavl
name = planet

values  = ./values.tavl
buffers = ./buffers.tavl

steps = [
  {
    name = topology
    body = ./scripts/S01_topology.lua
    writes = [ cells, cell_offsets, cell_arcs ]
  }
  ...
]
```

Всё, что здесь написано — **demiurg-id**: путь от корня модуля без расширения. Расширение в примере
оставлено для глаза, разбор его снимает; путь, начатый с точки, считается от папки самой точки входа,
а любой другой — от корня модуля (то же правило, что у `require` в lua). Один перевод на весь движок
живёт в `demiurg::absolute_resource_path`, и второго здесь заведено не было.

Шаги лежат ВНУТРИ документа, в `steps = [ ... ]`, а не блоками верхнего уровня, и это не оформление.
`tavl` читает документ либо как одну структуру, либо как список значений; строка `values = ...` рядом
с блоком `{ ... }` делает документ структурой, у которой все блоки становятся её лишними значениями.
Отказа при этом не было: документ просто читался не тем обходом. Теперь форма документа
классифицируется ДО разбора, и обе путаницы — строка в списке шагов и голый список вместо точки
входа — отклоняются с именем документа.

Ещё одно правило того же рода: в файле точки входа не должно быть отделителей `//---`. `demiurg`
раскладывает такой файл на суб-ресурсы `путь:имя`, и id без хвоста перестаёт существовать вовсе —
ошибка выглядит как опечатка в пути, хотя файл лежит на месте. Поэтому она называется вслух.

Собирает всё это `load_generator(resources, "generator/planet")`: читает точку входа, разрешает
ссылки, разбирает значения, диапазоны и буферы и отдаёт `generator_config` — описание пайплайна плюс
тексты всех скриптов, уже разложенные по абсолютным id. Дальше `script_host` получает текст, а не
файл: хост скриптов не должен уметь ходить за файлами.

Хосту, которому понадобился скрипт ВНЕ пайплайна, есть `read_generator_source(resources, id)`.
Понадобилось это сразу: перф-стенд GN01 гоняет одно и то же правило на двух уровнях исполнения, и
lua-двойник правила шагом не является — значит точка входа его и не называет, и правильно не называет.

Тип ресурса регистрируется одной строкой, `register_generator_resources(resources)`, и по контракту
`demiurg` имя типа обязано быть СЕГМЕНТОМ пути — значит файлы генератора лежат под `generator/`
внутри модуля. Все три расширения (`tavl`, `lua`, `ds`) — один тип, потому что тип отвечает на вопрос
«чей это файл», а что в нём написано, говорит точка входа.

## Общие значения пайплайна

Число, нужное нескольким шагам, объявляется один раз в отдельном документе, а не дублируется:

```tavl
{
  numbers = { sea_level = 0.5, dry = 0.35, wet = 0.65, features = 5 }
  strings = { tree = "DQkGDA==" }
}
```

Шаг видит их среди своих параметров и может переопределить своим `params`. Смысл ровно в том, чтобы
порог, который читают и нативное ядро, и правило на `devils_script`, и подсчёт итогов, жил в одном
месте: продублированный в трёх местах он однажды разъедется, и три уровня исполнения начнут считать
разное, а заметить это будет почти нечем.

Рядом с числом можно объявить, в каких границах и с каким шагом его осмысленно крутить:

```tavl
ranges = {
  land_target = [0.10, 0.60, 0.01]
  continent_count = [3, 16, 1]
}
```

`parse_value_ranges` отдаёт это хосту, и хост строит настройки генератора, **ничего не зная о смысле
числа**: он не может ни вывести значение за границы, ни сойти с сетки шага (`value_range::advance`
считает позицию в шагах от минимума, поэтому повторные «плюс-минус» не оставляют дробного хвоста).
Значение без объявленного диапазона просто не настраивается — правильный ответ по умолчанию, потому что
у большинства чисел мира есть область осмысленных значений, за которой генератор не ломается, а даёт
бессмыслицу, и знает эту границу автор мира, а не окно.

## Шаги

```tavl
{
  name = climate
  body = scripts/climate.lua
  writes = [ cells ]
  params = { radius = 2, sea_level = 0.5 }
}
```

Буфер в `writes` доступен своему шагу и на чтение, поэтому повторять его в `reads` нельзя — это
ошибка конфига. Состояние между шагами («сколько всего получилось») — обычный буфер с `size = 1`, а
не отдельный механизм.

Зерно шага — `hash(зерно пайплайна, имя шага)`, а не позиция в потоке случайности. Перестановка или
перезапуск одного шага не сдвигает случайность остальных.

## Апертуры: параллельность выводится, а не сообщается

Скрипт **не говорит** движку, что вызов можно распараллелить: он этого не знает. Апертуру объявляет
инструмент, и из неё вместе с фактическими привязками выводится способ исполнения.

| Апертура | Что делает | Условие параллельности |
|---|---|---|
| `pointwise` | читает и пишет свой элемент | всегда; источник и приёмник могут совпадать |
| `gather` | читает произвольные элементы, пишет свой | **источник ≠ приёмник**, иначе отказ |
| `scatter` | пишет по чужим индексам | только готовым инструментам с собственным детерминизмом |
| `reduce` | много → одно | всегда, с фиксированным разбиением на чанки |
| `sequential` | порядок значим | никогда |

Нарушение по возможности не ловится, а **не выражается**. Вью на чтение и вью на запись — разные
типы: у первого нет операции записи. Поэтому соседа неоткуда прочитать, кроме как из источника, а
источник в этом проходе никто не пишет. Оставшийся случай — gather, у которого источник и приёмник
совпадают, — отклоняется `check_dispatch` до исполнения, с именами шага, инструмента и поля.

Свёртки разбиваются на чанки **фиксированного** размера, а объединяются строго в порядке чанков,
поэтому сумма плавающих чисел не зависит от числа потоков.

Апертура определяет и то, **к чему относится диапазон**, и это не косметика: у `pointwise`/`reduce` —
и к входам, и к выходам; у `gather` — только к выходам, потому что входы читаются целиком, там и
лежат соседи; у `scatter` — только ко входам, потому что выход это ДРУГАЯ структура, и её размер
задаёт число групп, а не число обрабатываемых элементов.

## Инструменты ядра

Живут в `devils_engine::originator` и не требуют внешних зависимостей.

| Инструмент | Апертура | Что делает |
|---|---|---|
| `fill` | `pointwise` | константа во все компоненты поля |
| `position_grid` | `pointwise` | мировые позиции регулярной сетки в поле `v2`/`v3` |
| `value_noise` | `pointwise` | простой value noise на хеше, 2D-сетка |
| `index` | `pointwise` | порядковый номер элемента как значение: `i * scale + offset` |
| `remap` | `pointwise` | `значение * scale + offset` с ограничением; `absolute` берёт модуль до умножения; `component` выбирает компоненту источника; источник и приёмник могут совпадать |
| `classify` | `pointwise` | пороговая классификация по двум полям |
| `box_blur` | `gather` | усреднение по окну; приёмник обязан отличаться от источника |
| `reduce_min` / `reduce_max` / `reduce_sum` / `reduce_count_above` | `reduce` | свёртки с фиксированным разбиением |
| `blend` | `pointwise` | `a * x + b * y + offset` с ограничением: сложить два поля |
| `modulate` | `pointwise` | `scale * x * y + offset`: величина под маской |
| `ratio` | `pointwise` | `scale * x / y + offset` с ОБЯЗАТЕЛЬНЫМ минимальным знаменателем |
| `decay` | `pointwise` | `offset + amplitude * exp(-x / width)`: спад по расстоянию |
| `maximum` / `minimum` | `pointwise` | побольше и поменьше из двух полей |
| `group_by` | `scatter` | ключ → CSR из смещений групп и индексов элементов |
| `accumulate` | `scatter` | ключ и значение → суммы по корзинам |

Тройка `blend`/`modulate`/`decay` появилась в GN02 и выглядит мелочью, но без неё правила в конфиге не
собираются: программа на `devils_script` возвращает ОДНО значение в ОДНО поле, а вызов функции в этой
версии `ds` не является операндом выражения. Значит сложить два слагаемых, ограничить величину маской
и посчитать экспоненциальный спад нечем — а из этих трёх операций состоит почти любая мировая формула.
Разделение получилось правильным: движок считает арифметику, конфиг остаётся местом, где слагаемые
складываются, то есть где живёт смысл.

Остальное того же набора приехало из второго захода на рельеф GN02, и каждое закрывает свою дыру:

- `maximum`/`minimum` — там, где два слоя НАКЛАДЫВАЮТСЯ, а не складываются. Остров посреди океана
  поднимается над дном, а не прибавляется к спадающему материковому конусу; сумма делала его тем ниже,
  чем дальше от материка. Тем же выражается объединение масок: сумма с обрезкой по единице ведёт себя
  как максимум только пока слагаемые не перекрываются.
- `absolute` у `remap` — без модуля не выражается складчатый (ridged) шум, а это единственный дешёвый
  способ получить хребет с ИЗЛОМОМ: у обычного шума гребень круглый, у свёрнутого излом ровно там, где
  значение проходит ноль.
- `graph_slope` — средний модуль разности со всеми соседями. Отличается от «отклонения от размытого»
  ровно тем, ради чего заведён: наклонная ПЛОСКОСТЬ от своего размытия почти не отклоняется, поэтому
  по отклонению ровное нагорье и ровный склон неразличимы. Величина выходит в единицах поля НА ШАГ
  РЕШЁТКИ; приводить её к расстоянию — дело вызывающего, который один и знает шаг своей решётки.
- `component` у `remap` — какую компоненту источника читать. Заведён потому, что правило на
  `devils_script` компоненту вектора достать НЕ МОЖЕТ (у планеты из-за этого широта приезжала
  отдельным полем `lat_sin`), а объёму она нужна на каждом шаге: вертикальный градиент плотности —
  это высота, то есть вторая компонента поля позиций. Инструмент, умеющий читать только нулевую
  компоненту, оставлял бы единственным выходом копию поля позиций тремя скалярами.
- `ratio` — деление одного поля на другое, заведённое НОРМИРОВКОЙ: взвешенное среднее это сумма
  произведений, делённая на сумму весов, и без деления оно не выражается вовсе. Первый потребитель —
  смешивание правил генерации (биомы GN03), но нормировка нужна любому среднему, поэтому инструмент
  общий. Минимальный знаменатель здесь ОБЯЗАТЕЛЕН БУКВАЛЬНО — без него инструмент отказывается, а не
  берёт что-нибудь маленькое: нулевая сумма весов означает «ни одно правило здесь не действует», и
  решать, что отвечать в этом месте, — дело автора конфига, а не движка. Молча вернуть ноль было бы
  худшим ответом: у поля плотности ноль это ПОВЕРХНОСТЬ, то есть в дырке покрытия появилась бы стена.
  (Сначала у параметра было значение по умолчанию `1e-9`, и документация при этом называла его
  обязательным — расхождение нашёл закрывающий аудит GN03.)
- `index` — порядковый номер элемента как данные. Выглядит бессмысленно, пока не понадобится заливка,
  которая несёт не признак «здесь граница», а НОМЕР клетки границы: с признаком заливка отвечает
  только «далеко ли до границы», и всё, что у той границы происходит, остаётся недоступным. Номер
  превращает косвенность в данные, а читает её дальше `lookup`. В GN02 на этом стояла настоящая ошибка
  модели — см. README площадки.

Параметры инструментов принимают из lua и БУЛЕВЫ значения (`absolute = true`). Проверка на bool идёт
последней, после числа и строки: у числа `lua_toboolean` тоже истинен, и порядок здесь единственное,
что не даёт единице приехать булевым. Без этой ветки флаг молча пропадал бы — параметр не число и не
строка, значит его просто нет, и инструмент брал бы значение по умолчанию, ничего не сообщая.

## Замкнутая поверхность и граф соседства

Отдельный набор `add_graph_tools()`, и он отдельный потому, что это ДРУГОЙ способ адресовать
пространство. У сферы нет плоскости: нет окна растра, нет края карты, нет строки. Любая развёртка даёт
шов, то есть место, где соседство считается неверно и притом молча. Поэтому адрес поверхности —
направление, соседство — данные (CSR), и всякий пространственный проход выражается через соседство.

| Инструмент | Апертура | Что делает |
|---|---|---|
| `sphere_points` | `pointwise` | равнораспределённая решётка Фибоначчи на сфере; ось — параметр |
| `sphere_adjacency` | `scatter` | K ближайших, СИММЕТРИЗОВАННЫЕ в канонический CSR |
| `graph_blur` | `gather` | усреднение по соседям: замена `box_blur` там, где окна растра нет |
| `graph_frontier` | `gather` | «есть ли сосед с другой меткой»: граница как свойство графа |
| `graph_flood` | `sequential` | заливка от нескольких источников по стоимости и ПРОХОДИМОСТИ |
| `graph_slope` | `gather` | средний модуль разности со всеми соседями: настоящий уклон |
| `graph_vote` | `gather` | пустая клетка перенимает метку сильнейшего соседа |
| `poisson_seeds` | `sequential` | затравки под маской, разнесённые не ближе `min_distance` |
| `lookup` | `gather` | значение из другого буфера по индексу в поле (`offset` для метк с единицы) |
| `connected_components` | `sequential` | связные куски подграфа под маской, нумерация плотная |
| `label_adjacency` | `scatter` | CSR по МЕТКАМ, собранный из CSR по элементам |

Последние два появились от задачи, которая поклеточной меткой не выражается вовсе — иерархия названных
мест на планете:

- `connected_components` отвечает на вопрос про СВЯЗНОСТЬ. Метка «суша» есть у каждой клетки суши, но
  того, что Евразия и Америка это два разных куска, в ней нет: чтобы узнать это, надо обойти граф.
  Верхний уровень любой географической иерархии — всегда связный кусок, а не значение поля. Куски
  мельче `min_size` получают ноль, и нумерация после отбрасывания остаётся ПЛОТНОЙ: дырка в номерах
  сломала бы `group_by`, для которого номер — это индекс корзины.
- `label_adjacency` отвечает на вопрос «кто чей сосед» на уровне ОБЛАСТЕЙ, и без него нельзя вырастить
  область из областей так, чтобы её граница совпала с границами исходных. Если растить историческую
  область заливкой по клеткам, её граница ляжет посреди провинции и разрежет провинцию на части.
  Правильный способ один: собрать граф соседства провинций и растить по НЕМУ, а клетка получает свою
  область через `lookup` по номеру провинции — тогда совпадение границ не проверяется, а выполняется
  по построению. Граф выходит симметричным сам: соседство элементов симметрично, а метка соседа не
  зависит от того, с какой стороны смотреть на дугу.

**Строка метки лежит по индексу, равному МЕТКЕ**, а строка 0 всегда пуста. Соглашение то же, что у
`group_by` и `accumulate`: корзина равна сырому значению ключа, а ключ 0 означает «метки нет». Один
индекс на все таблицы областей — иначе запись области, её суммы и её строка соседства расходятся, и
расхождение это ничем не ловится, потому что все три буфера остаются валидными. В GN02 на этом стояла
настоящая ошибка: скрипт писал центр и размер области по «метка минус один», а суммы приходили по
метке, и запись склеивала две разных области (см. README площадки).

Решётка Фибоначчи выбрана за одно свойство: площадь клетки почти одинакова по всей поверхности,
поэтому «площадь = 4πR²/N» верно с точностью до процентов и любая сумма по клеткам считается **без
весов**. У широтно-долготной сетки это неверно грубо, у кубосферы — умеренно, но с шестью швами.

Два контракта, которые стоит знать до использования:

- **соседство симметризуется.** Если `i` считает `j` соседом, то и `j` считает соседом `i`.
  Асимметричный граф даёт ошибки, которые проявляются через несколько шагов (заливка идёт в одну
  сторону, размытие усредняет не то) и почти не находятся по результату.
- **у заливки отдельный вход проходимости, а не только стоимость.** Дорогая цена и запрет — разные
  вещи: область, залитая через непроходимое место «по дорогой цене», получается РАЗОРВАННОЙ, и заметно
  это становится только на отрисовке границы. Непроходимая клетка не входит в очередь вовсе, поэтому
  область связна по построению.

`graph_flood` и `graph_vote` отвечают на разные вопросы, и подменять их друг другом не стоит: заливка
это «кто ближе» (один проход, геометрия), голосование — «кто напористее» (много проходов, и между
проходами вес меняется). Расселение культуры — второе, административное деление — первое.

`poisson_seeds` гасит кандидатов **по прямой**, а проходимость у заливки идёт **по графу**, и это
несовпадение надо держать в голове: замкнутое море рядом с океаном может остаться без затравки, потому
что его погасила затравка по другую сторону перешейка. GN02 закрывает это добором с соседским шагом.

`value_noise` существует не как конкурент FastNoise2, а потому что примитивы — **отдельная цель
сборки**: потребителю, которому нужно детерминированное поле без внешних зависимостей, нужно чем-то
его получить. Для настоящей генерации берётся `noise_grid`/`noise_at`.

## Объёмные инструменты: выход ПЕРЕМЕННОЙ длины

Отдельный набор `add_volume_tools()`, и он отдельный не по зависимостям (их нет), а по контракту: это
первый инструмент библиотеки, у которого длина выхода не равна длине входа и не известна до
исполнения. Сколько треугольников даст поле плотности, знает только само поле.

| Инструмент | Апертура | Что делает |
|---|---|---|
| `marching_cubes` | `scatter` | поверхность нулевого уровня поля плотности треугольниками |
| `polyline_distance` | `gather` | расстояние до набора ломаных (CSR цепочек) с отсечением по прямоугольнику |

У `polyline_distance` параметр `max_distance` ОБЯЗАТЕЛЕН, и это про смысл, а не про оформление: он
значит две вещи сразу — насколько широко смотреть (поле отсечения вокруг отрезка) и что отвечать там,
где ломаной рядом нет. Пока у него было значение по умолчанию, эти два смысла разъезжались: подготовка
брала `0`, тело `1e9`, и вызов без параметра давал поле, у которого почти везде миллиард, а внутри
прямоугольника отрезка настоящее расстояние. Разрыв в поле плотности выглядит как стена посреди мира.

У `polyline_distance` есть параметр `metric`, и он задаёт не точность, а ФОРМУ СЕЧЕНИЯ коридора:
евклидова метрика даёт круглую трубу (естественная пещера), чебышёвская — угловатую (тоннель бункера),
потому что поверхность уровня у неё куб. Замер идёт от ближайшей точки, найденной в евклидовой
метрике: у отрезка вдоль оси ответ точен, у наклонного сечение слегка скошено, и эта скошенность
читается как «прорублено не идеально», то есть как признак рукотворности.

`polyline_distance` — это то, чем двухмасштабный генератор превращает МАРШРУТ грубого прохода в поле:
«насколько эта точка близка к маршруту». Дальше конфиг делает из расстояния что угодно — вычитает
коридор из плотности, поднимает насыпь, увлажняет пойму.

Кривую движок НЕ знает, и это решение: Безье, Катмулл-Ром, дуги — их много, они разные, и все они
распрямляются в ломаную ОДИН раз на грубом масштабе, где точек сотни, а не миллионы. Густота
распрямления остаётся решением того, кто строил маршрут: она и есть гладкость результата. Отсечение по
охватывающему прямоугольнику отрезка — не оптимизация, а условие применимости: без него цена элемента
равна числу отрезков во всём мире, а с ним — числу отрезков рядом, то есть обычно нулю. Проекция на
отрезок ЗАЖИМАЕТСЯ в его концы: без зажима «расстояние до прямой» продолжает коридор за конец
маршрута, то есть строит тоннель в никуда.

Входов два — плотность (`v1`) и позиции узлов (`v3`), выходов три — позиция вершины, нормаль вершины и
поле, куда пишется ЧИСЛО вершин. Параметры: `size_x`/`size_y`/`size_z` (решётка отсчётов), `iso`
(порог) и `border` (сколько узлов с каждой стороны исключить из обхода клеток).

Позиции приходят ПОЛЕМ, а не выводятся из размера клетки: инструмент не знает ни про чанки, ни про
шаг решётки, и по той же причине, по которой их не знает `position_grid`. Заодно это единственный
способ дать ему регулярную сетку, посчитанную кем-то другим, не заводя второго мнения о том, где
лежит клетка (i, j, k).

**Нового механизма под переменную длину не появилось, и это главное.** Хватило трёх вещей, которые
уже были: ёмкость объявлена размером буфера, занятая длина приезжает обычным буфером на один элемент
(«состояние между шагами — обычный буфер с `size = 1`», см. «Шаги»), а переполнение — громкий отказ с
именем буфера и двумя числами. Не обрезка: обрезанная поверхность выглядит как дырка в мире, и по
картинке её причину не найти.

**Детерминизм даёт не апертура, а схема** — та же, из которой сделаны `group_by` и `accumulate`: три
фазы с фиксированным разбиением (случай куба по клеткам, префиксная сумма в порядке клеток, запись
каждой клеткой своего заранее вычисленного отрезка). Поэтому результат побитово один и тот же при
любом числе потоков, и это проверено тестом.

**Носитель ключа здесь `chunk_local`** — первый честный в проекте: группа это список вершин одного
прохода, и чанк заканчивает его сам. Объявляет это, как и положено, автор пайплайна.

**Таблица случаев ВЫВОДИТСЯ, а не переписывается.** Канонические 256 строк по 16 чисел — данные,
которые можно списать с опечаткой, и одна неверная строка означает дырку в поверхности при одном
сочетании знаков: баг, который видно раз в сотню чанков. Поэтому таблица строится из правила
соединения на грани куба, а правило это функция ТОЛЬКО четырёх знаков самой грани — значит два
соседних куба видят общую грань одинаково, и непрерывность поверхности получается по построению, а не
по совпадению. Ориентация выводится оттуда же: отрезок направлен так, чтобы плотная часть грани
оставалась справа при взгляде снаружи, поэтому нормаль треугольника смотрит в сторону убывания
плотности.

Что здесь стоит знать про ПРОВЕРКУ такой поверхности: критерий «каждое ребро принадлежит ровно двум
треугольникам» НЕВЕРЕН. На неоднозначной грани поверхность законно касается сама себя вдоль отрезка,
и такое ребро встречается четырьмя. Правильный критерий — по НАПРАВЛЕННЫМ рёбрам: число проходов
вперёд равно числу проходов назад. Дырка тогда непарна, вывернутый треугольник даёт два прохода в одну
сторону, а касание двух листов проходит. Измерено на шумовом поле, где встречаются все 256 случаев:
незакрытых рёбер `0`, касаний `74` из `20752`.

Нормаль считается центральной разностью плотности, поэтому чанковому проходу нужна полоса перекрытия
шириной ОДИН узел (`border = 1`): без неё вершины на шве совпадают точно (они считаются из одной пары
узлов), а нормали нет, и шов виден полосой другого оттенка. С ней чанки складываются в целое
побитово — измерено на паре чанков против одного прохода по обоим.

## Быстрый путь доступа к полю

Нативное ядро может взять поле как `span` и обработать векторно — но только когда C++-тип **точно**
совпадает с родом хранения и поле однокомпонентное. Сверять один размер нельзя, и это не теория:
`ui1` и `v1` оба четырёхбайтовые, и `span<float>` над полем, объявленным сырым `uint32`, молча писал
бы туда биты float — значение читалось обратно как `1061158912` вместо `0.75`. Теперь такой `span`
приходит пустым, и инструмент честно уходит на путь через аксессор.

Роды без точного C++-типа — `sf` (половинная точность) и `c` (нормализованный байт) — быстрого пути
не имеют вовсе: к ним обращаются только через аксессор, который делает преобразование.

## Scatter: почему он только у готовых инструментов

Произвольного параллельного разброса по чужим индексам в originator нет и не будет. Детерминизм даёт
не апертура, а конкретный алгоритм, поэтому `scatter` — это не право, которое можно выдать любому
телу, а свойство двух готовых инструментов:

- **`group_by`** — ключ → CSR из смещений групп и индексов элементов. Три фазы: подсчёт по чанкам,
  префиксная сумма по паре (корзина, чанк), заполнение каждым чанком своего заранее вычисленного
  отрезка. Порядок внутри группы — по номеру чанка, затем по индексу элемента.
- **`accumulate`** — ключ и значение → суммы по корзинам. У каждого чанка приватный срез, слияние
  строго по номеру чанка.

Общий приём — **фиксированное** разбиение на чанки: от него зависит порядок результата, поэтому оно
не может зависеть от числа потоков. Обе схемы дают побитово одно и то же при любом раскладе
исполнения и параллелятся (измерено 4.6x и 4.2x на 11 потоках).

Инструменту `scatter` или `sequential` движок отдаёт пул: их работу он не разбивает, потому что
корректное разбиение зависит от алгоритма. Телу `pointwise`, `gather` или `reduce` пул не достаётся —
оно уже исполняется внутри чанка.

## Нативные примитивы: FastNoise2 и jc_voronoi

Живут отдельной целью `devils_engine::originator_primitives`. Контракт обычный: каждый примитив —
такой же инструмент с объявленной апертурой.

Граф шума — **данные конфига**, а не код: дерево узлов приходит закодированной строкой из редактора
FastNoise2.

```tavl
params  = { feature = 190, amplitude = 2.4, offset = 0.35 }
strings = { tree = "DQkGDA==" }
```

**РАЗМЕР ФОРМЫ ЗАДАЁТСЯ В МИРОВЫХ ЕДИНИЦАХ, а масштаб дерева ИЗМЕРЯЕТСЯ.** Это правило появилось из
ошибки, и ошибка была тихой. Частота — величина обратной размерности, и её перевод в метры зависит от
того, что стоит внутри дерева: доменный масштаб, число октав, множитель. У общего дерева движка период
оказался `91` единица координат, поэтому `frequency = 1/190` в расчёте «форма в 190 метров» дала форму
в **17 километров**: чанк в 32 метра видел поле ПОСТОЯННЫМ, мир получался пустым, и ни одна проверка не
падала — нашлось это только по диапазонам полей в отчёте.

Вывод не «умножать на 91», а «не предполагать масштаб чужих данных». Поэтому `prepare` измеряет период
сам: среднее расстояние между сменами знака вдоль наклонной линии (по одной оси линия проходит через
узлы решётки и даёт не тот масштаб), зерно для измерения — **всегда ноль**, потому что период обязан
быть свойством ДЕРЕВА, а не мира, иначе один и тот же `feature = 190` означал бы разные метры в разных
мирах. Результат кэшируется по тексту дерева: восемь тысяч выборок на каждый чанк были бы четвертью
стоимости самого шума.

`frequency` при этом остаётся, и у него свой смысл — «единиц шума на единицу мира». Он нужен там, где
мировая длина не имеет смысла: у планеты поле живёт на единичной сфере, и «190 метров» там не
величина. Задать оба сразу — громкая ошибка: одно из них обязано быть неверным.

Проверено тестом: при `feature` в `40`, `160` и `640` наблюдаемое расстояние между сменами знака
совпадает с запрошенным по порядку (допуск двукратный — период это СТАТИСТИКА дерева, а не точное
свойство; расхождение, которое ловится, было девяностократным).

| Инструмент | Апертура | Что делает |
|---|---|---|
| `noise_grid` | `pointwise` | регулярная 2D-сетка: элемент i → (i % width, i / width) |
| `noise_at` | `pointwise` | выборка в произвольных точках по полю позиций v2/v3 — единственный путь для объёма |

Про единицы у ОСТАЛЬНЫХ инструментов, чтобы не искать это по коду. Длину несут: `feature` у шума —
мировые единицы; `cell_size`/`origin_*` у `position_grid` — мировые; `radius` у `box_blur` и
`graph_blur` — ШАГИ РЕШЁТКИ, а не метры (окно считается по элементам); `width` у `decay` — те же
единицы, что у входного поля (обычно это расстояние заливки, то есть шаги графа); `graph_slope` отдаёт
единицы поля НА ШАГ РЕШЁТКИ, и приводить их к расстоянию — дело вызывающего, который один знает шаг
своей решётки. Всё остальное безразмерно.
| `voronoi_label` | `gather` | «какому сайту принадлежит клетка»: kd-запрос ближайшего, дерево строится подготовкой |
| `voronoi_adjacency` | `scatter` | «какие области соседствуют»: соседство из Делоне в канонический CSR |

Разметка и соседство — разные вопросы, и второе не выводится из первого: тонкая область может не
получить ни одной клетки растра, а две области могут коснуться по диагонали. Поэтому соседство берётся
из геометрии, а не угадывается по картинке.

`position_grid` (ядро, не примитивы — это чистая арифметика) заполняет поле **мировых позиций**
регулярной сетки: без него `noise_at` был неприменим, потому что заполнить его вход было нечем.
Раскладка индекса — `x` внутренний, затем `y`, затем `z`, как у `noise_grid` и у самого FastNoise2,
поэтому поле скармливается выборке без перестановки. Начало координат приходит **параметром**:
инструмент не знает про чанки, и перевод ключа чанка в мировое смещение остаётся в теле шага.

Измерено: `noise_grid` и `position_grid` + `noise_at` дают **побитово одинаковое** поле (`0` из
`65536` расхождений). Значит двумерную карту можно считать регулярной сеткой, а трёхмерные чанки
выборкой по позициям, и на стыке систем они сойдутся, а не «примерно совпадут».

**Две измеренные тонкости FastNoise2,** из-за которых обвязка и сборка выглядят именно так:

- `GenUniformGrid2D` накапливает позиции внутри строки. Полная строка бит в бит совпадает с одним
  большим вызовом, а отрезок с середины строки расходится примерно на `3e-07`. Поэтому `noise_grid`
  генерирует строку целиком независимо от того, где начался чанк. `GenPositionArray2D/3D` этой
  проблемы не имеет: позиции заданы явно.
- Набор SIMD-инструкций FastNoise2 выбирает в рантайме, и по умолчанию наборы расходятся: `max`
  против `SSE2` — `1.8e-07`, то есть один seed давал разные артефакты на разных машинах. Проект
  собирает FastNoise2 с **`FASTNOISE2_STRICT_FP`** — штатной опцией upstream, после которой выход
  всех наборов побитово одинаков. Измерено: расхождение стало ровно нулевым и на регулярной сетке, и
  на массиве позиций, а цена не различима на уровне пайплайна. Параметр `feature_set` после этого
  остаётся диагностическим.

## Входы пайплайна: то, что приходит от грубого прохода

```tavl
name = volume
values  = ./values.tavl
buffers = ./buffers.tavl

inputs = [ route_points, route_offsets ]
```

Понятие появилось из ДВУХМАСШТАБНОЙ генерации, и без него она не выражается. Грубый мировой проход
считается один раз и отдаёт каркас — маршруты, узлы, сводки; чанковый пайплайн читает из каркаса то,
что попадает в его область. Заполняет такой буфер **хост**: он один знает, какая часть каркаса
резидентна и что попадает в область этого чанка, потому что каркас бывает много больше видимого мира.
Значит шага, который его пишет, нет и быть не должно, — а правило «читать раньше первой записи нельзя»
без объявления входа отклонило бы весь пайплайн.

Объявляется вход **автором**, а не выводится из того, что буфер никто не пишет: именно это библиотека
и обязана считать ошибкой, а отличить «привезли извне» от «опечатался в имени» можно только по
объявлению. Вход, которого нет среди буферов, — отказ; вход, который никто не читает, — предупреждение
своей формулировкой («привезён и не понадобился»), а не общее «не привязан».

**Контракт для хоста, и он жёсткий:** заполненный вход обязан быть ФУНКЦИЕЙ ОБЛАСТИ чанка, а не того,
что успело подгрузиться. Неполный вход — это не «чуть хуже», это другой мир: тот же ключ дал бы разный
результат в зависимости от истории загрузки. Поэтому хост обязан либо гарантировать полноту, либо
отложить чанк, а поле запроса выводить из радиуса влияния, который объявляет сам каркас.

## Чанки

Чанкованная генерация и фоновое исполнение — **две разные вещи**. Фоновый поток живёт у потребителя:
он сам решает, когда дёрнуть `run_step`, и что делать с готовыми буферами (`published_after` говорит,
какие именно готовы). В библиотеке остаётся только то, что без неё не сделать — правило независимости.

**Правило: результат чанка зависит только от (зерно мира, ключ чанка) и не зависит от того, какие
чанки посчитаны раньше.** `set_chunk` не перевыделяет буферы, поэтому один пайплайн стримит много
чанков без аллокаций, а `clear_buffers()` существует ровно для доказательства обратного: если
результат меняется от того, обнулили буферы или нет, значит какой-то шаг читает то, чего не писал.

Отсюда **два зерна с разными контрактами**, и это выяснилось на первой же сверке чанков с картой
целиком — сначала было одно, и шум разъезжался на швах:

| Значение | Что это | Для чего |
|---|---|---|
| `step.seed` | `hash(зерно мира, имя шага)` | поле по мировой позиции: **непрерывно** через границу чанка |
| `step.chunk_seed` | `hash(зерно мира, имя шага, ключ)` | то, что обязано быть **независимым** в каждом чанке |

По умолчанию инструмент получает непрерывное: шум, молча разъехавшийся на швах, — отказ куда хуже,
чем случайно совпавший джиттер соседних чанков. Ключ чанка виден телу шага как `step.chunk`, чтобы
считать мировое смещение.

**Что чанкуется, а что нет** — измерено на GN01, карта `512x512` как 2x2, 4x4 и 8x8 чанков:

| Апертура | Поведение при чанковании |
|---|---|
| `pointwise` | **точно**: расхождение с картой целиком ровно `0` на всех 262144 клетках |
| `gather` | расходится **только** в полосе шириной `radius` у границы чанка, внутри ровно `0` ⇒ нужна полоса перекрытия |
| `scatter` | зависит от **носителя ключа** — см. ниже; глобальный отклоняется |
| `reduce` | свёртка по чанку не равна свёртке по карте |

### Носитель ключа: единственное, что здесь ОБЪЯВЛЯЕТСЯ, а не выводится

У pointwise и gather критерий был чистый: значение элемента определяется ограниченной окрестностью,
поэтому хватает полосы перекрытия. У scatter выход индексируется не элементом, а **группой**, и
ограничена не окрестность, а **носитель ключа**:

| Носитель | Пример | Поведение при чанковании |
|---|---|---|
| `chunk_local` | группировка по блоку внутри чанка | чанк заканчивает группу сам, слияния нет |
| `global` | «сумма высот по области», «сколько всего суши» | ни один чанк не заканчивает ни одну группу |

Что означает ключ — знание автора пайплайна, и из одного чанка это не проверяется никак. Поэтому это
**единственное место в библиотеке, где контракт объявляется, а не выводится**, и безопасное значение
стоит по умолчанию: необъявленный ключ считается глобальным, и при чанкованной генерации `scatter`
отклоняется до исполнения. Молчание означает отказ, а не разрешение.

```lua
originator.group_by{ inputs = {...}, outputs = {...}, key_support = "global" }
```

Отказ здесь не «неточность», а отказ по смыслу: глобальную сводку из чанков не собирают, её считают в
**грубом мировом проходе**, где чанков нет. Стриминговый генератор естественно имеет два масштаба —
грубый мировой (маленький, один раз: материки, области, диаграмма вороного, сводки) и мелкий чанковый
(большой, по требованию: рельеф, детали). Числа это подтверждают: вся диаграмма соседства на 1024
сайта стоит `0.48` мс, а контуры `0.71` мс — чанковать это незачем в принципе.

Кросс-чанкового слияния в библиотеке нет намеренно. Если оно когда-нибудь понадобится, замер уже
показывает, каким оно должно быть: при float-аккумуляторе порядок прихода чанков меняет **816 из 1024**
групповых сумм (относительная ошибка `4.8e-07`), а при целочисленном или фиксированно-точечном —
ровно `0` в любом порядке. То есть либо хранить частичные суммы и сливать в каноническом порядке
ключей, либо считать в фиксированной точке и вливать чанки по мере готовности. Второе дешевле и
согласуется с тем, что фиксированная точка уже выбрана языком симуляции.

Практическое следствие для авторов пайплайнов: **самокалибровка по измеренному диапазону несовместима
с чанкованием.** Шаг, который меряет min/max и нормализует по ним, для карты целиком даёт устойчивый
мир, а для чанка — своё отображение в каждом чанке. Выбор режима принадлежит конфигу, а не догадке
скрипта; в GN01 это значение `normalize`.

## Границы уровней исполнения

| Уровень | Кто | Для чего | нс/элемент, 1 поток | нс/элемент, 11 потоков |
|---|---|---|---|---|
| 0 | нативный инструмент | шум, размытие, свёртки, сегментация | 5.88 | 2.04 |
| 1 | `devils_script` | семантика, которую нужно моддить без C++ | 87.96 | 17.29 |
| 2 | lua | композиция внутри шага, небольшие множества | 119.36 | нет пути |

Уровень 0 — `noise_grid`, уровни 1 и 2 — одно и то же правило классификации. GN01, `4 194 304`
элемента, Release. Пороги правила у уровня 1 приходят из конфига; с литералами в скрипте он стоит
`64.12` нс, то есть конфигурируемость обходится в 51%.

**Окружение lua у генератора урезано сознательно.** Открыты только `base`, `coroutine`, `math`,
`string`, `table`, `utf8`; `math.random`/`math.randomseed` погашены явно; `os` не открыт вовсе. Ни
выхода в ОС, ни источников недетерминизма: зерно приходит шагом, а случайность выводится из аргументов.
Из того же решения следует, что `require` и модулей нет, поэтому помощник, нужный двум телам шагов,
ДУБЛИРУЕТСЯ — это норма, а не пробел.

Взамен в окружении лежит таблица **`base` с базовыми функциями движка** (`bindings::basic_functions`):
`base.prng64_2(a, b)` — хеш пары целых, `base.prng64_normalize` — число в `[0, 1)` из хеша,
`base.value`/`base.dice`/`base.interval` — числа из состояния, `base.rng` и метаметоды `rng_state`,
упаковка `pack_*`/`unpack_*`, очереди. Смысл — **один хеш на весь движок**: пока каждое тело шага
держало свой splitmix, «то же зерно» означало «то же зерно в этом файле», и генератор с симуляцией
считали по-разному. Две функции таблицы телу шага противопоказаны: `base.perf` (замер времени) и
`base.script_stack` — диагностика, и решение, зависящее от времени, сломало бы и воспроизводимость, и
равенство «параллельно == последовательно».

Ради этого базовые функции вынесены в отдельную цель сборки (`devils_engine::bindings_base`): в них нет
ничего от интерфейса, а генератор считает планету headless, и тянуть за собой visage с nuklear ему
незачем.

Правило для lua не «не трогает данные», а: **lua обходит только те множества, которые сама
перечислила** — список областей, отобранные кандидаты, вершины графа. В абсолютных числах: 4 млн
элементов из lua это `501` мс, а 4 тысячи провинций — `0.48` мс. Отсюда и граница. Обратная сторона
того же правила: расставить `1024` позиции сайтов поэлементно из lua — совершенно нормально, и в
GN01 это делает именно скрипт.

Про `devils_script` замер сказал не то, чего можно было ожидать. **Его выигрыш перед lua — не в
скорости интерпретации:** в один поток разница всего двукратная. Значение имеет другое:

- ds **распараллеливается**, а поэлементный lua нет — интерпретатор один и однопоточный. Сравнивать
  надо `8.69` против `108.12`;
- программа ds проверяется по типам **на разборе**, поэтому сломанное правило не доходит до
  исполнения вообще;
- ds остаётся единственным языком симуляции проекта, то есть правило, написанное для генератора,
  говорит на том же языке, что и правила игрового мира.

Цена ds против нативного ядра — примерно 12-кратная на одинаковой работе. Это и есть плата за
моддинг без перекомпиляции; арифметику внутреннего цикла на этот уровень выносить не нужно.

## Цели сборки

- `devils_engine::originator` — ядро: буферы, инструменты (включая объёмные), пайплайн. Не зависит ни
  от lua, ни от `devils_script`.
- `devils_engine::originator_script` — слой `devils_script`: программы над плотным буфером.
- `devils_engine::originator_primitives` — FastNoise2 и jc_voronoi.
- `devils_engine::originator_lua` — скриптовый хост. Свой `sol::state`, своё окружение и свой бюджет,
  никакой связи с `visage` ни в одну сторону — см. «Окружение lua и бюджет тела шага».
- `devils_engine::originator_config` — генератор как РЕСУРС: тип ресурса `generator_source` и сборка
  пакета по одному id точки входа. Единственная цель, знающая про `demiurg`; см. «Точка входа».

## Окружение lua и бюджет тела шага

Стейт lua у генератора **свой**, а не общий с `visage`, и это не деталь реализации. Тело шага
адресуется к буферам на миллионы элементов, UI-скрипт — к кадру; смешивать их права незачем, а
детерминизм генератора — часть контракта, а не пожелание. Поэтому `script_host` владеет собственным
`sol::state` и собственным `sol::environment`, а цель сборки `originator_lua` не зависит от `visage`
ни в одну сторону.

Что видно телу шага: `step` (имя, индекс, оба зерна, ключ чанка, параметры, `reads`/`writes`,
`programs`), таблица `originator`, усечённый набор базовых функций и стандартные библиотеки
`coroutine`/`string`/`table`/`math`/`utf8`. Чего не видно: файловой системы, `os`, `package`,
`require`, `load`/`dofile`, `debug` и `math.random` — всё, из чего мог бы просочиться недетерминизм.
Случайность приходит зерном шага и считается инструментом как функция от индекса.

Заодно нашлось, что весь этот whitelist **не работал**: ключ `std::string_view` в проксировании sol2
молча промахивался, и базовые функции оседали в окружении как `nil`. Тела шагов GN01 этого не
замечали, потому что обращались только к `step`, `originator` и арифметике, а единственный `error()`
в `terrain.lua` стоял на пути, который не срабатывал: сообщение об ошибке само упало бы с «attempt to
call a nil value». Теперь ключи — `const char*`, а пропажа **ядра** списка (`assert`, `error`,
`pcall`, `type`, `tostring`, `tonumber`, `pairs`, `ipairs`) или пустая стандартная библиотека — это
громкая ошибка при создании хоста. Такую потерю нельзя заметить по результату генерации, значит её
обязана ловить проверка.

### Зацикленное тело шага

Роль ровно та же, что у `budget_config` в `visage`, но величина выбрана другая:

| Бюджет | По умолчанию | Что измеряет |
|---|---|---|
| `instruction_limit` | `200 000 000` | инструкции **lua**; время внутри нативного инструмента не считается |
| `wall_time_us` | `0` (выключен) | стенные часы тела шага целиком |

Ограничение по умолчанию идёт по инструкциям именно потому, что эти две величины измеряют разное.
Счётчик инструкций растёт только пока исполняется lua, поэтому он ловит то, что нужно ловить —
цикл в скрипте, — и не срабатывает на честном шаге, который час считает мировой шум в нативном ядре.
Часы этого различия не видят, поэтому остаются инструментом хоста, который знает свои сроки.

Величина взята из правила самой библиотеки: lua обходит только те множества, которые сама
перечислила. Тело, потратившее сотни миллионов инструкций, это правило уже нарушило. Перф-стенд
нарушает его намеренно — и снимает бюджет **вслух**, `set_budget({0, 0})`, а не пользуется тем, что
по умолчанию ничего не ограничено.

Шаг счётчика хуков выводится из лимита (`min(лимит, 10000)`), а не берётся константой: с лимитом в
500 инструкций хук, стоящий раз в 10000, не сработал бы ни разу, и маленький бюджет оказался бы тихо
бесконечным.

Одна вещь сделана строже, чем в `visage`. Ошибку бюджета можно поймать `pcall`'ом внутри тела —
`pcall` из окружения не убрать, он нужен по делу. Поэтому исчерпание бюджета **отмечается флагом**, и
хост проверяет его после возврата из тела: шаг, доевший бюджет, провален, даже если сам себя простил.
Иначе `pcall(function() while true do end end)` висел бы вечно, а генерация считала бы шаг
выполненным.

Проверяется это в `--verify` GN01 четырьмя пунктами: бюджет по умолчанию не бесконечный, окружение
отдельное и без недетерминизма, цикл падает по лимиту инструкций и по лимиту времени, и проглоченная
`pcall`'ом ошибка бюджета всё равно проваливает шаг.

## devils_script над буфером

Программа компилируется против **имён входных полей**, и имена берутся у самих привязок — поэтому в
скрипте поле зовётся ровно так же, как в `buffers.tavl`, а второго списка имён, который мог бы
разъехаться с первым, не существует. Привязка не тем полем или не в том порядке отклоняется до
исполнения.

```
{ value_or = { smoothed < 0.5, 0,
  value_or = { moisture < 0.35, 1,
  value_or = { moisture < 0.65, 2, 3 } } } }
```

Апертура здесь не объявляется, а **следует из регистрации**. Скрипту доступны ровно два вида
обращений: прочитать поле своего элемента и вернуть значение. Функции, которая пишет, не
зарегистрировано; функции, которая доберётся до соседа, тоже. Поэтому программа структурно
`pointwise` и её нельзя случайно сделать не такой. Когда появится доступ к соседям, он приедет
отдельной регистрацией — и вместе с ней апертура станет `gather` со всеми её проверками.

Пороги правила приходят как `ctx:arg:имя` из параметров шага, то есть из общих значений пайплайна:

```
{ value_or = { smoothed < ctx:arg:sea_level, 0,
  value_or = { moisture < ctx:arg:dry, 1,
  value_or = { moisture < ctx:arg:wet, 2, 3 } } } }
```

Разделение простое: правило живёт в скрипте, числа в конфиге. Аргументы выставляются один раз на
контекст и постоянны на весь проход — они описывают проход, а не элемент. Каждый объявленный
`ctx:arg:` обязан найтись в параметрах шага; забытый параметр — громкая ошибка с его именем, а не
молчаливый нуль в правиле. Типы аргументов (`double`/`int64`/`bool`) проверяются при компиляции
программы.

Случайность внутри скрипта — функция от элемента: перед каждым элементом состояние PRNG выставляется
в `hash(зерно шага, индекс)`. Поэтому `chance`/`random` тоже не зависят от раскладки по потокам.

Система компилируется с небезопасными опкодами: проверка типов остаётся на разборе, где ей место, и
это удваивает скорость исполнения.

## Очередь вычислений

Очередь — **названная цепочка заранее объявленных вызовов, которая исполняется целиком**. Понятие
взято из уже написанного кода: в телах шагов встречаются цепочки инструментов, между которыми нет ни
одного промежуточного значения в lua (`box_blur` -> `classify` в теле шага `climate` у GN01 — ровно
такая). Значит подграф уже существовал — у него просто не было имени, и потому его нельзя было ни
померить как одну вещь, ни слить проходы, ни перенести целиком.

Отсюда и разделение НЕЙМСПЕЙСОМ, а не флагом в аргументах: `originator.box_blur{...}` считает
сейчас, `originator.queue.box_blur{...}` работу ОБЪЯВЛЯЕТ, а исполняет её очередь.

```lua
originator.queue{
  originator.queue.box_blur{
    inputs = { height }, outputs = { smoothed },
    params = { width = step.params.width, radius = step.params.radius },
  },
  originator.queue.classify{
    inputs = { smoothed, moisture }, outputs = { biome },
    params = { sea_level = step.params.sea_level, dry = step.params.dry, wet = step.params.wet },
  },
  output = { smoothed, biome },
}
```

Строка аргументов у обоих неймспейсов одна и та же — отличается ровно момент исполнения. Внутри
очереди доступны и `originator.queue.run("имя", {...})`, и `originator.queue.run_script{...}`, то
есть программа `devils_script` становится таким же элементом, как нативный инструмент.

**ВХОДЫ ВЫВОДЯТСЯ, ВЫХОД ОБЪЯВЛЯЕТСЯ.** Всех своих читателей внутри очередь видит сама: поле,
которое элемент читает и которого до него никто не писал, — это вход, и его можно вычислить. А кто
прочитает результат ПОСЛЕ очереди, очередь не знает и знать не может, поэтому `output` называется
вслух. Это не удобство, а **граница передачи**: на устройстве то, что не названо в `output`, не
обязано покидать его вовсе, а что названо — обязано. В примере выше названы оба поля, потому что
`smoothed` читает правило на `devils_script` в следующем шаге.

Из той же границы следует **проверка на мёртвую работу**: элемент, чей выход никто дальше не читает
и который в `output` не назван, — мёртвый, и об этом говорится до исполнения, ровно как сейчас
говорится про непривязанный буфер. Сюда же попадает выход, ПЕРЕЗАПИСАННЫЙ позже без чтения. Затирание
проверяется по ПОКРЫТИЮ диапазона: два вызова, пишущие разные отрезки одного поля, оба живые, и
ложный отказ здесь стоил бы дороже пропущенного предупреждения.

**Один отказ на всю очередь.** Очередь проверяется до первого вызова, а не падает на середине работы,
и сообщение называет номер элемента (нумерация — как в списке lua, с единицы). Привязки нативного
инструмента проверяются тем же `check_dispatch`, что и у одиночного вызова: второго набора правил у
очереди нет. Из lua это делается на ОБЪЯВЛЕНИИ, а не при запуске, — тогда сообщение приходит из той
строки, где вызов написан, а не из одного места, где очередь исполняется.

В очередь пускаются апертуры, которые пишут СВОЙ элемент в объявленный выход: `pointwise` и `gather`.
У остальных трёх отказов три РАЗНЫЕ причины, и каждая называется своей:

| Апертура | Почему не пускается |
|---|---|
| `scatter` | пишет по чужим индексам в структуру другой формы, и порядок задаёт алгоритм, а не очередь |
| `sequential` | порядок значим по построению — очередь на нём разрывается, и это граница, видимая в конфиге |
| `reduce` | отдаёт ОДНО число, а промежуточных значений в lua у очереди нет: деть его некуда |

Отказ `reduce` — не ограничение реализации. Свёртку и считают ради того, чтобы прочитать результат и
параметризовать следующий вызов (так работает нормализация в `terrain.lua`), то есть ради того самого
возврата в дирижёра, которого очередь не делает.

**Объявленный вызов обязан попасть в очередь ровно один раз.** Иначе у тела шага две тихие ошибки,
которых не видно по результату: забытый элемент ничего не посчитал, а отданный дважды посчитал одно и
то же поле теми же аргументами второй раз. Поэтому объявления считаются, и расхождение проваливает
шаг с числом потерянных.

Возвращает очередь отчёт: `calls` — сколько элементов объявлено, `passes` — сколько обходов данных
реально сделано. Сегодня они равны; слияние соседних `pointwise` обязано уменьшить `passes`, и
величина существует именно затем, чтобы выигрыш от слияния был ИЗМЕРЕН, а не предположен.

Чего в очереди пока нет: слияния проходов, исполнения на устройстве и передачи по границе `output`.
Ядро очереди (`computation_queue.h`) не знает ни про lua, ни про `devils_script`: элемент, чей код
лежит вне ядра, несёт своё исполнение телом.

### Открытое направление: та же очередь на GPU

Отдельным документом — [`ORIGINATOR_GPGPU.md`](../../ORIGINATOR_GPGPU.md). Коротко: единица переноса
это **очередь**, а не отдельный шаг — по причине, описанной выше. Детерминизма float на GPU нет и это принято: очередь неприменима к чанкованной
генерации, если она не целочисленная, а расхождение CPU- и GPU-прохода — объявленное свойство, а не
дефект (побитовое совпадение генератору не нужно). Единственное больное место — воспроизводимость
свёрток: выход `reduce` возвращается в мир, и его последний бит решает, где будет берег. `painter`
втягивается ограниченно — originator СОСТАВЛЯЕТ pipeline для `graphics_base` из своего конфига,
второго планировщика не появляется. В работе первый пункт порядка работ — сама конструкция на CPU
(она описана выше); ни транслятора `ds` -> GLSL, ни вычислительного контекста ещё нет.

## Чего пока нет

- расстояние до набора сегментов (`gather` с индексом в `prepare`) — нужно пещерной генерации;
- эрозия, watershed, сплайновые коридоры;
- порядко-независимый `accumulate` на фиксированной точке и проверка определённости по полосе
  перекрытия — обе формы известны, но без потребителя проектировать их нечестно;
- запечатывание СГЕНЕРИРОВАННОГО пакета на диск и чтение его штатным `demiurg`-ресурсом (описание
  генератора через `demiurg` уже читается — см. «Точка входа», речь о результате генерации);
- полигоны областей из `jc_voronoi` (сейчас берётся только соседство);
- запечатывание пакета: без знания проекта его не угадать — что считать картой, как устроена
  связность внутри уровня и как выглядят генерируемые геймплейные скрипты, решает проект. Движок
  может дать шаблон, а не формат.
