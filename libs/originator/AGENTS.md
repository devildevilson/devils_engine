# originator — рабочая карта

Документ для агента, который правит эту библиотеку. Человеку — `README.md`: там устройство и
объяснения. Здесь только то, что нужно, чтобы ПРАВИТЬ и не сломать: где что лежит, чего нельзя
нарушать, как делаются типовые правки и чем это проверяется.

Общий контекст проекта — `AGENTS.md` в корне репозитория. Контекст переноса на GPU —
`ORIGINATOR_GPGPU.md`.

---

## 1. Куда смотреть

Вопрос -> файл, который на него отвечает. Ответ ищется В ЭТОМ файле; если его там нет, значит вопрос
задан не тот.

| Вопрос | Файл |
|---|---|
| какие бывают роды полей, апертуры, носители ключа | `include/.../common.h` |
| как поле лежит в памяти, аксессор, быстрый путь, форма буфера | `include/.../buffer.h` |
| как объявляется инструмент, как проверяется и запускается вызов | `include/.../tools.h` |
| что такое очередь, что в неё пускается, что она проверяет | `include/.../computation_queue.h` |
| как собирается текст шейдера, кто вправе объявить чужое тело | `include/.../device_form.h` |
| как очередь превращается в pipeline устройства | `include/.../device_queue.h` |
| кэш планов устройства | `include/.../device_executor.h` |
| разбор конфига, пайплайн, шаги, чанки, диапазоны настройки | `include/.../pipeline.h` |
| id ресурса -> тексты генератора | `include/.../generator_resource.h` |
| lua-хост, биндинги, бюджет | `include/.../script_host.h` |
| `devils_script` над буфером | `include/.../script_program.h` |
| куда уходят часы и что годно к устройству | `include/.../execution_profile.h` |
| перевод `ds` -> GLSL, что переводится и где расходятся пути | `include/.../script_translate.h` |
| FastNoise2 и jc_voronoi | `include/.../primitives.h` |

Инструменты по наборам: `src/originator/standard_tools.cpp`, `graph_tools.cpp`, `volume_tools.cpp`,
`constraint_tools.cpp`, `scatter_tools.cpp`, `noise_tools.cpp`, `voronoi_tools.cpp`. Каждый файл
начинается блоком, объясняющим, ПОЧЕМУ набор отдельный.

Цели сборки: `devils_originator` (ядро), `_script`, `_primitives`, `_lua`, `_config`, `_device`.
Ядро не знает ни про lua, ни про `devils_script`, ни про `demiurg`, ни про Vulkan — если правка
заставляет ядро о них узнать, правка неверна.

## 2. Инварианты

Нарушение любого из них — дефект, даже если тесты зелёные.

1. **Апертура объявляется инструментом, параллельность выводится.** Не добавлять API, которым скрипт
   сообщает «это можно параллелить».
2. **Проверка идёт ДО исполнения** и называет шаг, инструмент/номер элемента и поле. Падение на
   середине очереди недопустимо.
3. **Один способ выложить push-байты:** `device_call_header` + параметры по одному `float`. Второй
   шапки не заводить (она уже была и разъехалась).
4. **Одна запись значения в поле:** `store_component`. Любой второй путь (в том числе перевод в GLSL)
   обязан повторять её зажим и усечение.
5. **Быстрый путь только при точном совпадении рода**, не размера.
6. **Один хеш на движок:** `utils::shared::prng2` / `utils::prng`. Свой splitmix в новом коде — дефект.
   Копия хеша в преамбуле шейдера существует только потому, что у compute-программы нет `#include`, и
   она сверяется тестом.
7. **`run_script` принимает только `devils_script`.** `translated_form` выдаёт исключительно
   транслятор (ключ `translation_authority`).
8. **Где считается очередь — объявление конфига.** Не добавлять «умный» выбор пути по наличию
   устройства: молчаливый переход на CPU меняет мир под тем же зерном.
9. **Результат не зависит от разбиения работы.** Побитовое равенство «параллельно == последовательно»
   и «слито == не слито» проверяется тестами; всякая новая схема обязана его сохранить.
10. **Результат чанка — функция (зерно мира, ключ чанка).** Никаких переносов состояния между чанками.
11. **Отказ несёт причину.** Ни одного `return {}` там, где вызывающий не сможет отличить «нет» от
    «нельзя, и вот почему».
12. **Ядро не тянет чужие зависимости** (см. цели сборки выше).

## 3. Рецепты

### Добавить нативный инструмент

1. Тело и `tool_description` — в файл своего набора (`standard_tools.cpp` и т.д.). Апертура выбирается
   по тому, КАК инструмент адресуется, а не по тому, как удобнее.
2. Читать поля через `tool_call::input/output`, форму — через `resolve_extent`, параметры — через
   `call.params->number(...)` с тем же default'ом, что попадёт в `device_params`.
3. Необязательные входы/выходы объявляются числами `optional_inputs`/`optional_outputs`, а тело
   спрашивает `has_input`/`has_output`, а не считает размер списка.
4. Зарегистрировать в соответствующем `tool_registry::add_*`.
5. Тест в `subprojects/tests/originator_tools_test.cpp` (или по набору): результат + «1 поток ==
   N потоков побитово».
6. Строку в таблицу инструментов `README.md`.

### Дать инструменту устройственную форму

1. Написать `device_body` ПРОТИВ АКСЕССОРОВ (`in_0_at(index)`, `out_0_set(index, value)`), без
   `layout(...)` и без своей push-шапки. Индекс элемента уже есть, охранник по `count` уже стоит.
2. `device_params` — те же имена и те же default'ы, что читает тело на CPU; `symbol`, если имя занято
   в GLSL (`min`, `max`).
3. `device_filtered_inputs` — только для входов, которые читают МЕЖДУ элементами: это единственное,
   из чего выводится картинка.
4. `device_integer_ready` ставить, только если тело честно работает над целым полем (перевод через
   `float32` точен до 2^24).
5. `order_free_writes` — только целочисленное накопление; плавающее объявить так нельзя.
6. Тест в `originator_device_queue_test.cpp`: сверка с CPU-путём.

### Добавить конструкцию в транслятор `ds` -> GLSL

1. Понять форму узла в AST: `=`/`?=`/пустой оператор — это ВЫЗОВ, блоки приходят объектами, пути вроде
   `ctx:arg:x` — одним `unrecognized` токеном.
2. Ветку добавить в `translator::call` (или в `value` для голого идентификатора). Переводить
   ПОДВЫРАЖЕНИЯ строго ВПЕРЁД, отдельными операторами: перевод попутно нумерует аргументы
   push-константы и соли случайности.
3. Если конструкции нужна именованная величина — класть её локалью через `temporary`/`declare`, а не
   повторять выражение. Локаль вычисляется ДО ветвления: запись изнутри ветки обязана отклоняться
   (`branch_depth`).
4. Если перевести нельзя — строка в `refusals` со СВОЕЙ причиной.
5. Тест в `originator_translate_test.cpp`: форма текста + побитовая сверка с CPU на ЦЕЛОЧИСЛЕННОЙ
   программе (на плавающей пути расходятся законно).
6. Обновить список переводимого в `script_translate.h` и в README.

### Добавить поле в общую шапку push-константы

Правятся ТРИ места, и все три обязаны совпасть: `device_call_header` (`tools.h`), строка шапки в
`build_device_shader` (`device_form.cpp`) и заполнение в `device_queue::write_push`. Комментарий с
байтовой раскладкой в `script_translate.cpp` — четвёртое. Тесты, собирающие push вручную, используют
саму структуру, поэтому чинятся сами.

### Добавить биндинг lua

Только СВОБОДНОЙ ФУНКЦИЕЙ или методом `script_host`, никогда лямбдой (см. ловушки). Ярлык с
привязанным именем — замыканием в lua (`install_shortcuts`). Новое имя в `originator` не должно
совпасть с `reserved_api_names`.

### Добавить набор инструментов

Новый `.cpp` в `src/originator`, метод `tool_registry::add_*_tools()`, файл-блок с объяснением, ПОЧЕМУ
набор отдельный (по способу адресоваться или по контракту, а не по теме), строка в `CMakeLists.txt`.

## 4. Проверка

```
cmake --build build-release -j 8            # ТОЛЬКО из корня репозитория
cd build-release && ctest -R originator -j 4
```

Сборка из подкаталога даёт ложное «utils/core.h: No such file or directory» во всех TU.

| Что меняли | Что гонять |
|---|---|
| буферы, аксессоры | `originator_buffer_test` |
| инструменты ядра/графа | `originator_tools_test`, `originator_scatter_test` |
| объём | `originator_volume_test` |
| решатель | `originator_collapse_test` |
| очередь, слияние | `originator_queue_test`, `originator_queue_lua_test` |
| устройство | `originator_device_test`, `originator_device_queue_test` |
| транслятор | `originator_translate_test` |
| `ds` над буфером | `originator_script_test` |
| разбор конфига, ресурсы | `originator_config_test`, `originator_pipeline_test` |

Тесты с устройством сами проверяют `painter::compute_device_available()` и молча пропускают сверку,
если GPU нет: зелёный прогон без устройства ничего не доказывает про GPU-путь.

Живые потребители — площадки `subprojects/playgrounds/GN01..GN05`. У каждой свой `--verify`, и
серьёзную правку разумно прогнать через них: они ловят то, чего не видит юнит-тест (иерархия
названных мест, швы чанков, дыры в поверхности).

## 5. Ловушки

- **sol2 и лямбды.** Две лямбды с одинаковой сигнатурой в одной функции делят метатаблицу `__gc` —
  порча памяти, падающая далеко от места ошибки. Биндинги объявлять функциями.
- **Порядок перевода.** Порядок вычисления аргументов одного вызова в C++ не определён; собранный
  as-is список аргументов зависел бы от компилятора.
- **Равенство в `ds` — с допуском** (`1e-6`), а не побитовое. Перевод обязан повторять ту же константу.
- **`as_span<T>` над чужим родом** молча пишет биты. Проверять род, не размер.
- **Форма документа `tavl`.** Строка `values = ...` рядом с блоком верхнего уровня превращает документ
  в структуру, и он читается не тем обходом, БЕЗ ошибки. Разделителей `//---` в точке входа быть не
  должно.
- **Разделитель строк в `tavl`** — запятая или перевод строки; пробел не разделяет.
- **Случайность на устройстве не равна CPU** (соль `ds` живёт в скомпилированном контейнере, хеш на
  GPU 32-битный). Не «чинить» это сверкой значений: сверять надо повторяемость и формулу на хосте.
- **Прогон на ноутбуке меряет тепло.** Замеры — отдельным режимом, варианты чередуются, читать медиану.
- **`view<>::operator[]` у demiurg** возвращает висячую ссылку; в этой библиотеке ходить через
  `filter<T>`/`get<T>`.

## 6. Соглашения

- **Комментарии по-русски**, как и во всём проекте. ИСКЛЮЧЕНИЕ: текст, который уезжает наружу —
  сгенерированный GLSL, сообщения об ошибках трансляции, — по-английски: его читают glslc, отладчик и
  люди вне проекта.
- **У каждого файла блок сверху**, после `#include` и до `namespace`: что это, на что обратить
  внимание, особенности реализации. Длинные объяснения живут ТАМ, а не над отдельной декларацией.
- **По коду — только заметки по делу:** описание алгоритма над функцией и короткие пояснения
  особенностей. Копна комментариев над одной декларацией — повод перенести её в блок файла.
- **Комментарий объясняет ПОЧЕМУ, а не что.** «Считаем сумму» — мусор; «сумма идёт в порядке чанков,
  иначе результат зависит от числа потоков» — по делу.
- **Числа в документации — измеренные.** Если числа нет, писать, что его нет, а не оценивать.
- Порядок полей структур — по убыванию размера/выравнивания.
- Не `std::map`: `std::vector` или `gtl::flat_hash_map`.
