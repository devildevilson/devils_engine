# Синхронизация компонентов — рабочий контракт

Состояние: рабочее решение, 2026-10-08. Первый потребитель — `frontier_online` с **полным причинным
миром у клиента**. Это осознанное ограничение первого опыта, а не требование `libs/network` ко всем
проектам.

## Ревизия общего слоя

| Требование | Сейчас | Следующий контракт |
| --- | --- | --- |
| Рукопожатие и совместимость | `libs/network` сравнивает protocol, content root, checkpoint/intent/component schema и numeric profile; `frontier_online` проверяет мир и полный join | Связать проверенные схемы с непрерывной сессией |
| Доставка и валидация | Есть GNS reliable/unreliable, лимиты сообщений, парсеры, journal и replay | Собрать authoritative bundle с origin sequence, root и оконный rollback в project runtime |
| ECS и проекты | Полный checkpoint использует 17 зарегистрированных компонентов; `component_wire<T>` объявляет два формата значений | Клиент исполняет каждый причинный тик из canonical bundle; регистрация компонента сама по себе не включает поток |
| Учёт байтов | Известны размеры полных checkpoint; transform/intent имеют расчёт раскладки | Собирать по классам сообщения полезные байты, заголовки, повторные интенты, компрессию и фактические GNS bytes |

`libs/network` уже содержит много проверенных механизмов, но ещё не составляет из них готовый
минимальный session runtime для нового проекта. Это и есть основной незакрытый результат ревизии.

## Два независимых объявления

`SERIALIZABLE_COMPONENT(T)` включает `T` в полный ECS checkpoint. Такой checkpoint уже содержит
timeline, все зарегистрированные пулы компонентов и проектные причинные счётчики; он загружается
транзакционно. Это путь initial join и полного recovery.

Добавленный `network::component_wire_table::add<T>()` объявляет полный образ компонента:

```cpp
table.add<actor_position>();
table.add<actor_state>();
```

- ID выводится из полного имени типа, layout hash — из `utils::serial`; ручные числа не нужны;
- `utils::serial` кодирует/декодирует значение; типовой **лимит** выводится из `sizeof(T)` для
  тривиально копируемых типов, иначе равен 1024 байтам, а нестандартный бюджет задаётся явно;
- проектную семантическую проверку можно добавить отдельно через `component_wire_validation<T>`.

`sizeof(T)` здесь только стартовый предел, не формат в памяти: в провод идут канонические
байты сериализатора. Для `actor_position` и `actor_state` кодер действительно выдаёт по 8 байт;
больший/переменный образ требует явного лимита. Декодер ограничивает и число вложенных значений.

`component_wire_table` проверяет ID и предел значения, сортирует объявления,
считает отпечаток из канонических байтов и может быть заморожена до handshake. Повторная
регистрация типа даёт отказ по совпавшему ID. Доставка и частота принадлежат **классу сообщения**,
а не типу ECS-компонента. Пока нет оболочки компонентного сообщения с тиком, entity и поколением
набора, delta, cadence и правила применения; объявление кодека не обещает регулярную репликацию.

Список объявлений проекта должен быть заморожен до handshake и передавать отпечаток
**формы wire**, отличной от частоты отправки. Другая частота при той же форме совместима;
другая форма должна быть отвергнута до первого тика. Envelope v3 передаёт отпечаток как отдельное
поле и даёт `component_schema_mismatch` до challenge. Версии v1/v2 читаются с пустой компонентной
схемой; если авторитету нужна непустая схема, старому клиенту приходит известный ему
`unsupported_wire_version`. `aesthetics::serial::component_registry` остаётся владельцем полного checkpoint. Сетевой список
не должен автоматически включать каждый сериализуемый компонент в регулярный трафик.

Имя C++ типа здесь такое же основание идентичности, как в checkpoint-реестре. Переименование
меняет ID и вызывает отказ совместимости. Для долгоживущего публичного wire-имени можно
специализировать `component_wire_identity<T>`; при изменении байтов пользовательского адаптера
без изменения layout нужно увеличить `revision` или имя адаптера.

Общие `baseline_store`, `try_materialize_delta`, `state_frame_header`, `relevant_set` и классы
transform пока не соединены с компонентной таблицей в runtime. Компонентный формат может
потребоваться для диагностики, correction или presentation, но не является источником причинных
тиков по умолчанию.

## Два компонента первого опыта

| Компонент | Причинный checkpoint | Объявленный wire-образ | Откуда клиент узнаёт причинное значение |
| --- | --- | --- | --- | --- |
| `actor_position` | Точное `glm::vec2` на тике K | Полное значение из двух `f32`, 8 байт | Локальная симуляция canonical bundles |
| `actor_state` | Точный hash состояния FSM на тике K | Полное значение `u64`, 8 байт | Локальная симуляция canonical bundles |

Для `actor_state` важно различать конечное значение и переходы. Последовательность
`think -> flee -> think` заканчивается тем же значением, но промежуточный переход мог вызвать
эффект. Снимок компонента восстанавливает **состояние**, а не пропущенные причинные события.

## Единая политика причинности и каналов

Клиент после join держит полный причинный мир и **сам исполняет тики**. Его локальные интенты
сразу участвуют в prediction; по сети уходит только минимальное предложение без acting entity и
provenance — сервер выводит их из проверенной session. Authority валидирует предложение,
запечатывает принятые действия в canonical bundle тика и рассылает каждый bundle, включая пустой.
Клиент применяет bundle **до** шага соответствующего тика. Только эта непрерывная, надёжно
доставленная и проверенная последовательность продвигает подтверждённый причинный мир.

Единое правило для всего движка: **сообщение, потеря которого меняет следующий причинный тик,
идёт по reliable ordered причинной истории**. Интент — предложение, а не подтверждённая история:
его batch допускает потерю и повторяет недавние тики. Unreliable transform — наблюдение для
presentation и, возможно, подсказка для prediction; он помечается тиком и поколением relevant set,
может быть отброшен и не пишет значение прямо в причинный ECS. Поэтому порядок между control и
unreliable lanes не нужен для исполнения тиков. Изменение relevant set и полный checkpoint
доставляются надёжно, причём checkpoint идёт с отдельным bulk-бюджетом.

Root на авторитетном тике сравнивается с сохранённым root **того же** тика. Если предсказанные
inputs отличаются от canonical bundle, клиент берёт удержанный checkpoint перед расхождением,
исполняет canonical bundles до последнего известного тика и затем переигрывает локальные
интенты ещё открытых тиков. Повторный root обязан совпасть; иначе причина глубже
(численная недетерминированность, несовместимые правила или повреждённая история) и нужен
новый authoritative checkpoint. Каждый canonical bundle закрывает свой тик: предложения клиента
с указанными `(origin session, sequence)` приняты, остальные предложения этого тика отклонены
или потерялись. Поздние предложения к закрытому тику authority отвергает. Так bundle сам служит
application ACK; отдельное поле input ACK для этой схемы не требуется.

`intent_batch` теперь несёт tick, kind и младшие 16 бит монотонного per-session input sequence.
`(session, sequence)` станет ключом дедупликации. Runtime ещё должен восстановить полный номер
относительно удержанного окна и ограничить незакрытые inputs половиной диапазона. Окно batch равно
восьми тикам: при более долгой потере предложение может не попасть к authority, что проявится
в canonical bundle и приведёт к пересчёту prediction.

Если нужный checkpoint или непрерывная история выпали из ограниченного окна, клиент делает
recovery/full join. Root и решение о закрытом тике относятся к причинной истории; transform
не может служить авторитетной correction, даже если его координаты кажутся точнее prediction.

Политика доставки устраняет межканальный порядок как причину рассинхронизации. Сама она ещё не
реализует wire bundle, root, хранение окна и rollback — это части минимального session runtime.
У `frontier_online` пока заявлен native-float numeric profile: совпадение root между разными
машинами ещё не доказано, поэтому первые prediction/rollback проверки следует проводить на одной
платформе и отдельно исследовать строгий числовой профиль.

| Случай | Начальная точка | Следующие данные |
| --- | --- | --- |
| Обычная игра | Состояние после тика N | Каждый canonical bundle N+1.. с origin sequence, root; необязательные transform frames для presentation |
| Потеря unreliable образца | Последний принятый образец | Следующий абсолютный образец; delta только от точно известной базы |
| Поздний вход | Полный checkpoint K и его корень | Каждый canonical bundle K+1..N, включая пустые тики |
| Reconnect | Подтверждённый checkpoint или новый полный checkpoint K | Все canonical bundles до цели, затем новое поколение relevant set |

`try_send` и освобождение send slab не являются подтверждением применения. GNS reliable
гарантирует доставку только в пределах живого соединения. Применённый canonical bundle
подтверждает решения authority по тику, но не получается из send completion; получение baseline
для другого потока и последний committed tick остаются отдельными понятиями.

## Масштаб и первые проверки

Release `frontier_online_server --ticks=1 --workers=4 --dump=...` на текущей сборке:

| Запрошено акторов | Сущностей в ECS | Канонический checkpoint |
| ---: | ---: | ---: |
| 128 | 200 | 21 802 байта |
| 1024 | 1288 | 161 962 байта |

Это размер одного полного состояния, не трафик в секунду и не оценка после сжатия. Он делает
проверку join на тысяче акторов разумным первым опытом, но ничего не говорит о цене регулярного
стрима и тика симуляции.

Join-тест теперь проходит и на 1024 заданных акторах с совпадением корня. Полный checkpoint
ограничен 16 МиБ до выделения у получателя; куски обязаны покрыть документ строго по порядку,
без повторов, пересечений и дыр. Это предел суммарного документа, не размер одного сообщения GNS.

## Следующий срез

1. Связать минимальный project intent с `intent_batch`, session sequence/dedup, validation и `tick_journal`;
   сделать production wire для canonical bundle, включая пустой тик.
2. Провести bundle через fixed-step клиента, добавить root и origin sequence принятых интентов,
   затем bounded prediction history и rollback с проверкой совпадения корня.
3. Измерить время кодирования/загрузки, transfer и очереди GNS на 1024 акторах; проверить
   потерю intent/transform и recovery при дыре в истории. Нынешние размеры checkpoint не
   оценивают эти величины.
