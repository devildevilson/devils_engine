# PF03 — post processing и temporal

Расширяемая независимая галерея post-effects и первая лаборатория, работающая с данными предыдущего кадра.
Она специально не является обязательной зависимостью остальных площадок: `PF05` может зафиксировать
небольшой нужный ему набор, пока `PF03` продолжает расти.

Вопрос лаборатории: **можно ли собрать классический пост-стек и temporal-техники из обычных ресурсов и
проходов render graph** — и какие движковые контракты для этого не хватает. Побочная цель, ради которой
площадка и заводилась: оттачивание painter на большом наборе разнородных эффектов.

## Почему temporal идёт первым

Render graph уже буферизует ресурсы (несколько копий на ресурс), потому что кадры конвейеризуются: кадр
`N+1` начинает работу, когда `N` ещё не отрисован. Значит доступ к предыдущему кадру существует как побочный
эффект буферизации — надо было только оформить его как контракт, и главное решение тут в том, ЧТО именно
объявляет автор, а что движок обязан вывести сам.

**Как это устроено сейчас (сделано 2026-08-18).**

Число копий ресурса нигде не пишется руками — оно сводится из двух ортогональных фактов, у каждого из
которых своё место объявления:

- **период вращения — свойство СЧЁТЧИКА.** `per_frame` крутится по `frames_in_flight`, `swapchain` — по
  числу образов презентации, и ресурс уже говорит, на каком счётчике живёт (`swap`). Поле `type` из
  объявлений ресурсов поэтому ушло: до правки все 32 ресурса всех конфигов давали ровно три пары
  `(type, swap)`, то есть `type` был пересказом счётчика. Он остался как **override** — для ресурсов на
  host-счётчиках, про период которых движок ничего знать не может (там он обязателен и требуется громко),
  и для случая «этому ресурсу осознанно хватит меньшего числа копий» (`doublebuffer` у upload-буферов);
- **глубина истории — свойство ТЕХНИКИ-читателя,** поэтому объявляется там, где происходит чтение — в
  binding'е дескриптора: `history = 1`. Двум темпоральным техникам с разной глубиной согласовываться не
  надо: ресурс берёт max по читателям;
- **копий = период + max(history).** Минимальность проверена перебором (`painter_temporal_history_test`):
  копия должна дожить до чтения и не может перезаписываться, пока её читают кадры в полёте, а одной копией
  меньше — уже гонка.

Из того же объявления выводится всё остальное, и в конфиге графа для темпоральной техники не появляется ни
семафоров, ни барьеров:

- **read-only фиксация.** Копия, дописанная кадром, переводится в тот layout, который объявлен
  history-биндингом, и живёт в нём столько кадров, сколько попросили. Фиксация стоит в САМОМ КОНЦЕ кадра, а
  не сразу за пассом-писателем: копию может тронуть более поздний пасс — тот же blit в свопчейн переводит её
  в `transfer_src`, и тогда следующий кадр читал бы историю в layout, который дескриптор не обещал;
- **кросс-кадровый порядок.** Пасс-читатель ждёт семафор пасса-писателя ПРЕДЫДУЩЕГО кадра; семафор движок
  создаёт сам. Ожидание фенса тут не помогает: fence ждёт кадр `N - frames_in_flight`, а `N-1` ещё в полёте.
  На первом кадре графа хвост кросс-кадровых ожиданий отрезается — сигналить их ещё некому. Ручной
  `wait_previous` у пасса остался escape hatch, а `wait_for` стал честно внутрикадровым (раньше локальные
  семафоры молча ждали предыдущий кадр) с loud error, если сигналящий пасс идёт позже читающего;
- **начальное состояние.** Копии temporal-ресурса чистятся в нули и переводятся в history-layout при
  создании и после resize. Без этого первый кадр читает картинки в layout UNDEFINED и с мусором в памяти —
  то есть «отсутствие истории» выглядело бы как случайный кадр, а не как пустая история;
- **индекс истории — не данные и даже не индекс массива.** Binding даёт шейдеру ЛИБО текущую копию
  (одиночный дескриптор), ЛИБО окно истории из `history` копий. Текущая копия в окно не входит намеренно:
  пасс, который пишет новую историю и читает прошлую (ровно топология TAA), держит текущую копию в writable
  layout, а копии истории — в read-only, и один binding не может обещать оба layout сразу. Побочный эффект:
  шейдеры больше не объявляют `scene_data[3]` — массив, случайно равный `frames_in_flight`. При `history = 1`
  прошлый кадр приходит как обычный `sampler2D`.

Проверка — не «кажется, работает»: `PF03` крутит 400+ кадров с включённой валидацией без единого сообщения,
`feedback_color` получает 4 копии (период 3 + история 1), выведенная зависимость видна в логе
(`pass 'pf03_temporal' waits previous frame of pass 'pf03_temporal'`), а картинка при
`--history-weight=0.94` даёт шлейф, которого при `0` нет (площадь светлых пикселей 1.36% против 0.82%).

## Планируемые срезы

Порядок выбран по отдаче на единицу работы, а зависимости идут первыми. Каждый срез заканчивается
запускаемым состоянием, а не «частью системы».

1. **Тонкий G-buffer и контракт истории — СДЕЛАНО** (2026-08-19, см. «Что даёт срез 1» ниже). Depth +
   октаэдральная нормаль + motion vectors одним проходом; motion и от камеры, и от собственного движения
   объектов. Это НЕ переход на deferred shading: `PF01` выбрал Forward+, и лаборатория не меняет
   архитектуру освещения молча — G-buffer здесь набор атрибутов для экранных эффектов.
2. **Экспозиция и tone mapping — СДЕЛАНО** (2026-08-19, см. «Что даёт срез 2» ниже). Самый заметный сдвиг
   картинки за минимум работы; без него всё остальное оценивается на глаз неверно.
3. **Туман и аэроперспектива — СДЕЛАНО** (2026-08-19, см. «Что даёт срез 3» ниже). Дёшево, и попутно прячет
   край дальних каскадов — тот самый приём, которым пользуются игры вместо попыток дотянуть качество дальних
   теней.
4. **SSAO — СДЕЛАНО** (2026-08-19, см. «Что даёт срез 4» ниже). Именно он читается как «запечённые тени
   глобального освещения»; для стиля-референса это ощутимее, чем дальнейшая работа над картами теней.
5. **TAA — СДЕЛАНО** (2026-08-19, см. «Что даёт срез 5» ниже). Джиттер камеры по субпиксельной
   последовательности, reprojection по motion vectors, neighbourhood clamp против ghosting, disocclusion и
   явные правила сброса истории.
6. **Bloom и god rays — СДЕЛАНО** (2026-08-19, см. «Что даёт срез 6» ниже). Обе техники — яркий проход плюс
   цепочка понижений, поэтому сделаны вместе и переиспользуют одну пирамиду.
7. **MSAA — отдельный изолированный срез.** В painter уже есть крючки на уровне makers
   (`rasterizationSamples`, `multisampleCoverage`, `attachmentSamples`), но в конфиге нет ни `samples` у
   ресурсов, ни resolve-attachment у render target, ни выбора sample count из таргета, ни depth resolve.
   Важно: MSAA и TAA — развилка, а не сумма. MSAA не помогает экранным эффектам (SSAO, contact, god rays
   читают один сэмпл) и плохо сочетается с G-buffer, поэтому срез делается forward-only и как A/B против
   TAA, а не поверх него.

## План дальше (после аудита 2026-08-19)

Порядок — по отдаче на единицу работы, инфраструктура впереди своих потребителей.

7. **Выходной тракт — СДЕЛАНО** (2026-08-19, см. «Что даёт срез 7» ниже): sharpen после накопления, дизеринг
   перед 8-битным выводом и «линза» — виньетка, хроматическая аберрация, зерно. Всё живёт в компоновке, без
   новых пассов и ресурсов.
8. **Взрослый замер экспозиции**: гистограмма с перцентилем вместо log-среднего, центровзвешенность,
   асимметричная адаптация (к яркому быстро, к тёмному медленно) и exposure-волюмы. Это же и есть механизм
   «эффекта тёмной комнаты»: узкий проход работает визуальным барьером именно потому, что экспозиция
   глобальная и авторски ограниченная.
9. **Color grading и LUT** — закрывает `RND-21`.
10. **Depth pyramid (Hi-Z)** и **SSR** на ней: обе техники поверх мип-цепочки, которая теперь есть, и
    пирамида глубины заодно нужна отсечению (`RND-20`).
11. **Depth of field** — bokeh на той же пирамиде.
12. **Motion blur** — единственный потребитель motion-канала помимо TAA, поэтому в PF03 он уместен; стоит
    в конце сознательно, эффект автору не нравится.
13. **TAAU (апскейлинг)** — компромисс отставания уже измерен, расширение естественное.

**MSAA** остаётся отдельной развилкой (`RND-30`), и это не тумблер, а другая форма конвейера: шейдинг обязан
уехать в forward-пасс, а темпоральный слой уходит целиком (см. ниже).

**Объёмный туман по froxel'ам с картой теней** — «настоящие» световые шахты — требует смыкания с картой теней
`PF02` и поэтому уезжает в отдельную будущую лабораторию, а не в этот срез.

После среза 5 имеет смысл вернуться в тему теней: «резкая тень без шума и лесенки», которую `PF02`
намеренно не стал делать без истории, становится возможной как stochastic sampling + temporal accumulation.

## Что даёт срез 1

Граф среза: `тонкий G-buffer → шейдинг → компоновка/репроекция → present`. G-buffer пишется одним проходом
в три вложения (нормаль, motion, глубина), шейдинг и компоновка — compute-пассы, поэтому цепочку видно
целиком без лишнего кода.

**Репроекция — первый честный потребитель истории.** Пасс компоновки читает `scene_color` прошлого кадра
(`history = 1`) и сдвигает выборку на motion-вектор. Кросс-кадровый порядок между ним и пассом шейдинга в
конфиге не объявлен — движок вывел его из этого чтения (`pass 'pf03_compose' waits previous frame of pass
'pf03_shade'`), и это уже случай «читатель ≠ писатель», в отличие от предыдущего стенда.

**Per-object motion не требует понимания, что за объекты на экране.** Фрагмент уже знает, каким инстансом
нарисован, поэтому достаточно, чтобы объект нёс свой прошлый трансформ рядом с текущим — вершинный шейдер
считает две clip-позиции одной точки, и разница уходит в G-buffer. Идентичность объекта понадобится не для
motion, а позже для отбраковки истории (disocclusion), и там обычно хватает сравнения глубины и нормали.

Прошлый трансформ при этом **не дублируется руками**: трансформы лежат в обычном per_frame ресурсе, а второй
биндинг того же ресурса объявлен как `history = 1`, поэтому хост пишет только текущий кадр. Это второй
потребитель контракта и первый на буфере, а не на картинке.

**Motion-векторы проверены численно, а не на глаз** — иначе правдоподобная картинка скрывает ошибку:

- при **статичной камере** ошибка репроекции ровно нулевая (кадр целиком чёрный, не «почти»);
- поле motion **масштабируется линейно** со скоростью камеры: `3.02 → 6.09 → 11.14` пикселей среднего
  модуля при `0.5 / 1.0 / 2.0` rad/s. Удвоение скорости удваивает вектор — величина, а не только направление;
- **при одинаковом виде** ошибка с motion ниже наивной (без векторов), и разрыв растёт со скоростью:
  `1.22×` при 2.5 px/кадр → `2.17×` при 20 px/кадр. Это и есть подпись правильных векторов: наивная ошибка
  растёт со смещением, компенсированная упирается в собственный потолок.

Отдельно проверен **per-object motion**, при неподвижной камере и чистом переносе (вся ошибка тогда только
от движения объектов): наивная ошибка растёт со скоростью объектов (`107 → 581 → 885` при `0.5/1.0/2.0`),
компенсированная заметно ниже (`74 → 248 → 391`), выигрыш `1.5× → 2.3×`. А главное — на карте ошибок остаток
лежит тонкой каймой ровно по силуэтам кубов (disocclusion, неустранимая часть), тогда как без векторов
светится весь контур смещения.

Перенос и вращение объектов разведены по разным ручкам (`--object-speed`, `--object-spin`) не для удобства:
вращение меняет нормаль, от неё зависит затенение, и точка поверхности меняет цвет между кадрами — репроекция
такое не исправляет по определению. Чтобы мерить сами векторы, нужен инвариантный сигнал, то есть `spin=0`;
вращение остаётся как будущая нагрузка на neighbourhood clamp.

Остаточная ошибка при движении КАМЕРЫ — не дефект репроекции, а **передискретизация**: сцена намеренно покрыта жёсткой шахматной
клеткой (`step()`), и при субпиксельном сдвиге линейная выборка истории спорит с резким текущим кадром на
каждой границе клетки. Ровно с этим борется neighbourhood clamp в срезе TAA, поэтому стресс-паттерн оставлен.

**Инструмент измерения.** `--dump=<path>` пишет итоговый кадр в PPM на заданном номере кадра, а `--orbit=`
делает положение камеры функцией номера кадра. Вместе это даёт кадр-точное сравнение: два прогона с
одинаковыми аргументами **побитово** одинаковы, поэтому режимы можно сравнивать численно. Внешний скриншот
для этого не годился — он приходит в произвольный момент, и разница между режимами тонула в разнице фаз
камеры (на этом я и обжёгся: первое сравнение «с motion / без motion» оказалось сравнением разных видов).

**Движковая находка по пути.** Первая попытка положить прошлый трансформ в запись инстанса draw group дала
ровно ту ошибку, которую метрика и должна ловить: история совпала с текущим кадром ПОБИТОВО. Причина — инстанс
и indirect буферы host-visible draw group привязаны к счётчику `per_update` и типу `doublebuffer`, а
`per_update` в кадровом цикле не двигается, поэтому все кадры в полёте читают одну и ту же память, и
«прошлого кадра» для этих данных не существует. В инстанс-лейн теперь пишется только индекс объекта
(константа, ей общая память безопасна), а всё меняющееся каждый кадр живёт в per_frame ресурсе. Правильное
решение на стороне движка — выводить период этих буферов из того, кто и как часто их пишет (`RND-33`).

Заодно уточнён вывод кросс-кадрового порядка: производителем истории может быть не только пасс, но и ХОСТ
(он пишет копию текущего кадра, пока GPU читает предыдущую — это разные копии по самой арифметике
период+история). Для host-написанного ресурса семафор не нужен и требовать пасс-писателя нельзя.

Чего в срезе нет: overlay (виды переключаются клавишами `0..6` и печатаются в лог), camera jitter и
depth/normal history — они идут вместе с TAA.

## Что даёт срез 2 — экспозиция и tone mapping

Это две РАЗНЫЕ операции, и путать их дорого:

- **экспозиция — множитель** в линейном HDR. Она отвечает на вопрос «что в этой сцене считать средним
  серым» и физически соответствует чувствительности сенсора, диафрагме и выдержке. В коде это буквально
  `color * exposure`; вся сложность в том, откуда взять множитель;
- **tone mapping — кривая**, сжимающая уже отэкспонированный неограниченный диапазон в отображаемый `[0,1]`.
  Она отвечает на вопрос «что делать со светами, которые всё равно не влезли». Порядок обратить нельзя:
  кривая сжимает то, что множитель уже расставил.

**Замер яркости.** Отдельный пасс одной рабочей группой берёт 4096 проб по кадру и усредняет **логарифм**
яркости, то есть считает геометрическое среднее. Это не эстетика: по арифметическому среднему одно яркое
солнце в кадре перетягивает экспозицию на себя и вся сцена уходит в темноту. Яркость берётся по Rec.709, а не
как среднее каналов.

**Адаптация** идёт через историю того же 1×1 ресурса: новая экспозиция смешивается с прошлой экспоненциально
по РЕАЛЬНОМУ `dt`, иначе скорость привыкания зависела бы от частоты кадров. Это третий потребитель контракта
истории и снова случай «писатель он же читатель».

Проверено численно:

- замер **линеен по яркости сцены**: солнце `1 → 6 → 30` даёт `2.51` и `2.38` стопа при теоретических `2.58`
  и `2.32` (остаток — 8-битный шаг диагностического вида);
- экспозиция его **ровно компенсирует**: средняя яркость итоговой картинки держится `74–82` при
  тридцатикратном изменении освещения, тогда как при фиксированной экспозиции уезжает `180 → 233 → 247`;
- формула сходится: `log2(E)` совпадает с `log2(ключ) − adapted` во всех замерах;
- адаптация действительно читает историю: при `--adapt-rate=0` (замороженная) картинка отличается от
  мгновенной на 33.5 тысячи пикселей;
- без кривой (`--tonemap=none`) **1.2% кадра выжжено** в плоский белый, с Reinhard и Hable — ноль.

**Передаточная функция тракта измерена, а не предположена.** Вид `8` выдаёт ровно `0.5` в линейном свете; на
скриншоте это читается как `187/255`, то есть `blit` в свопчейн формата `B8G8R8A8Srgb` кодирует sRGB сам.
Значит кодировать в шейдере нельзя — вышло бы двойное кодирование, и картинка выцвела бы. Тумблер
`--encode-srgb=1` оставлен на случай линейного формата презентации.

Сцене пришлось дать настоящий динамический диапазон, иначе срез нечем проверить: небо ярче освещённых
поверхностей (как в реальности, где оно измеряется тысячами кандел против сотен у стены), ambient задан долей
солнца, добавлен широкий глянцевый блик и светящаяся панель. Панель здесь не для красоты: автоэкспозиция
нормирует СРЕДНЕЕ, поэтому небо она уложит под единицу и сжимать станет нечего — а маленький источник на два
порядка ярче среднего среднее почти не двигает, и вытянуть его может только кривая.

**Ещё один движковый баг, найденный этим срезом (`RND-34`).** `constant::offset` задаётся в байтах, а память
констант — массив `uint32_t`, и `get_constant_data`/`write_constant_data` прибавляли смещение к `uint32_t*`,
уходя вчетверо дальше. Первая константа (offset 0) работала всегда, поэтому баг дожил до первого конфига с
двумя используемыми константами: dispatch читал мусор (валидация показала `groupCountY = 1072693248` — старшая
половина double). Исправлено, покрыто регрессом.

## Что даёт срез 3 — туман и аэроперспектива

Туман применяется в **линейном HDR до экспозиции**, потому что это яркость сцены, а не постобработка
изображения: экспозиция обязана мерить кадр уже с туманом, иначе экспонируется не та картинка, которую увидит
зритель. Отсюда и порядок пассов: `G-buffer → шейдинг → туман → экспозиция → компоновка → present`.

Модель — однократное рассеяние с экспоненциальным спадом плотности по высоте, взятое **аналитически**:

```
density(h) = density0 * exp(-(h - h0) / H)
tau        = density0 * exp(-(cam.y - h0)/H) * H/dir.y * (1 - exp(-dist*dir.y/H))
T          = exp(-tau)
color      = scene * T + inscatter * (1 - T)
```

Численный марш вдоль луча не нужен: интеграл экспоненты по прямой берётся в закрытой форме, и именно поэтому
туман стоит одну `exp` на пиксель. При `dir.y → 0` выражение вырождается, поэтому горизонтальный луч считается
отдельной ветвью (`tau = density * dist`).

Направленность даёт фазовая функция Henyey–Greenstein: при `g > 0` рассеяние идёт вперёд, и туман светится в
сторону солнца. Без неё туман — равномерная серая пелена, и вся узнаваемость аэроперспективы теряется. Небо
туманом не закрашивается: атмосфера в него уже «встроена», иначе цвет рассеяния учтётся дважды.

Измерено:

- **точный passthrough**: при `--fog=0` пропускание ровно `1.000` по всему кадру;
- **зависимость от расстояния**: `T` ближнего плана против дальнего — `0.924/0.814`, `0.731/0.439`,
  `0.376/0.077` при плотности `0.02/0.08/0.25`;
- **потеря контраста на дальнем плане** (это и есть аэроперспектива): среднеквадратичный контраст далёкой
  шахматки `28.05 → 17.68 → 8.71` при плотности `0/0.08/0.25`. Мерить это надо при ФИКСИРОВАННОЙ экспозиции:
  автоэкспозиция заново нормирует яркость и возвращает контраст обратно, скрывая эффект;
- **фазовая функция**: при солнце у горизонта прямо перед камерой дальний план даёт `74.8` при рассеянии
  вперёд против `33.7` назад — разница 2.2× при одном и том же кадре.

Отдельная ловушка измерения, в которую я сначала попал: первый тест фазовой функции стоял в точке, где
направление взгляда почти перпендикулярно солнцу. При `cos θ ≈ 0` функция Henyey–Greenstein **симметрична по
знаку g**, то есть я мерил ровно там, где разницы не должно быть по построению, и получил 1%. Понадобился
`--sun-dir=`, чтобы поставить солнце к горизонту.

## Что даёт срез 4 — SSAO

**AO модулирует ambient, а не изображение.** Это главное решение среза: пассы SSAO стоят ДО шейдинга, и
шейдинг умножает на затенение только небесную составляющую. Умножать им готовый кадр — распространённая
ошибка: тогда гасится и прямой солнечный свет, который в природе перекрывается геометрией и тенями, а не
статистикой соседей. Прямое следствие, которое надо принять сразу: **в солнечно-доминированной сцене SSAO
слаб по построению**, и заметен он там, где ambient велик — в пасмурную погоду и в помещении. Поэтому в
площадке появилась ручка `--ambient=<доля>`.

Считается в половинном разрешении (`declare_values` с `type = screensize` и `scale`, поэтому цена — фиксированная
доля кадра при любом разрешении), затем depth-aware блюр, затем depth-aware апсемпл в шейдинге по нижайшей
разнице глубин. В `.g` половинного буфера лежит линейная глубина текселя — тот же контракт, что в PF02 у
контактных теней, ровно затем же: обычный bilinear протекает через силуэты.

Число проб — **specialization-константа шага** с CLI-переопределением распарсенного конфига до сборки графа
(приём из PF02): это тир качества, и его смена стоит пересборки pipeline, а не нового варианта шейдера.

### Оценщик пришлось переписать по измерению

Первая версия сравнивала глубины проб (классическая формулировка «hemisphere SSAO»), и измерение сразу
показало дефект: на **открытом плоском полу** AO падал с ростом радиуса — `0.99 → 0.89` при радиусе `0.3 → 2.5`.
Это самозатенение: на скользящих поверхностях проба уходит за поверхность просто из-за перспективы.

Вторая версия решает занятость по **восстановленной позиции затенителя** и его положению относительно
касательной плоскости: компланарная поверхность даёт `dot(v, n) ≈ 0` и отсекается порогом. Результат
измерения: открытый пол `0.9999–1.0000` при любом радиусе и даже при нулевом пороге, а угол стен `0.898` —
то есть сигнал остался, а ложное затенение исчезло.

Второй дефект нашёлся уже на карте AO: у нижнего края кадра, где пол виден под скользящим углом, появился
веер радиальных штрихов. Причина не в точности глубины (проверено отдельным порогом — не помогло), а в
разбросе: один пиксель там покрывает огромную область мира, и то же число проб размазывается по большей
площади. Лечение стандартное — ограничение радиуса **в экранных единицах**. Измерение: разброс в полосе
`std 30.3 → 0.075`, среднее `0.983 → 0.99999`, а сигнал в углу стен **не изменился вовсе** (`0.8214` до и
после). То есть ограничение убрало только шум.

### Что ещё измерено

- **шум против числа проб**: сырой AO `41.4 → 31.2 → 26.7 → 25.2` при `4/8/16/32` пробах, а **после блюра
  выравнивается около `23` при любом числе проб**. Отсюда практический вывод: блюр — часть техники, а не
  улучшение, и сверх ~8 проб он съедает всю разницу;
- **вклад в картинку**: угол стен `99.4 → 89.9` (около 10%) при `ambient = 0.55` и фиксированной экспозиции.
  Мерить AO при АВТОэкспозиции бесполезно: затемнение поднимает экспозицию, и эффект частично отменяется — та
  же ловушка, что с контрастом тумана;
- **цена не измерима** этим инструментом: разброс среднего времени кадра между одинаковыми прогонами
  `3.46–4.65 мс` перекрывает стоимость эффекта, а `4` пробы «оказываются быстрее» `32`. Честный вывод: для
  цены нужны GPU-таймстемпы по пассам (в движке есть `gpu_timing`, в площадке пока не подключён).

Остаточный шум AO на движении — задача TAA: темпоральное накопление с джиттером выборки и есть штатный способ
довести такие оценщики до чистой картинки, ровно поэтому TAA стоит в плане следующим.

## Что даёт срез 5 — TAA

Три обязательные части, и ни одна не опциональна:

1. **Субпиксельный джиттер проекции** по последовательности Халтона (основания 2 и 3 взаимно просты, поэтому
   координаты не коррелируют). Это не постобработка: смещается сама матрица проекции, поэтому каждый кадр
   сцена сэмплируется в других точках внутри пикселя. Без джиттера накапливать нечего — усреднение
   одинаковых кадров даёт тот же кадр;
2. **репроекция накопленного кадра** по motion-векторам. Копится РЕЗУЛЬТАТ накопления (`taa_color` читает
   свою же историю), а не сырой кадр: иначе смешивались бы всего два кадра вместо длинного среднего;
3. **neighbourhood clamp** — история зажимается в диапазон 3×3 окрестности текущего кадра. Это главный
   инструмент против шлейфов.

Смешивание идёт в **обратимо сжатом** диапазоне (`c/(1+luma)`, из доклада Karis): в линейном HDR один яркий
пиксель перетягивает среднее на себя и оставляет вокруг себя светящийся хвост.

### Знак джиттера пришлось определить измерением

Джиттер обязан быть вычтен из motion-векторов: обе позиции получены из джиттеренных проекций, а вектор должен
быть чисто геометрическим. Я знал про эту ловушку и всё равно попал в неё — с неверным знаком:

- **инвариант**, который её и поймал: на полностью статичной сцене со статичной камерой motion при включённом
  джиттере обязан быть **нулём**. Измерено: `0.008 px` без джиттера и `1.624 px` с ним — джиттер протекал в
  векторы с двойной амплитудой;
- следствие было контринтуитивным и потому опасным: TAA «работал» — картинка выглядела сглаженной, дрожание
  падало на 20%, — но выход оказывался **ДАЛЬШЕ** от истинного суперсэмплированного кадра, чем один
  джиттеренный кадр (RMSE `795` против `538`). Именно этот тест и вскрыл проблему, а не глаз;
- после правки знака всё встало на теоретические места.

### Измерения после исправления

- **сходимость к суперсэмплингу**: выход TAA против среднего восьми джиттеренных кадров — RMSE `96.7`, тогда
  как один кадр отстоит от того же среднего на `564.6`. То есть накопление действительно даёт
  суперсэмплированную картинку, а не просто мыло;
- **подавление дрожания**: кадр-к-кадру на статичной сцене `1238 → 49.5`, то есть **в 25 раз**, что совпадает
  с ожиданием для веса истории `0.92`;
- **сглаживание кромок**: высокочастотная энергия в области кромок `121.4 → 84.4`; без clamp — `26.1`, то есть
  предельно мягко (clamp торгует гладкость на отзывчивость);
- **цена clamp'а измерена с двух сторон**: на движущихся объектах отклонение от кадра без TAA составляет
  `1058` с clamp и `2249` без него — то есть clamp урезает шлейф вдвое;
- **шум AO** в затенённой области `44.4 → 36.7` при 8 пробах: вращение выборки AO получило временной сдвиг,
  и накопление его усредняет. Это и есть та пара «стохастическая выборка + темпоральное накопление», которая
  была обещана в выводах `PF02`;
- unit-проверки тракта: `--taa-weight=0` и `--jitter=0` дают кадр, побитово (до 0.01% пикселей) совпадающий с
  выключенным TAA — passthrough честный.

Правило, которое стоит запомнить и вне этой площадки: **TAA нельзя валидировать глазом**. Ошибка знака давала
картинку, которая выглядела лучше исходной и при этом была хуже эталона; поймал её только численный тест на
сходимость к среднему.

### Ступенька на далёкой статике при движении камеры — предел техники, а не нехватка данных

Наблюдение автора: у далёких статических объектов при даже небольшом движении камеры появляется резкая
ступенька и через пару кадров исчезает. Разобрано измерением, и вывод стоит записать, потому что он
контринтуитивен.

Механизм: при движении камеры репроецированная история попадает между текселями и выходит за диапазон
окрестности текущего кадра — на далёкой тонкой кромке этот диапазон узкий, — поэтому история отбраковывается и
выход схлопывается к **неусреднённому** кадру. Дальше накопитель сходится заново: при весе `0.92` это около
двенадцати кадров, отсюда и «через пару кадров исчезает».

Ключевое: **это не лечится ослаблением отбраковки**. Проверено тремя вариантами (жёсткая коробка min/max,
клип по дисперсии в YCoCg, клип по скорости с ходом вдоль луча): метрика гладкости дальней области
`75.5 / 75.3 / 76.2` — то есть ширина коробки вообще не является ограничителем.

Ещё важнее — метрика гладкости для этого вопроса **непригодна**: она не различает «сглажено» и «замылено».
Пришлось построить настоящий эталон: та же точка обзора, камера зафиксирована, среднее восьми джиттеренных
кадров. Отклонение от него (меньше = точнее):

| вариант | отклонение от эталона | гладкость дальней области |
|---|---|---|
| без TAA вовсе | **404** | 131 |
| TAA, min/max, bilinear | 596 | 75.5 |
| TAA, min/max, Catmull-Rom | **536** | 83.5 |
| TAA, по скорости, Catmull-Rom | 554 | 85.2 |
| TAA без отбраковки | 788 | **49.6** |

Читается это так: самый **гладкий** вариант (без отбраковки) — самый **неточный**, потому что гладкость там
берётся из отставания и мыла, а не из сглаживания. И наоборот, при непрерывном движении камеры честный
аляйсящий кадр ближе к истине, чем накопленный. Это фундаментальный компромисс экспоненциального накопителя с
одной историей, а не дефект реализации.

Что дало **измеримое** улучшение — фильтр выборки истории. Под движением история переинтерполируется каждый
кадр, и обычный bilinear на каждом шаге чуть размывает её; за десяток кадров набегает заметное мыло. Замена на
Catmull-Rom (5 билинейных обращений, отрицательные лепестки) улучшила точность `596 → 536`, то есть на 10%,
и именно поэтому она включена по умолчанию. Жёсткая коробка при этом фильтре оказалась точнее клипа по
скорости (`536` против `554`), поэтому она и стала дефолтом; `--taa-clamp=velocity` оставлен как «меньше
ступенек на движении ценой большего отставания».

Что ещё осталось из известных приёмов: sharpen после накопления, вес истории в зависимости от скорости, и —
принципиально — **больше входных сэмплов на кадр** (гибрид MSAA+TAA либо TAAU с расширенной выборкой). Одной
историей и одним сэмплом на пиксель этот предел не обходится.

### Движковая находка

Как только историю одного ресурса стали читать ДВА разных пасса (`pf03_taa` для накопления и `pf03_compose`
для отладочных видов), выведенный порядок сломался: бинарный семафор — это один сигнал на одно ожидание, а оба
пасса ждали одну и ту же семафору. Валидация поймала это сразу (`no way to be signaled`). Теперь семафора
создаётся на **пару** «писатель → читатель», и писатель сигналит по одной на каждого читателя.

## Что даёт срез 6 — bloom и световые лучи

Пирамида общая, как и планировалось: четыре понижения (`1/2 … 1/16`), три аддитивных подъёма, а лучи берут
маску с четверти той же пирамиды — различается только фильтр, радиальный вместо изотропного.

Оба эффекта добавляются **в линейном HDR до экспозиции**: это свет, попавший не туда, куда должен был
(рассеяние в оптике и в атмосфере), а не эффект над готовым изображением. Поэтому экспозиция и кривая
обрабатывают их наравне со сценой.

Фильтры выбраны не «какие-нибудь»: понижение тринадцативыборочное (Jimenez), потому что обычный box на каждом
уровне пропускает частоты выше нового Найквиста и пирамида начинает пульсировать на движении; подъём —
шатровый `3×3`, иначе на каждом уровне видны квадраты нижнего разрешения. Порог яркого прохода — с мягким
коленом: жёсткое отсечение даёт границу, на которой свечение включается скачком.

### Порог обязан быть в единицах ПОСЛЕ экспозиции

Первая версия задавала порог в линейных единицах — и bloom взял **всю сцену**, потому что в HDR-кадре небо это
`19`, освещённые поверхности `3.6`, и выше любой абсолютной планки оказывается почти всё. Отладочный вид сразу
это показал: вместо источников светилась размытая копия кадра, средняя яркость буфера `0.536`.

«Ярко» имеет смысл только относительно того, что принято за средний серый, поэтому порог применяется к
яркости, умноженной на экспозицию, а сам цвет остаётся линейным. Это заставило поставить пасс экспозиции
**перед** пирамидой. После правки буфер содержит только источник (средняя `0.021`), а порог выше яркости
источника гасит эффект полностью — при `--bloom=0` и при пороге `100` итоговые значения **идентичны**.

Измерено: профиль свечения по стене вправо от панели спадает и управляется параметром распространения —
`9.3 → 3.6` при `--bloom-spread=0.4` и `70.0 → 20.4` при `0.95` (замеры дальше 100 px попадают уже на небо,
которое светится равномерно и к профилю не относится).

### Экранные лучи умеют ровно то, что умеют

Лучи собираются радиальным размытием от экранной позиции солнца по маске ярких пикселей, умноженной на
признак **отсутствия геометрии**: шахты — это свет, дошедший мимо препятствий, а не свечение поверхностей.
Ограничения метода прямые и их надо знать: солнце обязано быть в кадре (за камерой лучи ровно нулевые —
проверено, `mean = 0`, `max = 0`), а затенители за границей кадра метод не видит. Полноценные шахты требуют
марша по карте теней, то есть отдельного среза.

Второе, что выяснилось на практике: **сцене нужны разрывы в маске**. Радиальное размытие большого сплошного
неба даёт просто засветку кадра, а не шахты, — поэтому у дальней стены появились пять колонн, и только между
ними лучи стали видимыми и измеримыми. Сила по умолчанию снижена до `0.08`: это доля рассеянного света, а не
яркость сама по себе, и при `0.8` эффект перекрывал кадр целиком.

### Движковые находки

- **ресурсы render graph однослойные по мипам**, поэтому пирамида собрана из отдельных ресурсов на уровень
  (`bloom_half … bloom_sixteenth`) с размерами через `declare_values` + `scale`. Работает и даже удобно
  читается, но мип-цепочка одним ресурсом была бы дешевле по памяти и дескрипторам — записано как пробел;
- **`usage = general` у картинки теперь честный read-write storage image.** Layout (`eGeneral`), usage-флаг
  (`eStorage`) и access-маска (read+write) у него уже были правильные, а тип дескриптора выдавался буферный —
  из-за чего шаг не мог одновременно читать и писать одну картинку. Аддитивный подъём пирамиды делает именно
  это, поэтому пробел был исправлен в движке, и ping-pong ресурсы на каждый уровень не понадобились;
- **`submit` ограничен шестнадцатью группами**, а пассов в цепочке уже двенадцать. Поэтому понижение и подъём
  сделаны МНОГОШАГОВЫМИ пассами: барьеры между шагами выводятся из дескрипторов шагов, а группы не тратятся;
- шейдер понижения один на четыре шага (варианты различает specialization-константа), и тут вылезло
  требование Vulkan: **layout обязан содержать все объявленные в шейдере биндинги**, даже если ветка отключена
  константой. Биндинг экспозиции добавлен всем уровням, хотя нужен только первому.

Среднее время кадра всей цепочки (двенадцать пассов, 1280×720, Iris Xe): `3.2 мс` — но напомню, что разброс
между одинаковыми прогонами здесь `±1 мс`, так что это порядок величины, а не измерение стоимости эффектов.

## Что даёт срез 7 — выходной тракт

Четыре мелких приёма, все в пассе компоновки: ни нового пасса, ни нового ресурса. Порядок применения не
произволен и следует физике: **аберрация и виньетка — оптика** (линейный свет, до кривой), **резкость — работа
с изображением** (после накопления), **зерно — свойство плёнки** (display-referred, после кривой), **дизер —
подготовка к квантованию** (в самом конце, амплитудой ровно в шаг).

### Резкость: это не исправление, а компромисс — и это измерено

Я записал в план, что резкость «лечит измеренное замыливание TAA». Измерение это опровергло: относительно
суперсэмплированного эталона нерезкое маскирование делает кадр **хуже**, и тем сильнее, чем оно больше —
`695 → 810 → 981` при силе `0 / 0.35 / 0.8`. Причина в overshoot: маска выбрасывает значение за пределы того,
что вокруг, и на кромках появляется звон.

Лечится защемлением результата диапазоном соседей (приём RCAS). После него та же сила `0.8` стоит `746`
вместо `981` — **клип срезает добавленную ошибку примерно вдвое**. Итоговая картина компромисса:

| вариант | отклонение от эталона | высокочастотная энергия |
|---|---|---|
| без TAA | **457** | 82.5 |
| TAA, без резкости | 695 | 50.6 (замылено) |
| TAA + резкость 0.35 | 725 | 56.4 |
| TAA + резкость 0.8 | 746 | 60.3 |
| TAA + резкость 1.5 | 774 | 64.2 |

Читается однозначно: резкость возвращает высокочастотную энергию в сторону эталонной (`50.6 → 64.2` против
`82.5`) за небольшую и **ограниченную** плату по точности. То есть это ручка вкуса с измеримой ценой, а не
исправление дефекта, и в документации это надо называть своим именем.

Отдельная ловушка, на которую я наступил: эталон привязан не только к точке обзора, но и **к сцене и к
настройкам**. После добавления колонн в срезе 6 старый эталон стал недействителен, и первое сравнение дало
RMSE около 4250 вместо ~700. Эталон надо перестраивать при любом изменении сцены.

### Дизер, виньетка, зерно

- **дизер** добавляет `353` различимых уровня в плавном градиенте неба вместо `327`, **не сдвигая яркость**
  (`220.80` против `220.79`). Именно это от него и требуется: убрать полосы, не сместив картинку. Шум
  треугольный (сумма двух равномерных) — при той же незаметности он убирает бандинг лучше равномерного;
- **виньетка** не трогает центр (`141.5 → 141.2`) и гасит угол (`199.3 → 172.6 → 135.3` при силе
  `0 / 0.25 / 0.6`);
- **зерно** меняется по кадрам (различие соседних кадров RMSE `1991`), то есть читается как зерно, а не как
  грязь на экране, и при этом **не смещает яркость** (`154.897` против `154.901`). Семя — функция номера
  кадра, поэтому дампы остаются сравнимыми.

Аберрация и зерно по умолчанию **выключены**: это приёмы на вкус, а не часть корректного тракта. Дизер и
виньетка включены — первый почти бесплатен и убирает реальный дефект, вторая дешева и почти всегда уместна.

## Что уйдёт при переходе на MSAA

Записано по итогам аудита, чтобы развилка не выглядела тумблером. MSAA — **другая форма конвейера**: шейдинг
здесь идёт compute-пассом из G-buffer, а множественные сэмплы требуют либо per-sample shading, либо
forward-шейдинга прямо при растеризации. Поэтому MSAA-вариант нуждается в своём forward-пассе.

Уходит: **TAA** (прямая альтернатива) вместе с джиттером и накопленной целью; **motion-векторы теряют
потребителя** (останутся только под motion blur); **временной сдвиг выборки AO** — усреднять его станет нечем,
и шум ляжет целиком на блюр (измерено: после блюра 8 проб ≈ 32, терпимо). Контракт истории остаётся
использованным только автоэкспозицией.

Остаётся без изменений всё **после resolve**: туман, экспозиция, tone mapping, bloom, лучи. SSAO выживает, но
экранные эффекты читают один сэмпл, поэтому кромки AO перестанут совпадать с геометрическими кромками MSAA.
Нюанс порядка: resolve обязан идти в линейном HDR ДО кривой, иначе яркий субпиксельный сэмпл ведёт себя не
так, как ожидается.

## Настройки эффектов и пресеты

К концу шести срезов видно, что у качества картинки **пять разных рычагов**, и они отличаются не силой, а
**ценой смены**. Это и есть та классификация, вокруг которой надо строить пресеты:

| рычаг | пример | цена смены |
|---|---|---|
| форма графа (какие пассы существуют) | нет пасса AO вообще | пересборка pipeline/фреймбуферов графа |
| размеры целей (`declare_values` + `scale`) | AO в половине против четверти | пересоздание ресурсов, `waitIdle` |
| глубина мип-цепочки (`mips = N`) | пирамида bloom на 4 против 6 уровней | пересоздание ресурсов |
| specialization-константы шага | `ao_samples`, `shaft_samples` | пересборка pipeline шага |
| числа в UBO | радиус AO, порог bloom, вес истории | бесплатно, живьём |

Отсюда два вывода.

**Первый: пресет обязан помечать уровень каждого переопределения.** Иначе движок не может честно ответить
«нужен перезапуск» или «применится сразу», а UI не может показать разницу. Форма — документ переопределений с
композицией:

```
{
  name = high
  base = medium              // дельта над базой, а не полное описание
  graph = pf03_post          // какие пассы вообще существуют
  values = [ viewport_half = [0.5, 0.5] ]           // уровень: ресурсы
  mips = [ bloom = 5 ]                              // уровень: ресурсы
  constants = [ compute_ao.ao_samples = 32 ]        // уровень: pipeline
}
```

**Второй, и более важный: числа UBO в пресет не входят.** Движку нечего знать про «радиус AO» — это
прикладной смысл; он владеет ресурсами, pipeline'ами и графами, а не физикой эффекта. Поэтому граница такая:
**пресет = движковые уровни (граф, размеры, мипы, spec-константы), настройки эффекта = прикладные числа**,
которые живут в настройках проекта и пишутся в UBO хостом. В UI они могут стоять рядом, но хранятся врозь и
имеют разную цену смены.

Правило, проверенное на PF02 и подтверждённое здесь: параметр, висящий на отладочной кнопке, живёт в UBO; в
spec-константы и define'ы он переезжает только став тиром качества, потому что их смена стоит пересборки
pipeline.

**Отдельное замечание про passthrough.** В площадке эффекты выключаются числом в UBO (`--ao=0`, `--taa=0`),
и пасс при этом продолжает выполняться. Для измерений это правильно — сравниваются два состояния одного
графа, — но для продукта неверно: на низком качестве пасс не должен выполняться вовсе. Это разные механизмы с
разными задачами, и путать их нельзя: `passthrough` для A/B, форма графа для тиров.

## Definition of Done первого среза — закрыт

Контракт истории закрыт, и тонкий G-buffer работает: проход кадра `N` читает результат кадра `N-1` с
корректным порядком и layout, отсутствие истории (первый кадр, resize, сброс) обрабатывается явно, а
motion-векторы — и камерные, и per-object — проверены численно, а не приняты на веру. Валидация чиста на всех режимах.

Дальше по цепочке остаётся общее требование площадки: каждый эффект имеет passthrough, цепочка валидирует
missing/incompatible inputs, GPU time и стоимость памяти каждого прохода доступны, а добавление простого
эффекта не требует специализированного C++ pass.
