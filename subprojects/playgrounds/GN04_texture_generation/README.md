# GN04 — фоновые текстуры на устройстве

Четвёртая лаборатория генераторной кампании и **первый настоящий потребитель вычислительной
очереди**. Полный контекст задачи — [`ORIGINATOR_GPGPU.md`](../../../ORIGINATOR_GPGPU.md), §5 п.5.

## Почему именно текстуры

Случай выбран не наугад: это единственное место, где **не мешает ни одна слабость очереди**.

| Слабость очереди | Почему здесь не мешает |
|---|---|
| передача съедает выигрыш (§4.5) | результат ОСТАЁТСЯ на устройстве: наружу едет сводка в 256 байт |
| детерминизма float на GPU нет (§4.1) | это ПРЕДСТАВЛЕНИЕ, а не симуляция — водораздел `NETWORKING.md` |
| воспроизводимость свёрток (§4.3) | свёртка здесь ЦЕЛОЧИСЛЕННАЯ, а целое сложение от порядка не зависит |
| короткая очередь бессмысленна | цепочка из четырёх проходов, и мёртвую работу видно глазами |

Проверять конструкцию надо там, где её слабости ни при чём. Иначе замер меряет слабости.

## Цепочка

Четыре прохода, все на устройстве:

1. **разметка Вороного** (`gather`): для каждого пикселя ближайший из N сайтов. В одну картинку
   уезжает НОМЕР области, в другую — разница расстояний до ближайшего и второго, то есть близость к
   границе. Сайты расставляет хост — множество маленькое и перечислено им самим, что правилом
   библиотеки разрешено;
2. **сглаживание с ФИЛЬТРОМ**: чтение выборкой по НЕЦЕЛОЙ координате, четыре отсчёта на половине
   текселя. Каждый из них аппаратный bilinear уже усреднил по четырём соседям — у буфера такого
   чтения нет вовсе, там пришлось бы читать шестнадцать элементов руками. Это и есть ответ на вопрос
   «что удобнее держать картинкой» (§6.3): то, что читают МЕЖДУ элементами;
3. **сборка цвета**: номер области → цвет (хешем от номера, таблицы цветов нет), сглаженная близость
   к границе → затемнение. Дальше эту текстуру читал бы пост-процесс;
4. **гистограмма** через атомики: сколько пикселей у каждой области. Только она и уезжает наружу.

## Числа (Iris Xe, 512x512, 64 области)

```
разметка Вороного    4.65 мс
сглаживание фильтром 0.87 мс
сборка цвета         0.85 мс
гистограмма          7.43 мс
ИТОГО на устройстве 13.81 мс
сводка наружу        0.58 мс, 256 байт
картинка осталась    1048576 байт — в 4096 раз больше того, что уехало
```

**Главное число — последнее.** Мегабайт остался на устройстве, наружу уехали двести пятьдесят шесть
байт: отношение `4096:1` и есть весь смысл §5 п.5. Круг передачи, который в §5 п.3 съедал 70% времени
на `remap`, здесь не платится вообще.

**Неожиданное число — гистограмма.** Она дороже самой разметки Вороного (`7.43` против `4.65` мс),
хотя работы в ней несравнимо меньше: один `atomicAdd` на пиксель против цикла по 64 сайтам. Причина —
КОНКУРЕНЦИЯ: 262144 пикселя бьются за 64 счётчика. Правильная форма известна и не сделана намеренно
(её стоит делать, когда свёртка понадобится по делу): накопление в разделяемой памяти группы и один
атомик на группу вместо одного на пиксель.

## Что проверяется (`--verify`, 11/11)

- гистограмма по областям сходится с числом пикселей — значит каждый пиксель куда-то попал;
- ни одна область не пуста — иначе разметка не разметка, а сводка врёт правдоподобно;
- разметка совпадает с эталоном на CPU. Сравнение осмысленно потому, что решение здесь
  ЦЕЛОЧИСЛЕННОЕ (номер области): разница арифметик меняет ответ только у пикселей ровно на границе;
- **фильтр действительно работал**: сглаженное поле отличается от исходного, и отличается заметно.
  Без этой проверки проход выборки был бы дорогим копированием, и по картинке этого не видно;
- сглаженное поле остаётся внутри диапазона исходного — среднее четырёх отсчётов лежит в выпуклой
  оболочке, а нарушение означало бы чтение мимо картинки;
- **свёртка целыми через атомики повторяется прогон в прогон**, хотя порядок прихода групп ничем не
  закреплён: целочисленное сложение от порядка не зависит. Плавающее зависит, и §4.3 называет это
  единственным больным местом свёрток;
- четыре программы скомпилированы РОВНО ЧЕТЫРЕ раза на два прогона — кэш по тексту сработал. Без
  проверки он перестал бы работать незаметно;
- наружу уехала сводка, а не картинка.

## Ключи

```
--size=N     сторона текстуры (по умолчанию 1024)
--sites=N    число областей (по умолчанию 64)
--seed=N     зерно расстановки сайтов
--verify     контрактные проверки
--dump=PATH  сохранить видимую текстуру в PPM — ДЛЯ ГЛАЗА, не для конвейера
```

Окна у площадки нет, и это не недоделка: она доказывает, что картинка НЕ уезжает с устройства, а окно
это доказательство подменило бы. `--dump` назван отдельно ровно затем, чтобы его нельзя было спутать
со сводкой.

Без устройства Vulkan площадка печатает, что проверять нечего, и выходит успешно: «устройства нет» —
законный ответ (§4.6), а не провал сборки.

## Чего здесь нет

- **проходы связаны руками, и это уже не единственный способ.** Составление pipeline из очереди
  появилось следующим шагом (`devils_engine::originator_device`, §8), но работает оно над БУФЕРАМИ, а
  эта площадка — про картинки: у устройственного плана образов пока нет. Перевести её на план значит
  сначала научить план картинкам, и это следующая работа именно здесь;
- переходы layout: картинки живут в `GENERAL` всё время. Упрощение названо в `compute_context.h` —
  правильный путь (вывод переходов из привязок) у painter уже есть в render-графе, и второй заводить
  здесь нельзя;
- барьеров между проходами нет, потому что каждая отправка ждёт свой fence. У настоящей очереди,
  уходящей на устройство ОДНОЙ отправкой, они понадобятся — и выводятся тем же вопросом, которым
  выводится проверка мёртвой работы (§6.1);
- накопление гистограммы по группам (см. выше).
