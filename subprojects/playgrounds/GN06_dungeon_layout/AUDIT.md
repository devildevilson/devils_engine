# Аудит GN06, 2026-09-29

## Итог

GN06 не остался на стадии идеи. Основной режим `site` уже собирает проверяемую
2D-композицию одной авторской локации: назначения областей, дерево связей,
выпуклые части, реальные дверные и открытые стыки, завершения путей и локальные детали.

Ощущение бесконечной площадки объясняется прежде всего смешением четырёх экспериментов
и будущих направлений в прежней документации. `cave`, `building`, `motifs`, `site` —
разные модели с разным порядком решений, не четыре стадии одного общего конвейера.
Уточнённая рабочая карта находится в [README](README.md).

При этом цель «любая тематическая локация полностью описана данными и загружается
как игровой ресурс» ещё не достигнута. Самые существенные границы — зависимость
каталогов от старого опыта, процедурная геометрия в GN06 и интерфейс результата,
ориентированный на viewer. Они важнее дальнейшей настройки отдельных коридоров.

## Что уже есть относительно первоначального замысла

| Замысел | Реальное состояние |
|---|---|
| Абстрактные области вместо обязательной схемы «комната + коридор» | Есть в `site`: назначение, категория и геометрия разделены; старый `cave` сохранён для сравнения |
| Несколько камер, пыточных и служебных путей; лаборатория не обязана следовать за пыточной | Есть: количества и родители варьируются по правилам; соединения пока образуют дерево |
| Авторские выразительные блоки | Есть словарь стилей и процедурные формы; библиотеки моделей/полных геометрических мотивов ещё нет |
| WFC для кусочков, не для всей судьбы данжа | Есть: локальные Wang-узоры пола; они не меняют геометрию или связи |
| Разные размеры, выпуклые части, диагональ, округлая сторона и обход вокруг неё | Есть в поддержанных шаблонах; произвольного набора форм или свободного поворота любой области нет |
| Проверяемое прохождение всей локации с возвращением ко входу | Есть проверки графа, полигонов и пола; обратный путь следует из двусторонних связей. Это не навигация игрового персонажа заданного размера |
| Оправдание или сокращение лишней длины пути | Есть `trim/accent/vary` для обоих торцов; только крайняя часть и один вид альковы |
| Реплика на основании расположения камеры относительно маршрута | Есть кандидат, упрощённая проверка обзора и токен `transfer_seen`; нет события, памяти конкретного NPC и текста диалога |
| Вход и пересечение с чанковым окружением | Есть западный вход и синтетическая маска поверхности; реальной интеграции с чанками нет |
| Локация из нескольких секций, переход в пещеру, состаривание | Пока обсуждённые направления, не реализованные преобразования |
| Воспроизведение по seed и входам | Проверяется для одинаковой реализации и полных каталогов; нет хеша правил или хранения старых версий |
| 3D и стриминг по R/r | Вне текущего среза; viewer пересобирает результат синхронно |

## Находки и ограничения

### 1. Обязательные ресурсы скрыты от обычного добавления в Git

Приоритет: исправить перед фиксацией текущей площадки. Это конкретная проблема
сохранности исходников, не ошибка генерации в нынешнем рабочем дереве.

Корневое правило `.gitignore:4: build*` игнорирует:

- `resources/gn06/generator/building.tavl`;
- `resources/gn06/generator/building_buffers.tavl`.

Оба файла есть на диске, но обычный `git add` каталога их пропустит. Более того,
[generator_registry](src/main.cpp) безусловно загружает генератор здания даже при
запуске `site`: отсутствие этих ресурсов затронет не только старый режим.
Вывод о риске переноса следует из проверки ignore-правила и загрузчика;
отдельная сборка из чистого checkout в этом аудите не выполнялась.

Проверка:

```sh
git check-ignore -v subprojects/playgrounds/GN06_dungeon_layout/resources/gn06/generator/building.tavl subprojects/playgrounds/GN06_dungeon_layout/resources/gn06/generator/building_buffers.tavl
```

Нужно отдельно уточнить область ignore-правила или исключить эти ресурсы.
В рамках аудита правило и индекс Git не менялись.

### 2. «Мотив» пока не единый ресурс геометрии, стиля и размещения

В [motif_demo.cpp](src/motif_demo.cpp) `motif_style` содержит имя, знак, цвет и палитру.
Размеры, формы и правила связей находятся в `site.tavl`, а реализации форм —
в [site_graph.cpp](src/site_graph.cpp). Библиотечный `motif` — непрозрачный id;
сам по себе он не вызывает модель или геометрическую процедуру.

Это рабочее разделение для стенда, но нельзя описывать нынешний `motifs.tavl`
как уже готовую библиотеку полноценных строительных моделей. README теперь
отделяет назначение области, геометрический рецепт, мотив, палитру и экземпляр.

Есть и скрытая зависимость: `site` не использует старые `motifs.tavl.rules`
для построения графа, но `bind_authored_motifs` вызывает общий `read_catalogue`.
Тот по-прежнему требует и разбирает `locations`, `scales` и `rules`, включая
их родителей и размеры. Удалить старую программу из файла, оставив только
нужные `site` стили и палитры, пока нельзя.

### 3. Сборщик не универсален, а описание тематики ещё не замкнуто в данных

[read_site](src/site_graph.cpp) знает закрытый набор форм и способов пристыковки.
`oblique`, `round_east`, `wrap_east` реализованы кодом площадки. Перцепция обязательна
в декларации; `check` также требует кандидата рядом с выбранным маршрутом.
Это не нейтральная обязанность любой возможной темы.

`--verify` содержит проверки конкретных видов замка; часть защищена условием
`site.name == black_castle_dungeon`, часть учитывает имена отдельных видов при сборе
статистики. Новая тема требует отдельно проверить применимость этого сценария.
`theme` сейчас только метка; CLI не выбирает другой каталог или версию правил.

В [originator](../../../libs/originator/README.md) уже вынесены общие геометрические
операции. Тематический граф, размещение сложных форм и конечная декларация `site`
остаются в GN06. Это граница прототипа, а не готовый универсальный API локаций.

### 4. Проверка полигонов независима, весь процесс `site` — ещё нет

`check_site_plan` проверяет выпуклость, пересечения, общие отрезки и связность частей
без клеток. Наклонная дверь действительно должна касаться обеих стен; соседних
растровых клеток недостаточно. Регрессия со сдвигом на 1/256 это защищает.

Однако `place_once` затем строит сетку и вызывает `trace_perceptions`.
`place` принимает вариант только после `check_projection`; растровый разрыв или
незаявленное соседство вызывают повторную укладку. Маршрут и обзор тоже растровые.
Поэтому верно «геометрическая истина в полигонах», но неверно «ни одно решение
`site` не зависит от сетки». Полная независимость от окна/разрешения проверена
в `building`, не в нынешнем `site`.

### 5. Разнообразие ограничено программой роста, а не общим решателем композиции

`assemble` добавляет каждому новому функциональному узлу одного родителя;
технический соединитель лишь делит ребро надвое. `check` явно требует дерево.
У `site` нет свободных циклов или поиска произвольного графа по обязательным соседствам.

Размещение ограничено 96 кандидатами на область и 256 укладками того же графа.
Оно может выбирать более подходящий профиль изгиба, но не прокладывает путь
между заранее закреплёнными точками. Отказ не доказывает математическую
невозможность размещения — только исчерпание поддержанного поиска.
`layout_attempts` в отчёте считает кандидатов успешной укладки, а не суммарную
работу всех отброшенных вариантов.

Завершение пути тоже локально: `trim_motif_path_end` сдвигает один внешний торец.
Оно не удаляет всю ненужную ветвь и не перестраивает её соседей. Поэтому остающийся
длинный проход не обязательно является поломкой политики завершения.

### 6. Локальная детализация не обещает единого узора по всему полу

WFC решается на прямоугольном резерве каждого экземпляра, а потом показывается
в его геометрии. Проверки сокетов относятся к отдельному образцу до общей проекции.
Через стыки выпуклых частей узор не согласуется; сетка палитры не поворачивается
вдоль диагональной оси. Пересечение резервов может оставить семантический цвет
вместо деталей. `marked` не равен числу уникальных видимых клеток.

Это допустимо для сегодняшнего визуального слоя. Если тайлы станут геометрией,
препятствиями или реальными коммуникациями, нынешних обещаний будет недостаточно:
потребуются границы/порты образцов и проверка уже итогового слоя.

### 7. Публичный результат пока рассчитан на просмотр, не на потребителя игры

Полный `graph`, кандидаты и подтверждённые перцепции — внутренние структуры
[site_graph.cpp](src/site_graph.cpp). Публичный [site_view_scene](src/site_graph.h)
содержит геометрию, соединения, исходы торцов, растры, строки свойств и число
перцепций, но не структурированный граф назначений и набор фактов для NPC.

Пространственное «может видеть участок» также не означает «видел событие».
Для нынешнего стенда это достаточно; переносить строки viewer как игровой
формат данных не стоит. Перед вторым реальным потребителем полезнее выделить
типизированный результат плана, чем продолжать наращивать строки свойств.

## Проверка в этом аудите

Повторно выполнено:

- Release CTest: **218/218** по фильтру `originator|GN06|gn06_viewer`.
  В этот набор входят 73 узких теста GN06, геометрии мотивов, структурных инструментов
  и страниц viewer. Это не число тестов одной площадки и не весь тестовый набор движка.
- Сценарии `site --verify`: все три масштаба, перебор seeds 0…127,
  отдельный зарезервированный вход и синтетическая поверхность; на `large` —
  дополнительный каталог зеркальных пар залов. Массовый перебор в `--verify`
  проверяет геометрию, но не решает WFC для каждого перебираемого seed.
- Обычная генерация с WFC и `--surface=cut`: **96/96** запусков,
  seeds 0…31 во всех трёх масштабах.
- Примеры `building` из нового README: участок 301 единица в растре 78×78
  и отдельное окно 64×64; оба запуска завершились с кодом 0.
- Отдельно воспроизведён `site/large/seed=0`: 35 областей, 34 связи,
  4 кандидата перцепции, 1 подтверждение, алькова одного пути и сокращение другого на 6 единиц.

Исходники генератора в ходе аудита не менялись, повторная компиляция не выполнялась.
Проверялась существующая Release-сборка. Новый GUI-прогон и автоматизация клавиатуры
не выполнялись: headless-проверка свойств не доказывает интерактивное листание страниц.
Детерминизм между платформами и многопоточная фоновая генерация здесь также не проверялись.

## Где разумно поставить границу

Текущий срез можно зафиксировать как **проверяемую 2D-композицию одного авторского данжа**.
Для этого не требуется одновременно добавлять секции, пещеры, состаривание и стриминг.

Ближайшие отдельные решения: сначала сохранить все обязательные ресурсы;
затем, если продолжаем обобщение, развести библиотеку мотивов и старую программу
`motifs`, выделить результат плана для потребителя и попробовать вторую тему
на уже имеющемся словаре. Это покажет, каких общих операций действительно не хватает.
Ни одна из этих рекомендаций не реализовывалась автоматически в рамках аудита.
